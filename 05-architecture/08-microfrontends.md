## Теория

### Что это и чем не является

Микрофронтенды (micro-frontends) — архитектурный стиль, при котором **независимо поставляемые** фронтенд-приложения композируются в один продукт (Cam Jackson, martinfowler.com). Ключевое слово — *независимо поставляемые*: если для выкладки изменения каталога нужно пересобрать и выкатить shell, это не микрофронтенды, а модульный монолит с лишней сложностью.

Минимальный набор свойств:
- **Независимый деплой** каждого фрагмента без релиза остальных.
- **Владение командой** end-to-end: от UI до (часто) BFF/бэкенда своего домена.
- **Изоляция отказов**: падение одного фрагмента не кладёт страницу.
- **Явные контракты** между фрагментами (как публичное API).

### Когда нужны: закон Конвея и автономность

**Закон Конвея** (Melvin Conway, 1968): организации проектируют системы, копирующие их коммуникационную структуру. Следствие для фронтенда: если 10 команд коммитят в один SPA с одним релизным поездом, архитектура неизбежно станет отражением этой «общей комнаты» — общий стор, общие компоненты, конфликты в одних файлах.

**Обратный манёвр Конвея** (inverse Conway maneuver): сначала нарезать команды по бизнес-доменам (stream-aligned teams из Team Topologies), затем дать им архитектуру, где граница модуля = граница команды. Микрофронтенды — один из способов закрепить эту границу **на уровне деплоя**.

Сигналы «пора»:

| Сигнал | Почему это аргумент |
|---|---|
| 4–5+ продуктовых команд в одном фронтенде | Координация релизов стоит дороже, чем инфраструктура MF |
| Общий релиз блокирует команды (заморозки, «поезд ушёл») | MF дают независимый time-to-production |
| Чёткие доменные границы (каталог, корзина, ЛК, админка) | Есть по чему резать без постоянных кросс-вызовов |
| Миграция большого легаси по частям | Strangler fig: новое рядом со старым |
| Интеграция продуктов разных подразделений/компаний | Разные стеки, разные циклы — нужна runtime-композиция |

Сигналы «не надо»:
- 1–2 команды. Модульность решается [FSD](03-fsd.md) / монорепо с границами (Nx tags, Steiger).
- Проблема — в плохой модульности, а не в релизах: MF превратят «большой ком грязи» в «распределённый ком грязи».
- Домены сильно переплетены (каждая фича трогает 3 «микрофронтенда»).
- Хочется «попробовать Svelte в одном углу» — технологическая свобода в MF чаще риск, чем ценность (двойной рантайм, найм, DS в двух реализациях).

💡 На собеседовании: «Сначала спрашиваю, какую организационную проблему решаем. Промежуточные шаги, которые часто достаточно: монорепо с независимыми CI-пайплайнами, отдельные приложения на своих путях под общим доменом (вертикальная нарезка без runtime-интеграции). MF — когда нужна композиция фрагментов разных команд на одной странице и независимый деплой».

### Вертикальная vs горизонтальная нарезка

- **Вертикальная** (по страницам/роутам): `/catalog/*` — команда каталога, `/account/*` — команда ЛК. На странице один владелец. Проще всего: изоляция, роутинг, производительность. Часто достаточно reverse proxy + общей шапки.
- **Горизонтальная** (фрагменты на одной странице): на странице товара — блок рекомендаций одной команды, корзина-виджет другой. Гибче, но дороже: shared-зависимости, CLS, контракты, оркестрация загрузки.

Правило: начинать с вертикальной, горизонтальную — только для действительно переиспользуемых сквозных виджетов (шапка, корзина, чат поддержки).

### Способы композиции

#### 1. Build-time интеграция (npm-пакеты)

Каждая команда публикует пакет, shell их импортирует. Плюсы: типы, tree-shaking, один бандл, нулевая runtime-сложность. Минус: **релиз общий** — чтобы выкатить новую версию каталога, shell обновляет зависимость и деплоится. Это модульный монолит; хорошо для design system и SDK, но независимости деплоя нет.

#### 2. Server-side composition

Страница собирается из HTML-фрагментов на сервере/edge: SSI (Nginx), ESI (Varnish, CDN), собственный composition-сервис или edge-функции. Каждый фрагмент — отдельный сервис со своим деплоем.

Плюсы: быстрый первый рендер и SEO, работает без JS, естественная изоляция. Минусы: интерактивность требует гидратации каждого фрагмента (и согласования, кто грузит React), сложнее кэширование персонализированных фрагментов, таймауты медленного фрагмента (нужен fallback и бюджет на фрагмент).

#### 3. iframe

Максимальная изоляция: свой JS-контекст, свой CSS, свой origin (можно sandbox). Цена: размер по контенту (ResizeObserver + `postMessage`), модалки не выходят за границы, двойная загрузка рантаймов, плохой SEO, сложная a11y (фокус, скринридеры), история браузера. Оправдан для недоверенного/стороннего контента, легаси-приложений «как есть», платёжных форм.

#### 4. Web Components

Каждый микрофронтенд регистрирует custom element (`<mf-cart>`), внутри — любой фреймворк. Контракт — атрибуты/свойства на вход и DOM-события (`CustomEvent`) на выход. Shadow DOM даёт изоляцию стилей.

```ts
// Обёртка React-приложения в custom element — контракт: атрибут user-id, событие cart:change
class CartElement extends HTMLElement {
  static observedAttributes = ['user-id'];
  #root?: import('react-dom/client').Root;

  async connectedCallback() {
    const { mount } = await import('./mount'); // React грузится лениво
    this.#root = mount(this.attachShadow({ mode: 'open' }), {
      userId: this.getAttribute('user-id'),
      onChange: (count: number) =>
        this.dispatchEvent(new CustomEvent('cart:change', { detail: { count }, bubbles: true, composed: true })),
    });
  }
  disconnectedCallback() { this.#root?.unmount(); }
  attributeChangedCallback() { /* перерендер с новыми props */ }
}
customElements.define('mf-cart', CartElement);
```

🪤 Ловушка: Web Components — **способ упаковки и контракт**, а не способ загрузки. Скрипт custom element всё равно надо как-то доставить (тег `<script type="module">`, import maps, Module Federation). И `composed: true` обязателен, чтобы событие вышло за shadow root.

#### 5. Module Federation

Runtime-загрузка модулей из отдельно собранных и задеплоенных бандлов с **разделяемыми зависимостями**. Появилась в webpack 5 (`container.ModuleFederationPlugin`). Термины: **host** (потребитель), **remote** (поставщик, `exposes`), **shared** (общие зависимости), **share scope** (реестр версий в рантайме).

**Module Federation 2.0** (проект module-federation.io) выносит рантайм из webpack в отдельные пакеты и добавляет:
- **manifest** (`mf-manifest.json`) вместо прямой ссылки на `remoteEntry.js` — метаданные о exposes/shared, удобно для реестров и devtools;
- **динамические type hints** — типы remote скачиваются потребителем;
- **Federation Runtime** — загрузка remotes в рантайме без build-плагина (`createInstance`, `loadRemote`, `registerRemotes`);
- **runtime plugins** — хуки жизненного цикла загрузки (ретраи, fallback, подмена URL);
- **Chrome DevTools** расширение.

Интеграции (по module-federation.io): `@module-federation/enhanced` для webpack и Rspack (`@module-federation/enhanced/rspack`), `@module-federation/rsbuild-plugin` для Rsbuild/Rslib, `@module-federation/vite` для Vite, отдельные пакеты для Modern.js, Next.js, Metro.

```ts
// module-federation.config.ts (Rspack, MF 2.0)
import { createModuleFederationConfig } from '@module-federation/enhanced/rspack';

export default createModuleFederationConfig({
  name: 'shell',
  remotes: {
    // <имя remote>@<URL манифеста>
    catalog: 'catalog@https://cdn.example.com/catalog/mf-manifest.json',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^19.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^19.0.0' },
  },
});
```

```tsx
// Загрузка remote в рантайме (адрес приходит из реестра, а не зашит в сборку)
import { createInstance } from '@module-federation/enhanced/runtime';

const mf = createInstance({
  name: 'shell',
  remotes: [{ name: 'catalog', entry: registry.catalog.manifestUrl }],
});
const CatalogPage = lazy(() => mf.loadRemote<{ default: ComponentType }>('catalog/CatalogPage')
  .then(m => m ?? { default: CatalogFallback }));
```

🪤 Ловушка: Vite-плагины MF и webpack/Rspack-реализация исторически отличались возможностями и форматом вывода; смешивание сборщиков в одной федерации проверяйте PoC-ом, а не по README.

#### 6. single-spa и import maps

**single-spa** — оркестратор: регистрирует приложения и монтирует/размонтирует их по активному URL. Каждое приложение экспортирует lifecycles `bootstrap`, `mount`, `unmount` (есть адаптеры для React/Vue/Angular). Загрузка модулей — через import maps (нативные или SystemJS) или Module Federation.

```ts
import { registerApplication, start } from 'single-spa';

registerApplication({
  name: '@shop/catalog',
  app: () => import('@shop/catalog'),        // резолвится через import map
  activeWhen: ['/catalog'],
  customProps: { authToken: () => session.token },
});
start();
```

```html
<script type="importmap">
  { "imports": { "@shop/catalog": "https://cdn.example.com/catalog/1.42.0/main.js" } }
</script>
```

Import map = **реестр версий**: деплой remote = обновление одной строки в map, откат — вернуть предыдущий URL. Минус: shared-зависимости приходится выносить в import map вручную (одна версия на всех), нет автоматического согласования версий, как в MF.

### Сравнение подходов

| | Build-time | Server-side | iframe | Web Components | Module Federation | single-spa + import maps |
|---|---|---|---|---|---|---|
| Независимый деплой | нет | да | да | да (с runtime-загрузкой) | да | да |
| Изоляция JS | нет | частичная | полная | нет | нет | нет |
| Изоляция CSS | нет | нет | полная | Shadow DOM | нет (дисциплина) | нет (дисциплина) |
| Общие зависимости | естественно | сложно | нет (дубли) | вручную | автоматически (share scope) | вручную через map |
| SEO / первый рендер | отлично | отлично | плохо | средне (SSR сложно) | средне (SSR сложно) | средне |
| UX-целостность (модалки, фокус) | отлично | хорошо | плохо | хорошо | отлично | хорошо |
| Разные фреймворки | нет | да | да | да | можно, но дорого | да (основной сценарий) |
| Сложность инфраструктуры | низкая | высокая | низкая | средняя | средняя–высокая | средняя |
| Типовой кейс | DS, SDK | контентные/e-commerce витрины | сторонний/легаси-контент | виджеты для чужих страниц | SPA из доменов одной компании | миграция между фреймворками |

### Изоляция стилей

Без изоляции два микрофронтенда с `.button {}` или разными reset-ами ломают друг друга, причём порядок загрузки CSS недетерминирован.

| Приём | Как работает | Ограничения |
|---|---|---|
| **Shadow DOM** | Стили внутри shadow root не протекают наружу и внутрь | Порталы (модалки в `document.body`) выпадают из shadow root; `@font-face` надо объявлять в документе; CSS-переменные и наследуемые свойства (`color`, `font`) проникают — это фича для тем |
| **CSS Modules** | Хэшированные имена классов | Глобальные селекторы (`:global`, теги, reset) не изолируются; задайте префикс в `localIdentName`, чтобы хэши разных сборок не совпали |
| **Префиксы / неймспейсы** | `.catalog-*`, Tailwind `prefix`, BEM-блок на MF | Дисциплина, нужен линтер (stylelint `selector-class-pattern`) |
| **CSS-in-JS с ключом** | Разные `key`/`prefix` у экземпляров Emotion/styled-components | Рантайм-стоимость, два экземпляра библиотеки |
| **Каскадные слои `@layer`** | Явный порядок приоритета: `@layer reset, ds, shell, remotes;` | Не изоляция, а **управление приоритетом**: решает «чей reset победил», но не конфликт одинаковых имён |
| **`@scope`** | Ограничивает селекторы поддеревом | Поддержка браузерами появилась недавно — проверяйте caniuse перед использованием |

Практика: design system и токены — от shell (CSS-переменные, singleton DS-пакет), глобальный reset — один, в shell, в `@layer reset`; remotes не пишут глобальных селекторов; CSS remote удаляется/не мешает при unmount (CSS Modules + lazy-чанки стилей).

### Роутинг

Типовая схема — **двухуровневый роутинг**:
- **Shell-роутер** владеет верхним уровнем: `/catalog/*` → remote `catalog`, `/account/*` → `account`, 404, редиректы, guards авторизации.
- **Remote-роутер** владеет вложенными путями внутри своего префикса (`basename="/catalog"`).

```tsx
// shell: верхний уровень
const routes = [
  { path: '/catalog/*', element: <RemoteBoundary name="catalog" load={() => import('catalog/App')} /> },
  { path: '/account/*', element: <RemoteBoundary name="account" load={() => import('account/App')} /> },
  { path: '*', element: <NotFound /> },
];
```

Проблемы и решения:
- **Два экземпляра роутера читают одну history.** Нужна одна история браузера: remote получает `basename` и **не создаёт** свою `BrowserRouter` поверх чужой, а использует navigation API, переданный shell (или singleton-роутер в shared).
- **Навигация между MF**: remote не знает путей чужих доменов. Shell даёт `navigate(to)`; кросс-ссылки — через общий пакет «карты маршрутов» (аналог `shared/routes` из FSD) или события `navigate-request`.
- **Синхронизация при `history.pushState` извне**: `pushState` не генерирует `popstate`. single-spa для этого патчит history и даёт `navigateToUrl`; в своей реализации — единый `navigate` от shell.
- **Владение 404 и deep links**: неизвестный путь внутри `/catalog/*` — 404 каталога; неизвестный префикс — 404 shell.
- **Сохранение состояния при уходе с MF** — URL как источник истины (фильтры в query string), не память remote.

### Shared-зависимости: React дважды и версии

Опции `shared` (webpack/MF 2.0): `singleton` (одна версия на весь share scope), `requiredVersion` (диапазон semver), `eager` (включить в начальный чанк, а не грузить асинхронно), `shareScope`, `import: false` (не бандлить свою копию — только брать из scope); в webpack также `strictVersion` (бросать ошибку, а не предупреждение, при несовместимой версии singleton).

Как разрешаются версии (по документации MF): при `singleton` и рассогласовании загружается **более высокая** версия, стороне с меньшей версией выводится warning; без `singleton` при разных версиях каждый грузит свою копию.

**Почему два React — катастрофа:** хуки работают через внутренний диспетчер конкретного экземпляра `react`. Если `react-dom` из shell рендерит компонент, который импортировал `useState` из другой копии `react`, получаем «Invalid hook call». Context из одной копии не виден в другой — провайдеры shell «пропадают» в remote. Поэтому `react`, `react-dom`, роутер, библиотеки с Context/синглтон-состоянием (state-менеджер, i18n, DS с ThemeProvider) — `singleton: true`.

```js
// bootstrap-паттерн: async boundary, чтобы share scope успел инициализироваться
// index.js
import('./bootstrap');
// bootstrap.js
import { createRoot } from 'react-dom/client';
import { App } from './App';
createRoot(document.getElementById('root')).render(<App />);
```

Политика shared на уровне платформы:
- Список singleton-зависимостей и **допустимые диапазоны** версий — общий конфиг-пакет (`@company/mf-shared-config`), обновляется платформенной командой.
- Мажор React/DS — скоординированное событие: сначала shell поднимает диапазон, remotes мигрируют в окно совместимости.
- Не шарить всё подряд: каждая shared-зависимость — **связь релизов**. Мелкие утилиты (date-fns, lodash-es) пусть дублируются.
- `eager: true` — только для shell и только для критичного (увеличивает начальный бандл); иначе async boundary.

### Коммуникация между микрофронтендами

Чем меньше, тем лучше: каждый канал — контракт, который нельзя ломать.

| Канал | Когда | Риски |
|---|---|---|
| **URL** (path, query) | Основной: «что показываем» — фильтры, выбранный товар | Только сериализуемое состояние |
| **Props/customProps от shell** при монтировании | Контекст: пользователь, локаль, токен-геттер, фича-флаги, `navigate` | Read-only, версия контракта |
| **DOM `CustomEvent`** / типизированная шина на `EventTarget` | Факты: `cart:updated`, `auth:logout` | Нет гарантии доставки поздним подписчикам — нужен «последний снапшот» или запрос состояния |
| **Общий бэкенд/BFF** | Источник истины для данных | Задержки, но это правильно |
| **Общий стор** (один Redux на всех) | Почти никогда | **Анти-паттерн**: распределённый монолит — изменение формы стейта ломает чужие команды, деплои снова связаны |

Нюанс про «общий стор — анти-паттерн?». Плохо — общий **изменяемый** стор, в который пишут все. Допустимо — **read-only контекст платформы** (сессия, локаль, флаги), который принадлежит shell и выставлен через узкое версионированное API (`platform.session.subscribe()`), а не через доступ к внутреннему стейту.

```ts
// Контракт событий — отдельный версионированный пакет @shop/mf-contracts
export type MfEvents = {
  'cart:updated': { count: number; version: 1 };
  'auth:logout': { reason: 'user' | 'expired' };
};
// Добавлять поля можно, удалять/переименовывать — только через новое событие (cart:updated.v2)
```

### Деплой и версионирование

- **Каждый remote — свой пайплайн** и свой CDN-префикс. Ассеты с хэшем — `Cache-Control: immutable`; точка входа (`mf-manifest.json`/`remoteEntry.js`/import map) — короткий кэш или `no-cache`.
- **Резолвинг версий**: (а) статический URL `.../catalog/latest/` — просто, но откат = передеплой; (б) **реестр** (discovery service / import map / JSON `{ name → manifestUrl }`), который shell читает при старте — деплой и откат = изменение записи, канарейка = разные записи для части пользователей.
- **Version skew**: старый shell + новый remote и наоборот существуют одновременно (кэш, открытые вкладки). Контракты — обратно совместимые; breaking change = новый exposed-модуль или новое событие, старое удаляется после окна депрекации.
- **Откат одного MF** не должен требовать отката остальных — проверьте это на практике до первого инцидента.
- **SemVer для exposes** и changelog контракта; потребители-тесты (consumer-driven contracts) в CI поставщика.

### Тестирование

| Уровень | Что | Где |
|---|---|---|
| Unit/компонентные | Внутри MF как обычно | CI remote |
| Контрактные | Типы exposed-модулей (MF type hints / пакет контрактов), схемы событий, consumer-driven тесты | CI remote: «не сломал ли я shell» |
| Интеграционные shell | Shell с **заглушками** remotes (fake remote, возвращающий фиксированный компонент) | CI shell |
| E2E | Сборка «как в проде» по реестру; короткий smoke после каждого деплоя любого MF | Отдельный пайплайн, по событию деплоя |
| Локальная разработка | Shell с прод-remotes + один локальный (override URL в реестре / DevTools) | Машина разработчика |

🪤 Ловушка: полный e2e-регресс на каждый деплой любого MF возвращает общий релизный поезд. Цель — короткий smoke + контрактные тесты, а не «прогоняем всё».

### Производительность

- **Водопад загрузки**: HTML shell → JS shell → манифест remote → entry remote → чанки. Лечение: `<link rel="preload"/modulepreload>` для манифестов критичных remotes, префетч remote по hover/виду ссылки, SSR/стриминг для первого экрана.
- **Дублирование зависимостей**: несовпадение диапазонов → две копии; аудит через bundle-анализатор и MF DevTools; общий бюджет.
- **Несколько фреймворков на странице** — двойной рантайм, двойная гидратация. Один основной фреймворк — норма для MF внутри компании.
- **CLS**: поздно загруженный фрагмент сдвигает контент — резервировать место (skeleton с фиксированной высотой).
- **Performance budget на MF** (размер начального JS, LCP/INP вклад) — проверка в CI каждого remote; общий RUM.

### Observability и изоляция отказов

- **Error boundary на каждый remote** + fallback UI («Рекомендации временно недоступны»); ошибка загрузки чанка (`ChunkLoadError`) — ретрай, затем fallback. В MF 2.0 это удобно делать runtime-плагином.
- **Атрибуция**: каждая ошибка и RUM-метрика тегируется `mf.name` + `mf.version` (release). Без этого инцидент «страница тормозит» не имеет владельца.
- **Алертинг по владельцу**: ошибки remote — в канал его команды.
- **Фича-флаги и kill switch** на уровне реестра: отключить проблемный remote без деплоя.

### Миграция монолита через strangler fig

1. **Поставить shell перед монолитом**: reverse proxy/edge-роутинг по путям; всё, что не мигрировано, уходит в монолит (монолит = «один большой remote» или просто бэкенд по префиксу).
2. **Платформа**: реестр, shared-конфиг, контракт контекста (сессия, локаль), DS-пакет, шаблон remote, CI-шаблон, observability.
3. **Первый домен** — некритичный, с чёткой границей (обучение на нём).
4. **Переносить вертикально** — страницы целиком; горизонтальные фрагменты — только для сквозных виджетов.
5. **Обратная интеграция**: новые MF внутри старых страниц — через Web Component-обёртку или mount-функцию.
6. **Новый код — только в MF**, метрика доли трафика/страниц вне монолита, дедлайн выключения монолита.

## Вопросы с собеседований

<details><summary>Когда микрофронтенды оправданы, а когда нет?</summary>

Оправданы, когда проблема организационная: несколько автономных команд с чёткими доменными границами упираются в общий релизный цикл; миграция легаси по частям; интеграция продуктов разных подразделений. Не оправданы при 1–2 командах, переплетённых доменах или когда реальная проблема — модульность (её решают FSD/монорепо). Упомянуть закон Конвея и промежуточные шаги: независимые пайплайны, вертикальная нарезка по путям без runtime-интеграции.
</details>

<details><summary>Что такое закон Конвея и как он связан с MF?</summary>

Структура системы повторяет коммуникационную структуру организации. Обратный манёвр — сначала нарезать команды по доменам, потом дать им архитектуру с границами по этим доменам. MF закрепляют границу команды на уровне деплоя. Если команды нарезаны по слоям (фронт/бэк/QA), MF не дадут автономии — каждая фича всё равно требует координации.
</details>

<details><summary>Сравните Module Federation, single-spa, iframe и Web Components.</summary>

MF — runtime-загрузка модулей с автоматическим согласованием shared-зависимостей; лучший UX для SPA одной компании на одном фреймворке. single-spa — оркестратор жизненного цикла приложений по URL, силён при разных фреймворках, загрузка через import maps или MF. iframe — полная изоляция ценой UX, a11y и производительности; для недоверенного/легаси-контента. Web Components — контракт и упаковка (атрибуты/события, Shadow DOM), не механизм загрузки. Их часто комбинируют: Web Component как контракт, MF как загрузчик.
</details>

<details><summary>Что будет, если в федерации загрузятся два React? Как предотвратить?</summary>

«Invalid hook call», потерянный Context (провайдеры shell не видны в remote), двойной размер. Предотвращение: `react`/`react-dom` — `singleton: true` с согласованным `requiredVersion`, async boundary (`import('./bootstrap')`) для инициализации share scope, единый shared-конфиг платформы, в webpack — `strictVersion` для раннего падения вместо тихой деградации. Проверка — MF DevTools/аудит бандла.
</details>

<details><summary>Как разрешается конфликт версий shared-зависимости?</summary>

Share scope регистрирует доступные версии. Без singleton каждая сторона берёт совместимую со своим `requiredVersion`, иначе свою копию. С singleton загружается одна (по документации MF — более высокая), стороне с меньшей версией — warning; `strictVersion` превращает несовместимость в ошибку. Поэтому мажоры singleton-зависимостей поднимают скоординированно: shell расширяет диапазон, remotes мигрируют.
</details>

<details><summary>Как изолировать стили микрофронтендов?</summary>

Shadow DOM — настоящая изоляция, но порталы и `@font-face` требуют внимания, CSS-переменные проникают (это удобно для тем). Без Shadow DOM — CSS Modules с префиксом сборки, неймспейсы/Tailwind `prefix`, запрет глобальных селекторов в remotes линтером. Один reset — в shell; `@layer` управляет приоритетом (reset < DS < shell < remotes), но не решает конфликты имён. Токены — CSS-переменные от shell.
</details>

<details><summary>Как устроить роутинг между shell и remotes?</summary>

Shell владеет верхним уровнем (префиксы, 404, guards), remote — вложенными путями под `basename`. Одна history; remote не создаёт свой корневой роутер поверх чужого, а получает `navigate` от shell. Кросс-доменные ссылки — общая карта маршрутов или запрос навигации у shell. Состояние, переживающее уход со страницы, — в URL.
</details>

<details><summary>Общий стор между микрофронтендами — анти-паттерн?</summary>

Общий изменяемый стор — да: связывает форму стейта и релизы всех команд, это распределённый монолит. Допустим read-only контекст платформы (сессия, локаль, флаги) с узким версионированным API от shell. Для фактов — события, для «что показываем» — URL, для данных — бэкенд/BFF как источник истины.
</details>

<details><summary>Как деплоить и откатывать remote независимо?</summary>

Свой пайплайн и CDN-префикс; хэшированные ассеты immutable, точка входа с коротким кэшем; реестр версий (import map / discovery JSON), который читает shell — деплой и откат = изменение записи, канарейка — разные записи по сегментам. Контракты обратно совместимы из-за version skew. Обязательно отрепетировать откат одного MF.
</details>

<details><summary>Как тестировать систему микрофронтендов?</summary>

Пирамида: unit внутри MF; контрактные тесты (типы exposes, схемы событий, consumer-driven) в CI поставщика; интеграционные тесты shell с заглушками remotes; короткий e2e-smoke на собранной по реестру системе после каждого деплоя. Полный регресс на каждый деплой — возврат к общему релизу. Локально — shell с прод-remotes и override одного URL.
</details>

<details><summary>Какие проблемы производительности приносят MF?</summary>

Водопад загрузок (shell → манифест → entry → чанки), дублирование зависимостей из-за рассогласованных версий, несколько фреймворков на странице, CLS от поздних фрагментов, сложность SSR. Лечение: preload манифестов, префетч по намерению, общий shared-конфиг, один фреймворк, резерв места, бюджеты производительности на MF и RUM с атрибуцией.
</details>

<details><summary>Как мигрировать монолит на MF?</summary>

Strangler fig: shell/edge-роутер перед монолитом, всё немигрированное — в монолит. Сначала платформа (реестр, shared-конфиг, контекст, DS, шаблоны, observability), затем первый некритичный домен, перенос вертикально по страницам, сквозные виджеты — в старые страницы через Web Component-обёртку. Новый код — только в MF, метрика доли трафика, дедлайн выключения монолита.
</details>

## Практика

**Задача 1.** Компания: 6 команд, один React-SPA, релиз раз в 2 недели, каждая команда ждёт «поезд». Домены: каталог, карточка товара, корзина/оформление, ЛК, поддержка. CTO просит «перейти на микрофронтенды». Ваш план.
<details><summary>Решение</summary>

1. Диагноз: что именно блокирует — общий CI (40 мин), ручной регресс, конфликты в общих файлах? Часть лечится без MF: монорепо с affected-пайплайнами, автотесты вместо ручного регресса, trunk-based + фича-флаги.
2. Если нужен независимый деплой — **вертикальная нарезка**: каталог+карточка, корзина/оформление, ЛК — отдельные приложения на своих путях, shell — тонкий (шапка, авторизация, роутинг верхнего уровня). Поддержка (чат) — горизонтальный виджет через MF.
3. Платформа: Module Federation 2.0, реестр remotes, shared-конфиг (React, роутер, DS — singleton), контракт контекста, шаблон remote, бюджеты, error boundaries + тегирование ошибок.
4. Миграция strangler fig: первым — ЛК (наименее критичен), последним — оформление заказа.
5. ADR, метрики успеха: lead time до прода, частота деплоев на команду, число блокирующих инцидентов, Web Vitals не хуже текущих.
</details>

**Задача 2.** Спроектируйте реестр remotes с канарейкой: 5% пользователей получают новую версию `catalog`.
<details><summary>Решение</summary>

```ts
type RemoteRecord = { stable: string; canary?: { url: string; percent: number } };
type Registry = Record<string, RemoteRecord>;

// Детерминированно: один пользователь всегда в одной группе
function bucket(userId: string): number {
  let h = 0;
  for (const ch of userId) h = (h * 31 + ch.charCodeAt(0)) >>> 0;
  return h % 100;
}

export function resolveRemotes(registry: Registry, userId: string) {
  return Object.entries(registry).map(([name, r]) => ({
    name,
    entry: r.canary && bucket(`${name}:${userId}`) < r.canary.percent ? r.canary.url : r.stable,
  }));
}
// shell: createInstance({ name: 'shell', remotes: resolveRemotes(await fetchRegistry(), user.id) })
```
Реестр отдаётся с коротким кэшем; запись меняет CD-пайплайн remote; метрики ошибок/RUM тегируются версией — автоматический откат канарейки при росте ошибок.
</details>

**Задача 3.** Remote «рекомендации» иногда падает с `ChunkLoadError` после деплоя. Почему и что сделать?
<details><summary>Решение</summary>

Version skew: у пользователя закэширован старый манифест/entry, ссылающийся на чанки, удалённые новым деплоем. Решение: не удалять старые хэшированные ассеты сразу (держать N версий), точка входа — `no-cache`, ретрай загрузки с обновлением манифеста (runtime-плагин MF), error boundary с fallback, мониторинг доли `ChunkLoadError` по версии.
</details>

**Задача 4.** Remote каталога рендерит модалку через портал в `document.body`, а стили каталога живут в Shadow DOM. Модалка без стилей. Варианты?
<details><summary>Решение</summary>

(а) Портал в контейнер **внутри** shadow root (`createPortal(node, shadowRoot.getElementById('overlay-root'))`), z-index-слой внутри фрагмента. (б) Модалки — сервис shell: remote вызывает `platform.openModal(Component)`, стили модалки — из DS (глобальные, singleton). (в) Отказаться от Shadow DOM в пользу CSS Modules + префиксов. Выбор зависит от того, нужна ли модалке перекрывать весь экран: обычно (б).
</details>
