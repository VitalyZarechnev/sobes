## Теория

### Начинать с проблемы, а не с технологии

«Давайте возьмём X» — плохое начало. Хорошее: «у нас проблема Y, вот как её измерить, вот варианты». Технология — средство: перед выбором сформулируйте, какие свойства системы нужны и какую боль снимаем.

### Вопросы до выбора стека

**Продукт:**
- Тип: контентный сайт/маркетинг (SEO, скорость первой загрузки → SSR/SSG, мало JS), продуктовое SPA/дашборд (богатый интерактив), e-commerce (SEO + интерактив + производительность), внутренняя админка (скорость разработки).
- Аудитория: устройства и сети, регионы, доступность, языки, офлайн.
- Срок жизни: прототип на 3 месяца или продукт на 5 лет.
- Нефункциональные требования: безопасность, compliance, SLA, нагрузка.

**Команда и организация:**
- Что команда знает сейчас, кого можно нанять на рынке (и сколько это стоит).
- Сколько команд будет работать с кодом, нужна ли независимость релизов.
- Стандарты компании: дизайн-система, инфраструктура, CI/CD, мониторинг, принятые библиотеки.

**Ограничения:** сроки, бюджет, существующая кодовая база и интеграции, требования заказчика.

### Критерии оценки библиотеки или фреймворка

| Критерий | Что проверить |
|---|---|
| Решает ли проблему | PoC на реальном сценарии, а не hello world |
| Зрелость и поддержка | частота релизов, ответ на issues, roadmap, кто поддерживает (компания, сообщество, один человек) |
| Bus factor | сколько активных мейнтейнеров, есть ли финансирование |
| Экосистема | интеграции, документация, примеры, Stack Overflow, AI-ассистенты хорошо знают API |
| Производительность | размер бандла, runtime-стоимость, SSR |
| DX | типы, ошибки, инструменты, скорость обратной связи |
| Безопасность | история уязвимостей, транзитивные зависимости, supply chain |
| Лицензия | MIT/Apache vs копилефт; смена лицензии в прошлом |
| Стоимость ухода | насколько глубоко проникает в код (фреймворк vs утилита), есть ли альтернативы и путь миграции |
| Совместимость | SSR, RSC, сборка, браузеры, текущий стек |

### Взвешенная матрица

```text
Критерий (вес)          | Вариант A | Вариант B | Вариант C
Решает задачу (5)       |    5      |    4      |    4
Знание командой (4)     |    2      |    5      |    3
Экосистема (3)          |    4      |    5      |    3
Производительность (3)  |    5      |    3      |    4
Стоимость ухода (2)     |    3      |    3      |    5
Итого (Σ вес × оценка)  |   66      |   72      |   63
```

Матрица не принимает решение за вас, но делает критерии и компромиссы явными и обсуждаемыми. Веса согласуйте **до** оценки, чтобы не подгонять результат.

### Процесс

1. **Проблема и критерии** — документ/RFC, обсуждение с командой и стейкхолдерами.
2. **Альтернативы** — минимум 2–3, включая «ничего не менять» и «улучшить текущее».
3. **PoC / спайк** с таймбоксом на реальном куске продукта, с метриками.
4. **Решение в ADR**: контекст, варианты, критерии, решение, последствия, **условия пересмотра**.
5. **Пилот** в одной команде или фиче, сбор обратной связи.
6. **Внедрение**: гайдлайны, шаблоны, линтеры, обучение, codemods для миграции, владелец.
7. **Ретроспектива** через 3–6 месяцев: подтвердились ли ожидания.

### Технологический радар

Классификация технологий компании: **Adopt** (используем по умолчанию), **Trial** (пробуем в ограниченных проектах), **Assess** (изучаем), **Hold** (не начинать новое). Ограничивает зоопарк, делает выбор прозрачным, упрощает найм и перемещение людей между командами. Пример публичного — Thoughtworks Technology Radar.

### Принципы

- **Скучные технологии для ядра** («Choose Boring Technology»): у команды ограниченный бюджет «инноваций» — тратьте его там, где это даёт конкурентное преимущество.
- **Обратимость**: предпочитать решения, которые легко поменять; для необратимых (фреймворк, база данных) — больше анализа.
- **Изолировать зависимость**: обёртки/адаптеры над внешними API и библиотеками (дата-библиотека, HTTP-клиент, аналитика) — заменить их потом дешевле.
- **Стандарт платформы > библиотека**: `Intl`, `fetch`, `structuredClone`, Popover API, CSS-возможности вместо пакетов, если поддержка достаточна.
- **Учитывать AI-эпоху**: популярные стабильные API AI-инструменты знают лучше — продуктивность команды выше.

### Типичные решения во фронтенде (2026)

| Задача | Частый выбор | Комментарий |
|---|---|---|
| SPA/дашборд | React + Vite или Vue + Vite | + React Router / TanStack Router, Vue Router |
| SSR/контент + интерактив | Next.js, Nuxt, React Router (framework mode), Astro для контентных | учитывать хостинг и команду |
| Серверное состояние | TanStack Query, Pinia Colada | см. [React](../03-react/10-state-managers-compared.md), [Vue](../04-vue/08-state-managers.md) |
| Формы | React Hook Form / TanStack Form + zod, VeeValidate | |
| Стили | CSS Modules, Tailwind, zero-runtime CSS-in-JS | см. [CSS-архитектура](../14-design-systems/05-css-architecture.md) |
| Тесты | Vitest + Testing Library + Playwright + MSW | |
| Монорепо | pnpm + Turborepo/Nx | |

## Вопросы с собеседований

<details><summary>Какие вопросы вы задаёте, чтобы подобрать стек?</summary>

Тип продукта и требования (SEO, интерактив, офлайн, доступность, локализация), аудитория и устройства, срок жизни, размер и опыт команды, найм, стандарты и инфраструктура компании, сроки и бюджет, интеграции и ограничения. Затем — критерии, альтернативы, PoC и ADR.
</details>

<details><summary>Как вы оцениваете новую библиотеку перед внедрением?</summary>

Решает ли реальную проблему (PoC), зрелость и bus factor, экосистема и документация, производительность и размер, типы, безопасность и лицензия, совместимость со стеком, стоимость ухода. Затем пилот, гайдлайны и решение в ADR.
</details>

<details><summary>Как убедить команду и бизнес перейти на новую технологию?</summary>

Говорить о проблеме и её цене (время разработки, баги, производительность, найм), показать альтернативы и PoC с метриками, предложить инкрементальный план с вехами и критериями остановки, назвать риски и стоимость. Собрать обратную связь через RFC и найти союзников.
</details>

<details><summary>Что такое ADR и что в нём обязательно?</summary>

Architecture Decision Record — короткий документ о решении: контекст, рассмотренные варианты, решение, последствия (что получаем и чем платим), статус и условия пересмотра. Хранится рядом с кодом, не переписывается — новое решение ссылается на старое.
</details>

<details><summary>Как избежать зоопарка технологий в компании?</summary>

Технологический радар со статусами, общие шаблоны и пресеты, архитектурный комитет или гильдия для решений уровня компании, ADR, правило «новая технология — только через trial в одной команде», регулярная ревизия и вывод устаревшего (hold).
</details>

## Практика

1. Напишите ADR для выбора библиотеки серверного состояния в своём проекте с тремя альтернативами.

3. Нарисуйте технологический радар своей команды (adopt/trial/assess/hold).
