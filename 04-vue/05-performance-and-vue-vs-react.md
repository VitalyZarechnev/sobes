## Теория

### Где Vue тратит время

Vue из коробки избегает многих проблем React (точечные ререндеры, кэш обработчиков), поэтому типичные узкие места другие:
1. **Слишком много реактивности**: глубокие прокси на огромных структурах (10⁵ объектов из API) — память и время на создание прокси/трекинг.
2. **Нестабильные пропсы**: дочерний компонент обновляется из-за пропса, который «меняется» без нужды.
3. **Большие списки** — тысячи компонентов-инстансов (каждый — эффект, прокси, VNode).
4. **Тяжёлые вычисления в шаблоне** — методы вместо `computed`.
5. **Вотчеры `deep`** на больших объектах — полный обход на каждое изменение.
6. Загрузка: бандл, гидратация (SSR).

Инструменты: Vue DevTools (Performance/Timeline — время рендера компонентов), Chrome Performance, `app.config.performance = true` (метки `performance.mark` в dev), `rollup-plugin-visualizer`.

### Стабильность пропсов

Дочерний компонент обновляется, только если изменились его пропсы. Значит, передавать нужно **минимум, который реально влияет** на ребёнка.

```vue
<!-- Плохо: activeId меняется → обновляются ВСЕ строки -->
<ListItem v-for="item in list" :key="item.id" :id="item.id" :active-id="activeId" />

<!-- Хорошо: меняется проп только у двух строк (старая и новая активная) -->
<ListItem v-for="item in list" :key="item.id" :id="item.id" :active="item.id === activeId" />
```

То же с computed: возвращать примитив, если потребителю нужно только булево (с 3.4 computed не триггерит подписчиков, если значение не изменилось).

### v-once и v-memo

```vue
<!-- v-once: отрендерить один раз, дальше — статический контент -->
<footer v-once>{{ legalText }}</footer>

<!-- v-memo: пропустить обновление поддерева, если значения в массиве не изменились -->
<div v-for="item in list" :key="item.id" v-memo="[item.id === selectedId, item.updatedAt]">
  <p>ID: {{ item.id }} — selected: {{ item.id === selectedId }}</p>
  <HeavyCard :item="item" />
</div>
```

- `v-memo` — аналог `React.memo`/`useMemo` для фрагмента шаблона. Полезен для больших `v-for` (тысячи строк), где обновление затрагивает лишь несколько. При совпадении массива даже VNode не создаются.
- 🪤 Ловушка: забыть зависимость в массиве `v-memo` → устаревший UI. Использовать точечно, по результатам профилирования. `v-memo="[]"` эквивалентен `v-once`.
- Внутри `v-for` `v-memo` должен стоять на том же элементе, что и `v-for`.

### Shallow-реактивность

```ts
// 10 000 строк из API, которые заменяются целиком
const rows = shallowRef<Row[]>([]);
rows.value = await api.getRows();                     // ✓ триггерит
rows.value = rows.value.map(r => r.id === id ? { ...r, done: true } : r); // иммутабельное обновление
// rows.value[0].done = true — не отследится (только с triggerRef)

// Внешние инстансы — никогда не проксировать
const map = shallowRef<maplibregl.Map>();
const editor = markRaw(new Editor());
```

Это сближает Vue с иммутабельной моделью React для больших данных: дешёвое создание, точный контроль обновлений. `shallowReactive` — только верхний уровень. Vue 3.5 существенно снизил стоимость глубокой реактивности, но для огромных структур shallow по-прежнему выигрывает.

### Большие списки и виртуализация

- Виртуализация: `useVirtualList` (VueUse), `vue-virtual-scroller` (`RecycleScroller`, `DynamicScroller`), `@tanstack/vue-virtual`.
- Уменьшение числа компонентов: в строках списка — разметка, а не 10 вложенных компонентов (каждый инстанс стоит памяти).
- `content-visibility: auto` для умеренных списков.
- Пагинация / бесконечная прокрутка.

### Прочие техники

- `v-show` vs `v-if`: `v-show` дешевле для частых переключений (только CSS), `v-if` — для редко показываемого (не создаёт инстансы вообще).
- `computed` вместо методов в шаблоне.
- `KeepAlive` с `max` для дорогих экранов.
- Lazy-маршруты и `defineAsyncComponent`; ленивая гидратация (3.5) и Nuxt Islands для SSR.
- Избегать `deep: true` на больших объектах — наблюдать конкретные геттеры.
- Не создавать реактивность для статических данных (константы — обычные объекты или `markRaw`/`Object.freeze`).
- Production build: флаги `__VUE_OPTIONS_API__: false`, `__VUE_PROD_DEVTOOLS__: false` для tree-shaking.

### Vapor Mode

**Vapor Mode** — альтернативная стратегия компиляции SFC без Virtual DOM (вдохновлена Solid.js): шаблон компилируется в код, создающий DOM напрямую и привязывающий **каждое динамическое место** к отдельному реактивному эффекту. Изменение `count` обновляет конкретный текстовый узел — без вызова render-функции компонента и без diff.

```vue
<script setup vapor>
const count = ref(0);
</script>
<template><button @click="count++">{{ count }}</button></template>
```

Упрощённо результат компиляции:

```js
const t0 = template('<button> </button>');      // клонирование готового DOM-фрагмента
function setup() {
  const count = ref(0);
  const n0 = t0();
  const x0 = child(n0);
  delegate(n0, 'click', () => count.value++);
  renderEffect(() => setText(x0, count.value)); // точечный эффект на текстовый узел
  return n0;
}
```

Ключевые моменты:
- Появился в ветке **Vue 3.6** как opt-in на уровне компонента (`<script setup vapor>`) или всего приложения (`createVaporApp`); на момент подготовки — экспериментальный статус, проверяйте актуальность в блоге Vue.
- Цель — производительность и память на уровне Solid/Svelte 5 и меньший рантайм (для чисто Vapor-приложений).
- Ограничения: только Composition API + `<script setup>`; Vapor- и VDOM-компоненты могут смешиваться (interop), но часть функций/библиотек может не поддерживаться.
- Параллельно в 3.6 реактивность переведена на **alien-signals** — ещё быстрее и экономнее.
- Код приложения (шаблоны, composables) не меняется — меняется стратегия компиляции. Это преимущество подхода «шаблоны + компилятор»: оптимизации приходят без переписывания.

### Vue vs React: честное сравнение

| Аспект | Vue 3 | React 19 |
|---|---|---|
| Модель обновлений | Мутабельная реактивность (Proxy), автоматический трекинг зависимостей | Иммутабельный state, явный `setState`, рендер — функция от state |
| Гранулярность ререндера | Компонент, чьи зависимости изменились (Vapor — отдельный узел) | Компонент со state **и всё поддерево** (если не memo / Compiler) |
| Выполнение логики компонента | `setup` один раз | Тело компонента на каждый рендер |
| Мемоизация | Почти не нужна (computed, кэш обработчиков) | Ручная или React Compiler |
| Зависимости эффектов | Автоматически | Массив deps (ошибки — stale closures) |
| Шаблоны | HTML-шаблоны + директивы (JSX опционально), компилятор оптимизирует | JSX = JavaScript, полная выразительность языка |
| Компиляторные оптимизации | patch flags, hoisting, block tree, Vapor | React Compiler (мемоизация) |
| Concurrent rendering | Нет (нет прерываемого рендера; потребность меньше из-за точечных обновлений) | Да: transitions, Suspense, selective hydration |
| Серверные компоненты | Nuxt Islands / server components (менее развиты) | RSC — стандарт в Next.js |
| Мета-фреймворк | Nuxt | Next.js, React Router v7, TanStack Start |
| State | Pinia (официальный) | Множество вариантов (Zustand, RTK, Jotai...) |
| Официальные решения | Router, Pinia, DevTools, Vite — от core-команды | Ядро минимально, остальное — сообщество/вендоры |
| Mobile | NativeScript-Vue, Capacitor/Ionic | React Native — зрелый стандарт |
| Рынок/найм | Сильная позиция в Азии и Европе, меньше вакансий глобально | Крупнейшая экосистема и рынок найма |
| Кривая входа | Ниже (шаблоны, понятная реактивность) | Выше на уровне нюансов (эффекты, мемоизация, RSC) |
| Риски | Ловушки реактивности (деструктуризация, `.value`), мутабельность | Лишние ререндеры, сложность эффектов и RSC/кэширования |

Ключевая разница **в модели**: Vue — «push»: система знает, что изменилось, и обновляет потребителей. React — «pull от корня изменения»: перезапускает функции компонентов и сравнивает результат. Отсюда разные болевые точки: в React — лишние рендеры и массивы зависимостей; во Vue — потеря реактивности и неявность мутаций.

Конвергенция: React добавил компилятор для автоматической мемоизации; Vue добавил Vapor и сигналы. Сигналы (Solid, Preact, Angular, Svelte 5 runes, предложение TC39 Signals) — индустрия движется к fine-grained реактивности, React — заметное исключение со своей моделью.

### Когда что выбрать (позиция lead)

Решают **не бенчмарки**, а контекст:
- **Команда и найм**: существующая экспертиза важнее технических различий. Переписывать ради фреймворка почти никогда не окупается.
- **React**, если: нужен React Native/общий код с мобильным приложением; RSC/Next.js-архитектура с серверным рендерингом как ключевое требование; большой рынок найма и библиотек (дизайн-системы, headless, enterprise-компоненты); интеграция с продуктами, где React — стандарт.
- **Vue**, если: важна скорость старта и низкий порог входа (в т.ч. для full-stack/бэкенд-разработчиков); нужна «батарейная» официальная экосистема без выбора из десятка библиотек; постепенное внедрение в серверно-рендеренные приложения (Laravel и т.п.); формы и дашборды с большим количеством реактивного состояния.
- Оба подходят для 95% задач. Для lead важно назвать критерии, риски и стоимость владения: обучение, найм, долгосрочная поддержка, миграции (Vue 2 → 3 была болезненной; React исторически мягче с миграциями, но переход на RSC — архитектурный сдвиг).

💡 На собеседовании: «Оба фреймворка зрелые; разница в модели реактивности даёт разные классы проблем. Я выбираю по команде, требованиям платформ (мобильные, SSR/RSC), экосистеме и найму, а не по бенчмаркам. Если меня спросят про производительность — у Vue точечные обновления из коробки, у React — concurrent rendering и компилятор; на практике узкое место обычно в данных, списках и бандле».

## Вопросы с собеседований

<details><summary>Как в Vue избежать лишних обновлений дочерних компонентов?</summary>

Передавать стабильные и минимальные пропсы (`:active="id === activeId"` вместо `:active-id`), computed с примитивным результатом, не создавать новые объекты/массивы в шаблоне для пропсов, `v-memo` для больших списков, shallow-реактивность для больших данных.
</details>

<details><summary>Что делают v-once и v-memo?</summary>

`v-once` — рендер один раз, дальше узел статичен. `v-memo="[deps]"` — пропустить обновление поддерева (даже не создавать VNode), если зависимости не изменились. Использовать точечно, в основном для больших `v-for`.
</details>

<details><summary>Когда использовать shallowRef вместо ref?</summary>

Большие структуры, заменяемые целиком или обновляемые иммутабельно; внешние инстансы (карты, редакторы, классы SDK), которые не должны проксироваться. Экономит память и время на создание прокси и трекинг.
</details>

<details><summary>Что такое Vapor Mode?</summary>

Режим компиляции без VDOM: шаблон превращается в прямые DOM-операции и точечные реактивные эффекты на каждую динамическую привязку. Opt-in на уровне компонента или приложения, только `<script setup>`, совместим с VDOM-компонентами. Цель — производительность уровня Solid и меньший рантайм.
</details>

<details><summary>В чём фундаментальная разница реактивности Vue и React?</summary>

Vue отслеживает зависимости автоматически при чтении (Proxy) и уведомляет конкретные эффекты при записи — точечные обновления без повторного выполнения логики компонента. React не знает, что именно изменилось: при `setState` перезапускает функцию компонента и его поддерево и сравнивает результат; оптимизация — мемоизация (ручная или компилятором).
</details>

<details><summary>Почему во Vue нет concurrent rendering и нужен ли он?</summary>

Рендер Vue синхронный и не прерывается. Благодаря точечным обновлениям объём работы на одно изменение обычно меньше, поэтому потребность ниже. Для тяжёлых сценариев — виртуализация, дробление работы, Web Workers. В React concurrent нужен в том числе потому, что ререндер поддерева может быть дорогим.
</details>

<details><summary>Какие проблемы есть у Vue, которых нет у React, и наоборот?</summary>

Vue: потеря реактивности (деструктуризация, передача примитивов), `.value`, неявность мутаций, Proxy ≠ оригинал, меньший рынок библиотек/найма. React: лишние ререндеры и мемоизация, массивы зависимостей и stale closures, сложность эффектов, сложность модели RSC и кэширования в Next.js.
</details>

<details><summary>Как бы вы принимали решение о выборе фреймворка для нового продукта?</summary>

Критерии: экспертиза команды и рынок найма, требования к платформам (мобильные — React Native), SSR/SEO и выбранный мета-фреймворк, экосистема нужных библиотек (дизайн-система, графики, таблицы), долгосрочная поддержка и миграции, интеграция с существующими системами. Оформить ADR с альтернативами и рисками, при сомнениях — прототип на критичном сценарии.
</details>

## Практика

**1. Оптимизируй.** Таблица 5 000 строк, у каждой — `<Row :row="row" :selected-id="selectedId" :columns="columns.filter(c => c.visible)" />`. Клик по строке тормозит.

<details><summary>Решение</summary>

`:selected="row.id === selectedId"` вместо `selected-id` (обновятся 2 строки, а не 5000); `visibleColumns` вынести в `computed` (сейчас каждый рендер создаёт новый массив → обновляются все строки); `rows` — `shallowRef` с иммутабельными обновлениями; виртуализация; при необходимости `v-memo="[row.id === selectedId, row.version]"`.
</details>

**2. Сравни** реализацию счётчика с производным значением в React и Vue и объясни, сколько раз и что выполняется при клике.

<details><summary>Решение</summary>

React: `setCount` → функция компонента выполняется заново целиком, производное значение пересчитывается (если не `useMemo`), JSX дочерних компонентов пересоздаётся, дети рендерятся (если не memo/Compiler), diff, commit. Vue: запись `count.value` → `trigger` → computed помечается dirty → эффект рендера компонента в очередь → в микрозадаче render-функция компонента (только его), computed пересчитывается при чтении, патч по patch flags; дочерние компоненты без изменённых пропсов не трогаются. Vapor: обновится только текстовый узел.
</details>

**3. Напиши ADR-тезисы** «Vue или React» для B2B-платформы с мобильным приложением и командой из 6 фронтендеров, знающих Vue.

<details><summary>Решение (тезисы)</summary>

Контекст: команда на Vue, нужен мобильный клиент. Варианты: (1) Vue + Capacitor/Ionic — переиспользование навыков и кода, достаточно для B2B-форм; (2) React + React Native — лучший нативный UX, но переобучение и найм; (3) Vue для веба + нативные приложения отдельной командой. Решение зависит от требований мобильного UX и бюджета; для типичного B2B — вариант 1 с проверкой критичных сценариев прототипом. Риски и критерии пересмотра указать явно.
</details>
