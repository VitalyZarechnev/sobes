## Теория

### Почему найм — главная работа лида

Ошибка найма стоит дорого: по разным оценкам, от 3–6 месячных зарплат (поиск, онбординг, время команды, расставание) до гораздо больше, если человек токсичен и уводит за собой сильных. Найм — одно из немногих решений лида, которое **плохо обратимо**. Отсюда принцип: «лучше пропустить хорошего, чем нанять плохого» (false negative дешевле false positive), но без перегиба — бесконечный поиск идеала тоже стоит денег.

### Профиль вакансии (до публикации)

Перед вакансией лид отвечает себе на вопросы:
- **Зачем** нужен человек: какую проблему команды он решит через 6 месяцев? (Не «нужен ещё один сеньор», а «нужен человек, который возьмёт на себя перф и SSR, потому что сейчас это делаю я».)
- **Грейд и бюджет**: согласованы с HR и руководителем, вилка понятна.
- **Must have / nice to have**: не больше 4–5 обязательных пунктов. Каждый must have должен **проверяться** на интервью.
- **Какой человек дополнит команду**: если в команде 5 «архитекторов», нужен человек, который любит доводить фичи до конца.

Пример компактного профиля:

| Поле | Значение |
|---|---|
| Роль | Senior Frontend Developer, команда «Каталог» |
| Задача на 6 мес. | Ownership производительности витрины: Core Web Vitals в зелёной зоне, SSR-стабильность |
| Must have | TypeScript, React (глубоко), опыт перф-оптимизации с измеримым результатом, SSR/Next.js, самостоятельность в декомпозиции |
| Nice to have | Опыт с RUM, менторинг мидлов, e-commerce |
| Не нужно | Знание конкретного стейт-менеджера, CSS-in-JS библиотеки |
| Как проверяем | Тех. интервью (перф-кейс), system design (витрина), поведенческое (ownership, менторинг) |

### Воронка найма и её метрики

```
Источник → Скрининг резюме → HR-скрининг → Тех. интервью → System design / финал → Оффер → Принятие → Испытательный срок
```

| Метрика | Что показывает | Ориентир (очень грубо, сильно зависит от рынка) |
|---|---|---|
| Конверсия по этапам | Где теряем кандидатов | Тех. интервью → оффер: 20–40% |
| Time to hire | Скорость процесса | 3–6 недель от отклика до оффера |
| Offer acceptance rate | Конкурентность оффера и впечатление от процесса | > 70% |
| Доля прошедших испыт. срок | Качество найма | > 90% |
| Отзывы кандидатов | Бренд работодателя | Собирать после каждого финала |

Если конверсия на тех. интервью очень низкая — проблема в скрининге (не тех кандидатов зовём) или в интервью (планка выше заявленного грейда). Если низкий offer acceptance — проблема в деньгах, скорости или в том, как команда себя показала.

💡 На собеседовании: лиду важно сказать, что **процесс найма — продукт**, у которого есть метрики и итерации. И что скорость — конкурентное преимущество: сильный кандидат параллельно в 3–5 процессах.

### Структура технического интервью

Принцип — **структурированное интервью**: одинаковые вопросы и критерии для всех кандидатов на позицию, оценка по scorecard, а не «понравился/не понравился». Исследования стабильно показывают, что структурированные интервью предсказывают успех лучше неструктурированных.

Пример интервью на Senior Frontend (90 минут):

| Время | Блок | Что проверяем |
|---|---|---|
| 0–5 | Знакомство, план встречи | Снять стресс, объяснить формат |
| 5–20 | Разбор опыта: самый сложный технический проект | Глубина, ownership, умение объяснить trade-offs |
| 20–50 | Практика: код-ревью готового PR или небольшая задача | Качество мышления, знание платформы, коммуникация |
| 50–75 | Мини system design: «спроектируй фронтенд ленты/формы/виджета» | Декомпозиция, архитектура, перф, a11y, тесты |
| 75–85 | Вопросы на знания по стеку (точечно, под пробелы) | Глубина в must have |
| 85–90 | Вопросы кандидата | Мотивация, что ему важно |

**Scorecard** (оценка 1–4 по каждой компетенции, с обязательным письменным обоснованием):

| Компетенция | 1 — нет | 2 — слабо | 3 — уверенно | 4 — сильно | Доказательства |
|---|---|---|---|---|---|
| JS/TS и платформа | | | | | |
| React / фреймворк | | | | | |
| Архитектура и декомпозиция | | | | | |
| Качество кода и тестирование | | | | | |
| Коммуникация и объяснение решений | | | | | |
| Ownership / самостоятельность | | | | | |

Итог — одна из позиций: **Strong hire / Hire / No hire / Strong no hire** (без «нейтрально»: это вынуждает принять решение).

🪤 Ловушка: заполнять scorecard после обсуждения с другими интервьюерами. Сначала каждый пишет свой независимый фидбек, потом калибровка — иначе первый высказавшийся задаёт тон (anchoring).

### Live-coding vs take-home vs код-ревью

| Формат | Плюсы | Минусы | Когда уместен |
|---|---|---|---|
| Live-coding (алгоритмы) | Быстро, стандартизировано | Слабо связано с работой фронтендера, высокий стресс, отсекает хороших людей | Почти никогда для продуктового фронтенда |
| Live-coding (практическая задача: компонент, хук, debounce, fetch с отменой) | Видно мышление и коммуникацию, близко к работе | Стресс, ограничение по времени | Мидлы и сеньоры, 30–40 мин |
| Take-home | Реалистично, без стресса, видно качество кода | Дорого для кандидата (сильные часто отказываются), нельзя проверить авторство, долго | Джуны/мидлы, кандидаты без публичного кода; ограничить 3–4 часами и **обязательно** обсуждение после |
| Код-ревью готового PR | Близко к реальной работе сеньора, мало стресса, видно глубину и приоритеты | Нужна хорошая подготовка PR с разными уровнями проблем | Сеньоры и лиды — один из лучших форматов |
| Pair programming на реальной кодовой базе | Максимально реалистично | Сложно стандартизировать, NDA | Финальный этап в некоторых компаниях |

💡 На собеседовании: «Для сеньоров я предпочитаю код-ревью заранее подготовленного PR с багами разного уровня — от race condition в useEffect до проблем с a11y — и небольшую практическую задачу. Take-home использую только с ограничением по времени и обязательным разбором, потому что иначе отсекаем сильных кандидатов, у которых нет вечера на тестовое».

### Оценка soft skills

Поведенческие вопросы по **STAR** ([09](09-behavioral-interview.md)): «расскажите о случае, когда…» вместо гипотетических «что бы вы сделали». Прошлое поведение — лучший предиктор будущего.

| Компетенция | Вопрос | Красный флаг |
|---|---|---|
| Ownership | Расскажите про баг на проде, который вы допустили. Что сделали? | Виноваты другие; не было действий после |
| Конфликты | Был ли случай, когда вы не согласились с техническим решением коллеги? | «Я всегда прав» или «я всегда соглашаюсь» |
| Обучаемость | Чему вы научились за последний год и как? | Ничему, «всё знаю» |
| Обратная связь | Какой самый полезный фидбек вам давали? Что изменили? | Не может вспомнить или обесценивает |
| Командность | Как вы помогали коллеге, у которого не получалось? | Только про себя |

Отдельно наблюдайте **по ходу технической части**: как реагирует на подсказку, признаёт ли «не знаю», задаёт ли уточняющие вопросы, как объясняет.

### Калибровка и bar raiser

**Калибровка интервьюеров** — регулярная практика, чтобы оценки разных людей были сопоставимы:
- Новые интервьюеры проходят shadow (наблюдают) → reverse shadow (ведут под наблюдением) → самостоятельно.
- Раз в месяц–квартал: разбор нескольких scorecard'ов, сравнение «кого бы наняли», выравнивание планки.
- Банк вопросов с ожидаемыми ответами по уровням («что скажет мидл, что скажет сеньор»).

**Bar raiser** (практика Amazon) — независимый опытный интервьюер не из нанимающей команды, у которого есть право вето. Его задача — чтобы каждый новый сотрудник был **лучше медианы** текущих на этом уровне, и защищать от «нанимаем, потому что горит». Аналог для небольших компаний — обязательный интервьюер из соседней команды.

**Debrief (обсуждение после финала):**
1. Все пишут фидбек независимо до встречи.
2. На встрече каждый зачитывает решение и обоснование, начиная с наиболее младшего (чтобы не давил авторитет).
3. Обсуждаем расхождения по доказательствам, а не по ощущениям.
4. Решение принимает нанимающий менеджер (лид), bar raiser может наложить вето.

### Онбординг

Цель онбординга — **сократить время до продуктивности** и **удержать** человека (значимая доля ранней текучести связана с плохим опытом первых месяцев).

**Роли:**
- **Лид** — ожидания, цели испытательного срока, 1:1 раз в неделю первый месяц.
- **Бадди (buddy)** — опытный коллега (не лид), отвечает на «глупые» вопросы, парное программирование, знакомит с людьми. На бадди закладывается 10–20% времени в первые 2 недели.
- **Новичок** — улучшает онбординг-документацию: всё, что было непонятно, сразу правит. Новичок — единственный, кто видит пробелы свежим взглядом.

**План онбординга (пример для сеньора):**

| Период | Цели | Артефакт / критерий |
|---|---|---|
| День 1 | Доступы, рабочее окружение, знакомство с командой | Локально запущен проект; доступы во все системы |
| Неделя 1 | Первый PR в прод (маленький: баг, текст, тест) | Пройден весь путь: ветка → ревью → CI → релиз |
| Неделя 2 | Понимание архитектуры и продукта | Новичок рассказывает бадди архитектуру своими словами; встречи с продактом и дизайнером |
| Недели 3–4 | Самостоятельная задача среднего размера | Фича доведена до прода с минимальной помощью |
| Месяц 2 | Полноценный участник: ревьюит, участвует в оценке | Делает ревью, участвует в планировании |
| Месяц 3 | Ownership области | Отвечает за модуль/направление; итог испыт. срока |

**Онбординг-чеклист (пункты для документа в Confluence/Notion):**
- Доступы: репозитории, CI, трекер, Figma, Sentry, аналитика, VPN, стенды
- Окружение: README с запуском за 15 минут, переменные окружения, тестовые аккаунты
- Документы: архитектурный обзор, ADR, гайд по код-ревью, DoD, процесс релиза, on-call
- Люди: список ключевых людей и зачем к ним идти (продакт, дизайн, бэкенд, QA, DevOps)
- Процессы: календарь встреч команды, как берём задачи, как оцениваем
- Продукт: демо продукта, ключевые метрики, пользователи
- Цели на испытательный срок — письменно, согласованы в первую неделю

**Метрики онбординга:**

| Метрика | Как считать |
|---|---|
| Time to first PR | Дни от выхода до первого смёрженного PR (цель: ≤ 3–5 дней) |
| Time to first meaningful feature | Дни до первой самостоятельной фичи в проде |
| Time to productivity | Субъективно (лид + новичок) или по сравнению с медианой команды по throughput |
| Onboarding survey | Опрос через 30 и 90 дней: что помогло, что мешало, оценка 1–5 |
| Ранняя текучесть | Доля ушедших в первые 6 месяцев |

🪤 Ловушка: «вот репозиторий, разбирайся». Даже сильный сеньор без контекста потеряет 2–3 недели и сформирует впечатление «тут всем на меня плевать».

## Вопросы с собеседований

<details><summary>Как вы строите процесс найма в команду?</summary>

Начинаю с профиля: какую проблему решит человек через полгода, must have не больше 4–5, каждый проверяется на конкретном этапе. Дальше структурированные этапы: HR-скрининг → тех. интервью (опыт, практика или код-ревью, мини system design) → поведенческое / финал. Scorecard с независимым фидбеком, debrief, решение принимает нанимающий менеджер. Слежу за метриками воронки и time to hire, собираю отзывы кандидатов. Для lead-уровня — калибровка интервьюеров и обучение новых через shadow.
</details>

<details><summary>Live-coding или тестовое задание? Почему?</summary>

Зависит от уровня и рынка. Для сеньоров — код-ревью подготовленного PR плюс небольшая практическая задача: близко к работе, мало стресса, видно приоритеты. Алгоритмические задачи для продуктового фронтенда почти не предсказывают успех. Take-home — только с ограничением по времени и обязательным разбором, иначе теряем сильных кандидатов. Главное — чтобы формат проверял то, что реально нужно в работе.
</details>

<details><summary>Как оценить soft skills на интервью?</summary>

Поведенческие вопросы про прошлый опыт по STAR, с уточнениями «а что сделали именно вы», «что бы сделали иначе». Плюс наблюдение во время технической части: реакция на подсказки, умение сказать «не знаю», вопросы. Оцениваю по scorecard с конкретными доказательствами, а не «приятный человек». Красные флаги: виноваты все вокруг, нет примеров ошибок, неуважительно говорит о бывших коллегах.
</details>

<details><summary>Как вы снижаете субъективность в найме?</summary>

Структурированное интервью с одинаковыми вопросами и критериями; scorecard с доказательствами; независимый фидбек до обсуждения; debrief, где первыми говорят младшие; калибровка интервьюеров; bar raiser или интервьюер из другой команды. Отдельно — осознанность про когнитивные искажения: эффект ореола, «похож на меня» (affinity bias), якорение.
</details>

<details><summary>Что такое bar raiser и зачем он нужен?</summary>

Практика Amazon: независимый опытный интервьюер не из нанимающей команды с правом вето. Нанимающая команда всегда под давлением «нужен человек вчера», bar raiser защищает планку: каждый новый сотрудник должен быть лучше медианы текущих на уровне. В небольшой компании аналог — обязательный интервьюер из соседней команды и правило «сомневаешься — нет».
</details>

<details><summary>Вы нанимаете, а кандидат хорош технически, но вас что-то смущает в поведении. Что делаете?</summary>

Формулирую, что именно смущает, на уровне конкретных наблюдений. Если это потенциальный red flag (неуважение, перекладывание ответственности) — уточняю дополнительным поведенческим интервью или референсами. Если сомнения остаются по ключевой ценности — не нанимаю: токсичный сильный разработчик обходится команде дороже, чем вакансия ещё месяц.
</details>

<details><summary>Как вы организуете онбординг?</summary>

Письменный план на 3 месяца с целями испыт. срока, согласованными в первую неделю. Бадди (не лид) с заложенным временем. Первый PR в прод в первую неделю — чтобы новичок прошёл весь путь. Еженедельные 1:1 первый месяц. Онбординг-документация, которую каждый новичок улучшает. Метрики: time to first PR, опрос через 30/90 дней, ранняя текучесть.
</details>

<details><summary>Как понять, что онбординг работает?</summary>

Количественно: time to first PR и time to first feature сокращаются или стабильны, ранняя текучесть низкая. Качественно: опрос новичков через 30 и 90 дней, разбор на ретро. Индикатор проблем — новички задают одни и те же вопросы (значит, этого нет в документации) или бадди не успевает свою работу.
</details>

<details><summary>Как вы проводите испытательный срок и что делаете, если человек не справляется?</summary>

Цели испыт. срока письменно в первую неделю, промежуточная точка на середине срока с честным фидбеком. Если не справляется — сначала понять причину (онбординг, ожидания, навыки, мотивация), дать конкретный план с поддержкой. Если к концу срока прогресса нет — расставание, и оно не должно быть сюрпризом: человек знал о проблемах заранее.
</details>

<details><summary>Как вы продаёте вакансию сильному кандидату?</summary>

Честно рассказываю о задачах, проблемах и возможностях роста: сильные кандидаты ценят прозрачность больше, чем рекламу. Показываю команду (интервьюеры — лицо компании), быстрый процесс и обратную связь в течение 1–2 дней. Узнаю, что для кандидата важно (задачи, рост, стек, баланс), и говорю именно про это.
</details>

## Практика

**Задача 1.** Подготовьте PR для интервью в формате код-ревью на React. Какие проблемы туда заложить?

<details><summary>Решение</summary>

Несколько уровней, чтобы различать мидла и сеньора:
- Очевидные: неиспользуемая переменная, `any`, отсутствие `key` в списке, магические числа.
- Средние: `useEffect` без отмены запроса (race condition при смене id), стейт, дублирующий пропсы, отсутствие обработки ошибки и loading-состояния.
- Глубокие: утечка подписки, ре-рендер всего списка из-за нового объекта в контексте, `onClick` на `div` без роли и клавиатуры (a11y), XSS через `dangerouslySetInnerHTML`, нетестируемая структура (логика в компоненте).
- Архитектурные: фича нарушает границы модулей, напрямую ходит в API в обход слоя данных.
Оценивать не только количество найденного, но и **приоритизацию** и **тон** комментариев.
</details>

**Задача 2.** Debrief: два интервьюера ставят «Hire», один «Strong no hire» с формулировкой «не понравился». Как ведёте обсуждение?

<details><summary>Решение</summary>

Попросить третьего интервьюера перевести «не понравился» в наблюдаемое поведение. Если это конкретный red flag (например, грубость или перекладывание ответственности) — это весомо, обсудить, видели ли другие сигналы. Если это «не похож на нас» без доказательств — это affinity bias, решение не может на нём основываться. При сомнениях — дополнительное короткое интервью на спорную компетенцию. Затем отдельно поговорить с интервьюером о формате фидбека.
</details>

**Задача 3.** Новый мидл через 3 недели ещё не сделал ни одного PR. Что делаете?

<details><summary>Решение</summary>

Это сигнал о проблеме онбординга, а не только человека. 1:1: что мешает? Часто — окружение не запускается, задача слишком большая, человек стесняется спрашивать. Действия: дать маленькую задачу на 1 день, парное программирование с бадди, проверить онбординг-документацию. После — ретро онбординга, чтобы проблема не повторилась.
</details>
