## Теория

### Техническое видение и стратегия

Will Larson разделяет:
- **Стратегия** — как решаем конкретную проблему сейчас: диагноз → руководящие принципы → конкретные действия. Опирается на структуру Ричарда Румельта («Good Strategy / Bad Strategy»).
- **Видение** — как мир выглядит через 2–3 года, если всё получится. Задаёт направление, помогает принимать решения без лида.

Larson предлагает прагматичный путь: напишите **5 конкретных design-документов → обобщите их в стратегию; 5 стратегий → в видение**. То есть стратегия растёт снизу из реальных решений, а не придумывается в вакууме.

**Шаблон технического видения фронтенда (1–2 страницы):**
1. **Контекст**: продукт, команда, бизнес-цели на год (рост, новые рынки, мобильные клиенты).
2. **Диагноз**: что мешает сейчас (с цифрами): сборка 12 мин, 40% инцидентов из-за регрессий UI, 3 разных UI-кита, онбординг 6 недель.
3. **Видение через 2 года**: «любой разработчик выкатывает фичу за день от мёржа до прода; UI строится из design system; деградация перфа ловится до релиза».
4. **Принципы** (руководят решениями): «скучные технологии по умолчанию», «измеряем, прежде чем оптимизировать», «граница модуля = граница команды».
5. **Инициативы** с приоритетами, примерной стоимостью и бизнес-эффектом.
6. **Что не делаем** (non-goals): «не переписываем на другой фреймворк», «не строим микрофронтенды, пока одна команда».
7. **Метрики успеха**.

💡 На собеседовании: стратегия без non-goals — не стратегия, а список желаний. Сказать «мы сознательно не делаем X, потому что…» — сильный сигнал лидерского уровня.

### Технический долг

**Определение**: технический долг — метафора Уорда Каннингема: сознательный компромисс, который ускоряет сейчас, но создаёт «проценты» (замедление) потом. Не любой плохой код — долг; долг — то, что **мешает развивать продукт**. Плохой код в модуле, который никто не трогает, долгом почти не является: проценты не начисляются.

**Классификация по типу (фронтенд):**

| Тип | Пример | Как проявляется |
|---|---|---|
| Архитектурный | Нет границ модулей, глобальный стор на всё | Каждая фича трогает 20 файлов, частые регрессии |
| Код | Дубли, god-компоненты на 1500 строк | Медленные изменения, баги |
| Зависимости | React 16, устаревший webpack, библиотеки без поддержки | Уязвимости, нельзя использовать новые возможности |
| Тесты | Нет тестов на критичные флоу, flaky e2e | Страх изменений, ручной регресс |
| Инфраструктура | CI 30 минут, ручной деплой | Медленная обратная связь, редкие релизы |
| Документация / знания | Модуль понимает один человек | Bus factor, долгий онбординг |
| UX / Design | Несколько UI-китов, несогласованные паттерны | Медленная разработка UI, непоследовательный UX |

**Квадрант техдолга Мартина Фаулера:**

| | Безрассудный (reckless) | Благоразумный (prudent) |
|---|---|---|
| **Намеренный (deliberate)** | «Нет времени на дизайн» | «Надо выпустить сейчас, разберёмся с последствиями» |
| **Ненамеренный (inadvertent)** | «Что такое слоистая архитектура?» | «Теперь мы знаем, как это надо было сделать» |

Выводы: **prudent deliberate** — нормальный бизнес-инструмент (записываем в бэклог с датой возврата); **reckless inadvertent** лечится наймом, обучением и ревью; **prudent inadvertent** неизбежен — команда учится, и это нормально.

**Как приоритизировать:** оценить «проценты» (сколько времени/инцидентов/денег стоит в месяц) × частоту изменений в зоне × стоимость исправления. Удобно: матрица «влияние × стоимость исправления» и фокус на высоком влиянии и низкой стоимости.

### Как продать техдолг бизнесу

Бизнесу не интересен «рефакторинг», ему интересны **деньги, сроки и риски**. Перевод:

| Технический язык | Язык бизнеса |
|---|---|
| «Нужно отрефакторить корзину» | «Каждая фича в корзине занимает в 2 раза дольше, чем в других модулях. Последние 3 фичи — 6 недель вместо 3. Вложив 3 недели, вернём скорость к концу квартала» |
| «Нужно обновить React» | «Текущая версия не получает исправлений безопасности; у нас 4 известные уязвимости в зависимостях. Плюс без обновления мы не сможем сделать X, который в роадмапе на Q3» |
| «Нет тестов» | «За квартал 5 инцидентов на оплате из-за регрессий, каждый — потеря ~N заказов. Автотесты на оплату снизят риск и уберут 2 дня ручного регресса перед каждым релизом» |
| «CI медленный» | «6 разработчиков ждут CI ~1 час в день = ~0.75 человека в месяц простоя» |

**Стратегии выделения времени:**
- **Фиксированный бюджет**: 15–20% capacity каждой итерации на техдолг и платформу. Плюс — предсказуемо, не надо каждый раз продавать; минус — может уходить на мелочи. Важно: бюджет — договорённость с продактом, а не «тайная» работа.
- **Правило бойскаута**: оставляй код чище, чем был, — улучшение в рамках фичи, которая затрагивает модуль.
- **Техдолг как часть фичи**: «эта фича займёт 5 дней, или 3 дня + 2 на подготовку модуля, после чего следующие фичи будут быстрее».
- **Выделенные инициативы**: для крупного долга (миграция) — отдельный проект с бизнес-обоснованием, как фича.
- **Cool-down / hardening**: периоды между циклами (как в Shape Up).

🪤 Ловушка: «нам нужен спринт на техдолг» без измеримого результата. Бизнес однажды согласится, а потом не увидит эффекта — и второго раза не будет. Всегда: метрика «до», ожидаемая «после», и отчёт по факту.

### ADR и RFC

**ADR (Architecture Decision Record)** — короткий документ, фиксирующий **одно** значимое архитектурное решение, его контекст и последствия. Формат предложил Michael Nygard (2011). ADR хранятся в репозитории (`docs/adr/0001-....md`), нумеруются, не редактируются задним числом — при изменении решения пишется новый ADR со статусом «supersedes ADR-0005».

Когда писать ADR: решение дорого откатить, затрагивает несколько модулей/команд, через год кто-то спросит «а почему так?».

**Шаблон ADR:**

```markdown
# ADR-0012: Выбор TanStack Query для серверного состояния

- Статус: Принято (Proposed | Accepted | Deprecated | Superseded by ADR-XXXX)
- Дата: 2026-03-14
- Авторы: @lead, @senior-a
- Участники обсуждения: frontend-команда «Каталог», @backend-lead

## Контекст
Серверные данные хранятся в Redux через самописные thunk'и. 30% кода стора —
загрузка/кеш/инвалидация. Регулярные баги: устаревшие данные после мутаций,
дублирующиеся запросы, race conditions при смене фильтров.

## Решение
Используем TanStack Query для серверного состояния. Redux остаётся только для
клиентского состояния (UI, корзина до оформления). Новые фичи — сразу на Query,
старые мигрируем при изменениях модуля (правило бойскаута).

## Рассмотренные варианты
1. Оставить Redux + thunk — не решает проблем кеша и инвалидации.
2. RTK Query — меньше миграция, но привязка к Redux, команда хуже знает.
3. TanStack Query — зрелая библиотека, решает кеш/дедупликацию/отмену,
   независима от стора. Выбрано.
4. SWR — проще, но слабее мутации и инвалидация для нашего кейса.

## Последствия
+ Удаляем ~2–3 тыс. строк кода стора, меньше багов кеша.
+ Стандартный подход, проще онбординг.
− Два источника состояния на время миграции; нужен гайд «что куда».
− +~13 KB gzip к бандлу.
Риски: неполная миграция → гибрид навсегда. Митигация: дашборд прогресса,
срок — 2 квартала, повторная оценка в ADR-0018.
```

**RFC (Request for Comments)** — документ **до** решения, для обсуждения широкого круга. RFC отличается от ADR: RFC — процесс поиска решения (длиннее, с альтернативами, вопросами, прототипами), ADR — фиксация итога (коротко). Часто RFC после принятия порождает один или несколько ADR.

**Процесс RFC (пример):**
1. Автор пишет RFC по шаблону: проблема, цели и non-goals, предлагаемое решение, альтернативы, риски, план внедрения, открытые вопросы.
2. Период комментариев (1–2 недели), обязательные ревьюеры от затронутых команд.
3. Встреча для обсуждения спорных вопросов (если есть).
4. Решение (принято / отклонено / нужна доработка) — у определённого владельца решения (лид, архитектурный комитет).
5. ADR + план работ.

🪤 Ловушка: RFC-процесс для всего. Если для выбора библиотеки форматирования дат нужен двухнедельный RFC, команда перестанет предлагать улучшения. RFC — для решений, затрагивающих несколько команд или дорогих в откате.

### Tech Radar

**Технологический радар** Thoughtworks — визуализация технологий по квадрантам (Techniques, Tools, Platforms, Languages & Frameworks) и кольцам:
- **Adopt** — рекомендуем по умолчанию.
- **Trial** — пробуем в реальных проектах с ограниченным риском.
- **Assess** — изучаем, стоит понаблюдать.
- **Hold** — не начинать новое использование.

Внутренний радар компании — сильный инструмент лида/head: снижает зоопарк технологий, даёт командам понятные рамки («из Adopt выбирай свободно, для Trial нужен ADR, для Hold — нельзя в новом коде»). Обновлять раз в полгода через гильдию. Thoughtworks публикует инструменты для построения собственного радара (BYOR).

### Выбор технологий

**Критерии оценки (матрица с весами):**

| Критерий | Вопросы |
|---|---|
| Решает ли проблему | Какую конкретную проблему, есть ли она у нас? |
| Зрелость и поддержка | Сколько лет, кто поддерживает, частота релизов, bus factor мейнтейнеров |
| Экосистема | Документация, интеграции, ответы на Stack Overflow |
| Найм и обучение | Сколько людей на рынке знают, сколько учиться команде |
| Производительность / размер | Влияние на бандл и рантайм |
| Совместимость | С текущим стеком, SSR, тестами, TS |
| Стоимость выхода | Насколько тяжело будет заменить (lock-in) |
| Лицензия и безопасность | Лицензия, история уязвимостей |

**Принцип «Choose boring technology»** (Dan McKinley): у компании ограниченное количество «инновационных жетонов». Тратить их стоит на то, что даёт конкурентное преимущество, а для остального брать проверенное.

### Build vs Buy

| Строим сами, если | Покупаем / берём open-source, если |
|---|---|
| Это ядро конкурентного преимущества | Это commodity (авторизация, аналитика, feature flags, мониторинг) |
| Готовые решения не покрывают требований и не расширяемы | Готовое закрывает 80%+ потребностей |
| Есть экспертиза и люди на **поддержку** на годы | Нет людей на поддержку |
| Lock-in или стоимость внешнего решения неприемлемы | Time to market важнее |

Посчитать **TCO** (total cost of ownership): разработка + поддержка + онбординг + инциденты на горизонте 2–3 лет против лицензии + интеграции + рисков вендора. Типичная ошибка — считать только стоимость разработки, забывая, что своё решение нужно поддерживать вечно.

### Миграции: strangler fig

**Strangler Fig Application** (Мартин Фаулер): новая система постепенно «обвивает» старую, забирая функциональность по частям, пока старая не станет ненужной. Альтернатива — «большой взрыв» (переписать с нуля), который почти всегда занимает больше времени, чем планировалось, и останавливает продуктовую разработку.

**Фронтенд-примеры:**
- AngularJS → React: роутинг на уровне приложения отдаёт новые страницы React-приложению, старые — AngularJS; либо React-компоненты встраиваются в AngularJS-страницы через адаптеры.
- Монолит → модули/микрофронтенды: новый функционал в отдельных модулях, старый переносится при изменениях.
- Webpack → Vite, JS → TS (`allowJs`, постепенное ужесточение strict-флагов), Redux → TanStack Query.

**План миграции:**
1. ADR с причиной, целевым состоянием и критериями завершения.
2. Механизм сосуществования (адаптер, роутинг, обёртки, codemods).
3. Правило: **новый код — только на новом**. Без этого миграция никогда не закончится.
4. Порядок: начать с некритичного модуля (обучение), затем — модули с высокой частотой изменений (максимальная выгода).
5. Метрика прогресса на дашборде (доля файлов/страниц на новом стеке).
6. Codemods и автоматизация (jscodeshift, ts-morph) для массовых изменений.
7. Линтер, запрещающий импорт старого в новом коде.
8. Дедлайн на удаление старого и празднование, когда удалили.

🪤 Ловушка: миграция «в фоне без дедлайна». Через два года у вас два фреймворка, оба надо знать, а знающие старый уже уволились. Хуже, чем не начинать.

### Стандарты и линтеры

- **Автоматизировать всё, о чём можно не спорить**: Prettier (форматирование), ESLint/Biome (правила), TypeScript strict, Stylelint, commitlint, проверка размера бандла (size-limit), dependency-cruiser или правила ESLint для границ модулей.
- **Общие конфиги пакетами** (`@company/eslint-config`), версионируемые, с changelog.
- **Новые правила — через RFC/обсуждение**, сначала в режиме warning, затем error с codemod.
- **Pre-commit хуки** (lint-staged) — быстрые проверки; полные — в CI.
- Не превращать линтер в инструмент власти: каждое правило должно ловить реальный класс багов или решать реальный спор.

### Design system governance

Design system — **продукт для внутренних пользователей** (разработчиков и дизайнеров), а не библиотека компонентов.

**Модели владения:**

| Модель | Как устроено | Плюсы | Минусы |
|---|---|---|---|
| Централизованная | Выделенная команда делает всё | Консистентность, качество | Узкое место, оторванность от продуктов |
| Федеративная | Продуктовые команды контрибьютят по правилам, небольшая core-команда ревьюит | Масштабируется, близко к потребностям | Нужна дисциплина и процесс |
| Гибридная | Core-команда для основы, федерация для расширений | Баланс | Сложнее управлять |

**Процессы:**
- Contribution model: как предложить компонент (issue → дизайн-ревью → API-ревью → реализация → документация → релиз).
- Версионирование SemVer, changelog, codemods для breaking changes, политика deprecation (например, 2 минорных релиза).
- Дизайн-токены как единый источник правды между Figma и кодом.
- Метрики adoption: доля UI на компонентах DS, количество «отклонений» (detached components в Figma, локальные переопределения).
- Документация и песочница (Storybook), визуальные регрессионные тесты.
- Регулярный синк дизайн + фронтенд.

## Вопросы с собеседований

<details><summary>Как вы работаете с техническим долгом?</summary>

Классифицирую (архитектура, код, зависимости, тесты, инфраструктура, знания) и оцениваю «проценты»: сколько он стоит в часах, инцидентах, скорости. Приоритизирую по влиянию × частоте изменений в зоне. Выделяю время системно: фиксированный бюджет 15–20% по договорённости с продактом, правило бойскаута, крупное — отдельной инициативой с бизнес-обоснованием. Показываю результат метриками.
</details>

<details><summary>Расскажите о квадранте техдолга Фаулера.</summary>

Две оси: намеренный/ненамеренный и безрассудный/благоразумный. Благоразумный намеренный — осознанный компромисс ради скорости с планом возврата, нормальный бизнес-инструмент. Безрассудный намеренный — «некогда думать». Безрассудный ненамеренный — от незнания, лечится обучением и ревью. Благоразумный ненамеренный — «теперь мы знаем, как надо было» — неизбежен.
</details>

<details><summary>Как убедить бизнес выделить время на техдолг?</summary>

Перевести в деньги, сроки и риски с цифрами: «фичи в модуле стоят в 2 раза дороже», «N инцидентов в квартал стоили M заказов», «команда теряет X часов в неделю на CI». Предложить конкретный план с измеримым результатом и коротким горизонтом, а потом отчитаться фактом. Лучше всего — встроить в регулярный бюджет, чтобы не продавать каждый раз.
</details>

<details><summary>Что такое ADR и чем он отличается от RFC?</summary>

ADR — короткая неизменяемая запись одного архитектурного решения: контекст, решение, рассмотренные варианты, последствия. Хранится в репозитории рядом с кодом. RFC — документ для обсуждения до принятия решения, с альтернативами, вопросами и периодом комментариев. RFC — процесс, ADR — результат.
</details>

<details><summary>Как вы выбираете новую технологию?</summary>

Начинаю с проблемы, а не с технологии. Критерии: решает ли проблему, зрелость, экосистема, найм, производительность, совместимость, стоимость выхода. Прототип / spike на реальном кейсе, сравнение 2–3 вариантов, ADR. По умолчанию — «скучные» технологии, инновации — только там, где дают преимущество. Для компании — через tech radar.
</details>

<details><summary>Build vs buy — как принимаете решение?</summary>

Ядро конкурентного преимущества — строим, commodity — покупаем или берём open-source. Считаю TCO на 2–3 года, включая поддержку, — частая ошибка в недооценке поддержки своего решения. Учитываю lock-in, зрелость вендора, наличие людей на поддержку. Пример: feature flags — купить/взять готовое; кастомный редактор, который и есть продукт, — строить.
</details>

<details><summary>Как провести миграцию большого фронтенда на новый фреймворк?</summary>

Не переписывать с нуля. Strangler fig: механизм сосуществования (роутинг или обёртки), новый код — только на новом стеке, перенос модулей по приоритету (часто изменяемые — первыми), codemods, линтер-правила, дашборд прогресса, дедлайн удаления старого. ADR в начале и регулярный отчёт бизнесу. Подчеркнуть: продуктовая разработка не останавливается.
</details>

<details><summary>Что такое tech radar и зачем он команде?</summary>

Визуализация технологий по кольцам Adopt/Trial/Assess/Hold (формат Thoughtworks). Для компании — способ управлять зоопарком технологий и давать командам рамки: что можно брать свободно, что пробовать с ADR, что не использовать в новом коде. Обновляется через гильдию раз в полгода.
</details>

<details><summary>Как вы управляете design system в компании с несколькими командами?</summary>

Как продуктом: core-команда + федеративный вклад продуктовых команд по contribution model, SemVer, changelog, codemods для breaking changes, политика deprecation, дизайн-токены, Storybook и визуальные тесты. Метрики adoption. Регулярный синк дизайнеров и разработчиков. Главное — DS должна ускорять команды, иначе её начнут обходить.
</details>

<details><summary>Что вы включаете в техническое видение?</summary>

Контекст и бизнес-цели, диагноз текущих проблем с цифрами, целевое состояние через 2 года, принципы принятия решений, инициативы с приоритетами, non-goals и метрики успеха. Видение рождается из реальных решений и обсуждается с командой, а не спускается сверху.
</details>

## Практика

**Задача 1.** Напишите ADR на решение «переходим с Jest на Vitest».

<details><summary>Решение</summary>

Контекст: сборка на Vite, Jest требует отдельной конфигурации трансформаций (babel/ts-jest), расхождения с бандлером, тесты идут N минут. Решение: Vitest для unit/integration тестов, совместимый API (`describe/it/expect`, `vi` вместо `jest`). Варианты: оставить Jest (стабильно, но дублирование конфигурации), Vitest (единая конфигурация с Vite, быстрее на нашем объёме — замерить), Node test runner (мало экосистемы). Последствия: codemod для `jest.*` → `vi.*`, переходный период — оба раннера в CI, удаляем Jest после миграции; риск — различия в моках модулей. Метрика: время тестов в CI до/после.
</details>

**Задача 2.** Подготовьте одностраничное обоснование для CPO: «нужно 6 недель на миграцию корзины с легаси на новую архитектуру».

<details><summary>Решение</summary>

Проблема (в бизнес-языке): фичи корзины занимают в 2–2.5 раза дольше; за полгода 4 инцидента в оформлении заказа. Цена бездействия: Q3-роадмап содержит 3 фичи в корзине — при текущей скорости это ~12 недель вместо ~5. Предложение: 6 недель, 2 разработчика, поэтапно через strangler fig, без заморозки фич (остальная команда продолжает роадмап). Результат: скорость фич в корзине как в остальных модулях, автотесты на оформление, снижение инцидентов. Метрики и точки контроля каждые 2 недели. Риски и план B: если через 3 недели прогресс < 40%, останавливаемся, сохранив уже перенесённое.
</details>

**Задача 3.** Нарисуйте tech radar для своей команды (8–12 пунктов).

<details><summary>Решение</summary>

Пример: Adopt — TypeScript strict, React, Vite, TanStack Query, Playwright, Vitest; Trial — React Server Components в новом разделе, Biome вместо ESLint+Prettier; Assess — signals-подход, Module Federation 2; Hold — Enzyme, Moment.js, CSS-in-JS с рантаймом для новых модулей, Redux для серверного состояния. Для каждого — одна строка «почему». Главное — аргументы и правила использования колец.
</details>
