## Теория

### Стратегия тестирования

**Пирамида тестирования** (Mike Cohn, популяризирована Мартином Фаулером): много быстрых unit-тестов внизу, меньше интеграционных, немного медленных end-to-end сверху. Логика — стоимость и скорость.

**Testing Trophy** (Kent C. Dodds) — адаптация для фронтенда: снизу статический анализ (TypeScript, ESLint), затем unit, **основной объём — интеграционные тесты** (компонент/страница с реальными дочерними компонентами и замоканной сетью), сверху немного e2e. Принцип: «чем больше тест похож на то, как используется софт, тем больше уверенности он даёт».

| Уровень | Инструменты | Что проверяем | Доля усилий (ориентир для продуктового фронта) |
|---|---|---|---|
| Static | TypeScript strict, ESLint | Типы, очевидные ошибки | Всегда, «бесплатно» |
| Unit | Vitest/Jest | Чистая логика: утилиты, редьюсеры, форматтеры, хуки | 20–30% |
| Integration | Testing Library + MSW | Поведение компонента/фичи с точки зрения пользователя | 50–60% |
| E2E | Playwright | Критичные пользовательские пути на реальном окружении | 10–20%, только критичные флоу |
| Visual regression | Playwright screenshots, Chromatic, Loki | Регрессии UI design system | Для DS и ключевых страниц |
| Contract | OpenAPI-схемы, генерация типов, Pact | Совместимость с API | При активной разработке API |

**Стратегия лида — не «покрытие 80%», а ответ на вопрос «где у нас риск»:**
- Критичные флоу (регистрация, оплата, оформление заказа) — e2e + интеграционные.
- Сложная бизнес-логика — unit.
- UI-компоненты DS — визуальные + a11y-проверки (axe).
- Метрика покрытия — индикатор, а не цель (закон Гудхарта): 80% покрытия бессмысленными тестами хуже 50% осмысленных.
- **Flaky-тесты** — отдельная болезнь: карантин, владелец, дедлайн на починку; тест, который «иногда падает», учит игнорировать красный CI.

💡 На собеседовании: «Пирамида или трофей?» — правильный ответ: зависит от того, где в вашем приложении живёт сложность. Для типичного продуктового фронтенда, где сложность во взаимодействии компонентов и данных, — трофей. Для библиотеки с тяжёлой логикой — ближе к пирамиде.

### CI/CD

**Пайплайн фронтенда (пример):**

```
PR:   install (кеш) → lint + typecheck → unit/integration (параллельно, шардинг)
      → build → size-limit / бандл-анализ → preview-деплой → e2e smoke на preview
      → Lighthouse CI (перф-бюджет) → ревью
main: build → e2e (полный набор критичных) → деплой на staging → деплой на прод
      (canary / по проценту) → мониторинг → полный раскат
```

**Принципы:**
- **Быстрая обратная связь**: PR-пайплайн до ~10 минут. Кеш зависимостей, инкрементальные сборки (Turborepo/Nx affected), параллелизация тестов.
- **Build once, deploy many**: один артефакт идёт по всем окружениям; конфигурация окружения — в рантайме, а не пересборкой.
- **Preview-окружение на каждый PR** — дизайнер и продакт смотрят до мёржа.
- **Автоматический откат** или откат в один клик. Для статики — переключение на предыдущую версию ассетов.
- **Immutable ассеты** с хешем в имени + короткий кеш для `index.html`.
- Перф-бюджеты в CI (размер бандла, Lighthouse) — чтобы регрессии ловились до прода.

### Trunk-based development vs GitFlow

| | GitFlow | Trunk-based development |
|---|---|---|
| Ветки | main, develop, feature/*, release/*, hotfix/* | Одна основная ветка + короткоживущие ветки (≤ 1–2 дня) или прямо в trunk |
| Интеграция | Редкая, при мёрже фичи | Непрерывная, несколько раз в день |
| Незавершённые фичи | Живут в долгих ветках | Скрыты за feature flags |
| Релизы | По расписанию, через release-ветки | В любой момент из trunk |
| Конфликты | Большие, болезненные мёржи | Мелкие, частые |
| Когда уместен | Коробочный софт, мобильные приложения с ревью стора, несколько поддерживаемых версий | Веб-приложения с непрерывной поставкой |

«Accelerate» и исследования DORA связывают trunk-based development (мало активных веток, короткая жизнь веток, отсутствие периодов «заморозки кода») с более высокой эффективностью поставки. Для веб-фронтенда TBD + feature flags — стандарт индустрии; GitFlow создавался для другого мира (версионные релизы).

🪤 Ловушка: «перейдём на trunk-based» без feature flags, быстрого CI и хорошего покрытия тестами. Получите сломанный main. TBD — это набор практик, а не просто «мёржим в main».

### Feature flags

Мартин Фаулер (статья Pete Hodgson) выделяет 4 типа флагов по времени жизни и динамичности:

| Тип | Назначение | Время жизни |
|---|---|---|
| Release toggles | Скрыть незавершённую фичу в trunk | Дни–недели, удалить после релиза |
| Experiment toggles | A/B-тесты | Недели |
| Ops toggles | Kill switch, деградация функционала при нагрузке | Долго / постоянно |
| Permission toggles | Фичи для бета-пользователей, премиум | Долго / постоянно |

**Практики:**
- Флаги — **технический долг с рождения**: у каждого флага владелец и дата удаления; линтер/дашборд «протухших» флагов.
- Не вкладывать флаги друг в друга (комбинаторный взрыв состояний).
- Тестировать оба состояния флага для критичных путей.
- Постепенный раскат: внутренние пользователи → 1% → 10% → 50% → 100% с мониторингом на каждом шаге.
- Build vs buy: обычно — готовое решение (LaunchDarkly, Unleash, GrowthBook, Flagsmith и т. п.) или стандарт OpenFeature для независимости от вендора.

### Релизный процесс

**Цель** — релиз как скучное, рутинное событие. Чем чаще релизы, тем они меньше и безопаснее.

**Чек-лист зрелого релизного процесса:**
- Автоматический деплой из main (continuous delivery или deployment).
- Changelog / release notes генерируются из conventional commits.
- Канареечный или поэтапный раскат.
- Мониторинг ошибок и метрик после релиза с порогами автоматического отката (рост error rate × N).
- Откат за минуты.
- Отдельная процедура hotfix.
- Правило: не релизить крупное в пятницу вечером / перед праздниками **без готовности дежурных** (а лучше — сделать релизы настолько безопасными, что пятница не страшна, но дежурство всё равно нужно).
- Коммуникация: заинтересованные стороны знают, что вышло (канал релизов).

### Мониторинг фронтенда

| Слой | Инструменты | Что смотреть |
|---|---|---|
| Ошибки | Sentry (или аналоги) | JS-ошибки, unhandled rejections, ошибки по релизам, source maps, группировка, новые ошибки после релиза |
| RUM (Real User Monitoring) | web-vitals + своя аналитика, Sentry Performance, Datadog RUM и т. п. | Core Web Vitals (LCP, INP, CLS) на p75 по реальным пользователям, по устройствам, странам, страницам |
| Synthetic | Lighthouse CI, чекеры доступности | Регрессии в контролируемом окружении |
| Бизнес-метрики | Продуктовая аналитика | Конверсии ключевых шагов — падение конверсии часто первый сигнал бага |
| Сеть / API | RUM + бэкенд-мониторинг | Ошибки и латентность запросов с клиента |

Принципы: **алерты на симптомы, а не на причины** (рост error rate, падение конверсии), алерт должен быть actionable, иначе к нему привыкают (alert fatigue). Source maps загружаются в Sentry, но не публикуются в прод. Release tracking — связывать ошибки с версией. Сэмплирование для трафика и стоимости.

### DORA-метрики

Исследовательская программа **DORA** (DevOps Research and Assessment, книга «Accelerate») выделила метрики эффективности поставки ПО, связанные с результатами организации:

| Метрика | Что измеряет | Группа |
|---|---|---|
| Deployment frequency | Как часто деплоим в прод | Throughput (скорость) |
| Lead time for changes | От коммита до прода | Throughput |
| Change failure rate | Доля деплоев, вызвавших инцидент/откат/hotfix | Stability (стабильность) |
| Time to restore service (в новых отчётах — failed deployment recovery time) | Как быстро восстанавливаемся после сбойного изменения | Stability |

В отчёте 2024 года DORA добавила пятую метрику — **rework rate** (доля внеплановых деплоев для исправления проблем на проде).

Ключевой вывод исследований: **скорость и стабильность не противоречат друг другу** — лучшие команды хороши в обеих группах одновременно. Это главный аргумент против «давайте релизить реже, чтобы было стабильнее».

**Как использовать лиду:**
- Метрики команды, а не людей. Делать их KPI людей — гарантированно получить игру с цифрами.
- Смотреть на тренд, а не на абсолютное значение и сравнение с другими командами.
- Комбинировать с метриками опыта разработчиков (опросы, SPACE-фреймворк) — DORA не говорят о том, комфортно ли команде.
- Для фронтенда lead time часто съедается ожиданием ревью и QA — смотреть на разбиение (time to first review, time in QA).

### SLO для фронтенда

Из Google SRE: **SLI** (индикатор — что меряем), **SLO** (целевое значение), **error budget** (допустимая доля «плохого», 100% − SLO). Error budget превращает спор «скорость vs стабильность» в данные: пока бюджет есть — релизим смело, когда исчерпан — фокус на надёжности.

**Примеры SLO для фронтенда:**

| SLI | SLO (пример) |
|---|---|
| Доля сессий без JS-ошибок, ломающих флоу (crash-free sessions) | ≥ 99.5% за 28 дней |
| LCP на p75 по реальным пользователям на ключевых страницах | ≤ 2.5 s |
| INP на p75 | ≤ 200 ms |
| Доля успешных загрузок приложения (дошли до интерактивности) | ≥ 99.9% |
| Доля успешных клиентских запросов к критичным API | ≥ 99.9% |
| Успешное прохождение checkout (технически, без ошибок) | ≥ 99.5% |

Пороги LCP/INP/CLS совпадают с рекомендациями Core Web Vitals (хорошо: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 на p75).

🪤 Ловушка: SLO 100%. Это нереалистично и останавливает изменения. SLO выбирают исходя из того, что заметно пользователю и что важно бизнесу.

### Инциденты и blameless postmortem

**Процесс инцидента:**
1. **Обнаружение** — алерт или сообщение. Чем раньше, тем лучше.
2. **Объявление инцидента и уровень** (SEV1–SEV4), назначение **incident commander** (координирует, не обязательно чинит).
3. **Коммуникация** — канал инцидента, регулярные апдейты стейкхолдерам (каждые 30 минут для SEV1), статус-страница.
4. **Митигация, а не починка**: сначала остановить ущерб (откат, выключить флаг), потом искать корень.
5. **Восстановление и мониторинг**.
6. **Постмортем** в течение нескольких рабочих дней.

**Blameless postmortem** (Google SRE): цель — понять, как **система** позволила ошибке случиться, а не найти виноватого. Если человек мог одной командой уронить прод — это проблема системы, а не человека. Люди, которых наказывают за ошибки, начинают скрывать их — и вы теряете информацию.

**Шаблон постмортема:**

```markdown
# Постмортем: <краткое название> (SEV2)

- Дата инцидента: 2026-05-15, 18:40–19:25 MSK (45 мин)
- Автор(ы): ...           Статус: Черновик / На ревью / Завершён
- Затронуто: ~12% пользователей веб-версии не могли оформить заказ

## Резюме
2–3 предложения: что случилось, влияние, как устранили.

## Влияние
Пользователи, заказы, деньги (оценка), SLO / error budget, обращения в поддержку.

## Хронология (timeline)
- 18:32 — деплой v2.41.0 (изменение валидации формы адреса)
- 18:40 — рост ошибок в Sentry на /checkout (алерт сработал в 18:47)
- 18:52 — объявлен инцидент, IC — @dev-on-call
- 19:05 — причина локализована: новая валидация отвергает адреса без квартиры
- 19:10 — откат на v2.40.3
- 19:25 — метрики checkout вернулись к норме, инцидент закрыт

## Первопричина и сопутствующие факторы
Используем «5 почему» / анализ сопутствующих факторов, без поиска виноватых.
- Почему ошибка? Регулярное выражение требовало поле «квартира».
- Почему не поймали тестами? Нет тестов на адреса частных домов.
- Почему не поймали на раскате? Раскат сразу на 100%, нет канарейки.
- Почему алерт через 7 мин? Порог алерта — абсолютный, а не относительный.

## Что сработало хорошо
Быстрый откат, понятная роль IC.

## Что сработало плохо
Позднее обнаружение, нет поэтапного раската.

## Где нам повезло
Инцидент вечером, трафик ниже пикового.

## Action items
| Действие | Тип | Владелец | Срок | Тикет |
|---|---|---|---|---|
| Тесты на адреса без квартиры | Предотвращение | @a | 22.05 | FE-1201 |
| Канареечный раскат 5% → 100% для checkout | Предотвращение | @b | 05.06 | FE-1202 |
| Алерт на относительный рост ошибок checkout | Обнаружение | @c | 29.05 | FE-1203 |

## Уроки
```

Правила хорошего постмортема: формулировки без обвинений («деплой содержал…», а не «Вася задеплоил…»), action items конкретные, с владельцем и сроком, и **они выполняются** (отслеживать). Постмортемы открыты для всей инженерии — это база знаний.

## Вопросы с собеседований

<details><summary>Какую стратегию тестирования вы бы выстроили для фронтенда?</summary>

От рисков: критичные флоу — e2e на Playwright, основной объём — интеграционные тесты компонентов и фич через Testing Library и MSW, unit — для сложной логики, статический анализ — TypeScript strict и ESLint. Для design system — визуальные и a11y-тесты. Покрытие — индикатор, не цель. Flaky-тесты в карантин с владельцем. Это ближе к трофею Кента Доддса, чем к классической пирамиде.
</details>

<details><summary>Trunk-based или GitFlow?</summary>

Для веба — trunk-based: короткие ветки, частая интеграция, незавершённое за feature flags, релиз в любой момент. DORA связывает это с лучшей поставкой. Но TBD требует быстрого CI, тестов и флагов — без них сломаете main. GitFlow уместен там, где есть версионные релизы и несколько поддерживаемых версий (коробочный софт, иногда мобильные приложения).
</details>

<details><summary>Как вы используете feature flags и какие у них риски?</summary>

Для скрытия незавершённых фич, A/B-тестов, kill switch и доступа для бета-пользователей. Риски: флаги становятся долгом, комбинаторный взрыв состояний, нетестированные ветки. Поэтому: владелец и дата удаления у каждого release-флага, мониторинг протухших флагов, тесты обоих состояний для критичных путей, поэтапный раскат.
</details>

<details><summary>Что такое DORA-метрики? Как вы их используете?</summary>

Deployment frequency, lead time for changes, change failure rate, time to restore (плюс rework rate с 2024 года). Главный вывод исследований — скорость и стабильность идут вместе. Использую как метрики команды для выявления узких мест и тренда, но не как KPI людей и не для сравнения команд. Дополняю опросами о developer experience.
</details>

<details><summary>Как вы мониторите фронтенд в проде?</summary>

Ошибки — Sentry с source maps и release tracking. RUM — Core Web Vitals на p75 по реальным пользователям с разбивкой по страницам и устройствам. Synthetic — Lighthouse CI в пайплайне. Бизнес-метрики конверсии как ранний сигнал. Алерты на симптомы, actionable, с относительными порогами, чтобы не было alert fatigue.
</details>

<details><summary>Какие SLO можно поставить для фронтенда?</summary>

Crash-free sessions ≥ 99.5%, LCP p75 ≤ 2.5 s и INP p75 ≤ 200 ms на ключевых страницах, доля успешных загрузок приложения, доля успешных клиентских запросов к критичным API. С error budget: пока бюджет есть — релизим, исчерпан — фокус на надёжности. SLO согласуются с продуктом.
</details>

<details><summary>Что такое blameless postmortem и зачем он нужен?</summary>

Разбор инцидента без поиска виноватых, с фокусом на системных причинах: почему система позволила ошибке случиться и не обнаружила её раньше. Если людей наказывать, они начнут скрывать ошибки, и организация перестанет учиться. Результат — конкретные action items с владельцами и сроками, которые реально выполняются. Принцип из Google SRE Book.
</details>

<details><summary>Как сделать релизы безопасными?</summary>

Маленькие частые релизы, trunk-based с флагами, быстрый CI, canary / поэтапный раскат, мониторинг после релиза с автоматическим откатом по порогам, откат за минуты, build once deploy many. Релиз должен быть скучным событием.
</details>

<details><summary>Как вы снижаете change failure rate?</summary>

Анализирую постмортемы: какие классы ошибок доходят до прода. Тесты на критичные пути, контрактные тесты с API, preview-окружения для проверки продактом/дизайнером, feature flags и canary для снижения радиуса поражения, маленькие PR. Важно не снижать CFR ценой снижения частоты деплоев.
</details>

<details><summary>Как вы ведёте себя во время инцидента как лид?</summary>

Обеспечиваю, что есть incident commander (не обязательно я) и понятные роли. Сначала митигация — откат или выключение флага, потом поиск причины. Беру на себя коммуникацию со стейкхолдерами, чтобы инженеры не отвлекались. Слежу, чтобы не было паники и самостоятельных «героических» фиксов на проде. После — постмортем и контроль action items.
</details>

## Практика

**Задача 1.** Lead time у команды — 9 дней. Как найти, куда уходит время?

<details><summary>Решение</summary>

Разбить на этапы: от начала работы до PR, от PR до первого ревью, от ревью до мёржа, от мёржа до деплоя. Источники — трекер и Git/CI-история. Типично: несколько дней ожидания ревью, очередь QA, релиз раз в неделю. Действия по узкому месту (теория ограничений Голдратта — оптимизировать не узкое место бессмысленно): SLA ревью, меньше PR, автоматизация регресса, деплой из main без ожидания релизного окна.
</details>

**Задача 2.** После каждого релиза в Sentry появляются десятки новых ошибок, но никто их не смотрит. Как исправить?

<details><summary>Решение</summary>

Отделить шум от сигнала: игнорировать ошибки расширений и сторонних скриптов (фильтры), сгруппировать. Ввести владельца: дежурный по релизу проверяет новые ошибки в течение часа после деплоя. Алерты на новые issue с порогом по пользователям и на относительный рост error rate. Связка с релизами, чтобы видеть, какой релиз принёс ошибку. Регулярный разбор топ-ошибок как часть техдолга. Метрика — crash-free sessions как SLO.
</details>

**Задача 3.** Напишите action items к инциденту: «из-за обновления зависимости сломался рендер на Safari 15, заметили через 2 дня по жалобам».

<details><summary>Решение</summary>

Обнаружение: алерт на ошибки с разбивкой по браузерам (рост error rate в Safari); RUM-дашборд по браузерам. Предотвращение: e2e smoke в WebKit через Playwright в CI; browserslist согласован с аналитикой поддерживаемых браузеров; Renovate/Dependabot с группировкой и чтением changelog для мажорных обновлений. Процесс: в постмортеме — почему 2 дня без сигнала, кто смотрит обращения поддержки. У каждого пункта — владелец и срок.
</details>
