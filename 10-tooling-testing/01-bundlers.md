## Теория

### Зачем вообще сборщик

Браузер умеет ES-модули, но в продакшене без сборки:
- сотни мелких запросов и водопад импортов (каждый модуль узнаёт о своих зависимостях только после загрузки);
- нет поддержки TS, JSX, Vue SFC, CSS-модулей, импорта картинок;
- пакеты из `node_modules` в CommonJS и с «голыми» импортами (`import 'react'`), которые браузер не резолвит без import maps;
- нет минификации, tree shaking и хэшей для кэша.

### Этапы сборки

1. **Резолв** — превратить `import x from './a'` или `'react'` в путь к файлу (алиасы, поле `exports` в `package.json`, условия `import`/`require`/`browser`/`development`).
2. **Загрузка и трансформация** — TS → JS, JSX → вызовы функций, SFC → JS + CSS, CSS → модули/PostCSS, картинки → URL или inline.
3. **Граф модулей** — от точек входа по всем `import` (статическим и динамическим).
4. **Разбиение на чанки** — точка входа, каждый `import()` становится границей ленивого чанка, общие модули выносятся в общие чанки.
5. **Оптимизации** — tree shaking (удаление неиспользуемых экспортов), scope hoisting (склеивание модулей в одну область видимости), минификация, удаление мёртвого кода по `process.env.NODE_ENV`.
6. **Вывод** — файлы с хэшем содержимого (`index-3f9a1c.js`), манифест, sourcemaps, `index.html` с подключением.

### Vite

**Dev:** не собирает бандл. Сервер отдаёт исходники как нативные ES-модули и трансформирует каждый файл по запросу браузера. Зависимости из `node_modules` один раз **пред-собираются** (pre-bundling): CommonJS → ESM, сотни файлов `lodash-es` → один модуль. Старт — за сотни миллисекунд независимо от размера проекта.

**Prod:** полноценная сборка. Начиная с Vite 8 используется **Rolldown** (сборщик на Rust с API, совместимым с Rollup) вместо связки esbuild + Rollup — одинаковое поведение в dev и prod и быстрее сборка. Плагины — в формате Rollup плюс хуки Vite (`configureServer`, `transformIndexHtml`, `handleHotUpdate`).

Сильные стороны: скорость, простая конфигурация, экосистема (Vitest, Nuxt, SvelteKit, React Router, Astro построены на Vite), Environment API для SSR и нескольких сред.

### webpack

Всё — модуль: **loaders** трансформируют файлы (`ts-loader`, `css-loader`), **plugins** вмешиваются в любой этап компиляции (tapable-хуки). Собирает бандл и в dev (поэтому старт и HMR медленнее на больших проектах). Максимальная гибкость и зрелость: Module Federation, тонкая настройка `splitChunks`, огромное количество плагинов.

### Rspack и Turbopack

- **Rspack** — реализация webpack на Rust: совместим с большинством конфигов, лоадеров и плагинов webpack, в разы быстрее. Естественный путь миграции для больших webpack-проектов (Rsbuild — «Vite-подобная» обёртка над ним).
- **Turbopack** — инкрементальный сборщик на Rust от Vercel, сборщик по умолчанию в Next.js 16 для dev и prod. Вне Next.js не используется.

### Трансформеры: Babel, SWC, esbuild, Oxc

| Инструмент | Язык | Где используется |
|---|---|---|
| Babel | JS | максимальная гибкость плагинов, React Compiler как Babel-плагин, старые проекты |
| SWC | Rust | Next.js, Rspack, `@vitejs/plugin-react-swc` |
| esbuild | Go | трансформации TS/JSX и минификация в старых версиях Vite, быстрые CLI-сборки |
| Oxc | Rust | парсер и трансформер внутри Rolldown/Vite 8, Oxlint |

🪤 **Ловушка:** эти трансформеры **удаляют** типы TS, но не проверяют их. Проверка типов — отдельный шаг `tsc --noEmit` (или `vue-tsc`) в CI и в IDE.

### HMR

Dev-сервер держит WebSocket-соединение. При изменении файла сервер находит затронутые модули, браузер запрашивает новую версию модуля и вызывает обработчики `import.meta.hot.accept`. Плагины фреймворков (React Fast Refresh, Vue) регистрируют компоненты так, чтобы заменить реализацию без потери состояния. Если модуль не принимает обновление, оно «всплывает» к импортёрам; дошло до корня — полная перезагрузка.

### Хэши и долгое кэширование

Имя файла содержит хэш содержимого → можно отдавать с `Cache-Control: public, max-age=31536000, immutable`. `index.html` — без кэша (`no-cache`), чтобы пользователи получали новые ссылки. Если изменение одного модуля меняет хэши всех чанков (из-за общего рантайма или манифеста внутри чанков), кэш инвалидируется зря — сборщики решают это выделением рантайма и стабильными id модулей.

🪤 **Ловушка:** после деплоя старые чанки удаляются, а у открытой вкладки ещё старый `index.html` → `ChunkLoadError` / «Failed to fetch dynamically imported module». Решения: хранить предыдущие версии ассетов какое-то время, ловить ошибку загрузки чанка и перезагружать страницу (в Vite есть событие `vite:preloadError`).

### Как выбрать

| Ситуация | Выбор |
|---|---|
| Новое SPA, Vue, Svelte, библиотека | Vite (библиотеки — Vite library mode, tsdown, unbuild) |
| Next.js | встроенный Turbopack |
| Большой webpack-проект, тормозит сборка | Rspack — миграция с минимальными изменениями |
| Нужна Module Federation | webpack/Rspack (у Vite — через плагин `@module-federation/vite`) |

💡 **На собеседовании:** не «Vite лучше webpack», а «Vite быстрее в dev за счёт нативных ESM и по умолчанию проще; webpack/Rspack — когда нужна его экосистема или уже есть большой конфиг».

## Вопросы с собеседований

<details><summary>Почему dev-сервер Vite стартует мгновенно, а webpack — нет?</summary>

Webpack перед стартом строит граф и собирает бандл всего приложения. Vite отдаёт файлы как нативные ESM и трансформирует их по запросу — работа пропорциональна открытой странице, а не всему проекту. Зависимости пред-собираются один раз и кэшируются.
</details>

<details><summary>Чем отличается dev-сборка Vite от prod?</summary>

Dev — без бандла, модули по запросу, HMR. Prod — полная сборка (Rolldown) с tree shaking, чанками, минификацией и хэшами. Раньше dev шёл через esbuild, а prod — через Rollup, и поведение иногда расходилось (CJS-интероп, порядок CSS); Rolldown это унифицирует.
</details>

<details><summary>Что такое tree shaking и что ему мешает?</summary>

Удаление неиспользуемых экспортов на основе статического анализа ESM-импортов. Мешают: CommonJS (`require` динамичен), побочные эффекты при импорте (код верхнего уровня, полифилы, импорт CSS), реэкспорт-«бочки» без `sideEffects: false`, динамический доступ к объекту экспортов (`import * as ns; ns[name]`). Поле `"sideEffects": false` в `package.json` разрешает выбрасывать целые модули, если из них ничего не используется.
</details>

<details><summary>Зачем нужны sourcemaps и как их отдавать в продакшене?</summary>

Сопоставление собранного кода исходникам для отладки и стектрейсов. В продакшене — `hidden` sourcemaps: файлы генерируются и загружаются в Sentry при деплое, но ссылка `//# sourceMappingURL` в бандл не добавляется и сами файлы не публикуются.
</details>

<details><summary>Babel или SWC?</summary>

SWC в 10–20 раз быстрее и покрывает стандартные трансформации (TS, JSX, декораторы). Babel нужен, когда есть специфические плагины (некоторые макросы, React Compiler в виде Babel-плагина, кастомные трансформации кода). Многие проекты используют SWC/Oxc по умолчанию и Babel точечно.
</details>

<details><summary>Как работает HMR и почему иногда страница всё равно перезагружается?</summary>

Сервер по WebSocket сообщает об изменённых модулях, клиент загружает их заново и вызывает обработчики `accept`. Если цепочка импортов не содержит модуля, принимающего обновление (например, изменился конфиг или модуль с побочными эффектами), обновление доходит до корня и происходит полная перезагрузка. В React Fast Refresh состояние сбрасывается, если файл экспортирует не только компоненты.
</details>

## Практика

1. Соберите Vite-проект, откройте `dist/assets` и найдите, какие модули попали в каждый чанк.
2. Добавьте `import()` для тяжёлой страницы и проверьте, что появился отдельный чанк.
3. Включите `build.sourcemap: 'hidden'` и проверьте, что в бандле нет `sourceMappingURL`.
