## Теория

### Зачем тесты и сколько их нужно

Тесты — способ **менять код без страха**. Цель — не процент покрытия, а уверенность в критичных сценариях при разумной стоимости поддержки. Coverage полезен как индикатор непокрытых мест, но 100% покрытия тестами, проверяющими реализацию, хуже 60% тестов поведения.

### Уровни

| Уровень | Инструменты | Что проверяет | Скорость |
|---|---|---|---|
| Статика | TypeScript, ESLint | опечатки, типы, правила хуков, доступность в JSX | мгновенно |
| Unit | Vitest, Jest | чистые функции, форматтеры, редьюсеры, хуки | мс |
| Интеграционные / компонентные | Testing Library + Vitest (jsdom/happy-dom или Browser Mode), MSW | компонент или фича целиком: рендер, ввод, запросы, состояния | десятки мс |
| E2E | Playwright | сценарии в реальном браузере против собранного приложения | секунды |
| Визуальные | Chromatic, Playwright screenshots | вёрстка, темы, регрессии стилей | секунды |
| Нефункциональные | axe, Lighthouse CI | доступность, производительность | секунды |

**Трофей тестирования** (Kent C. Dodds): широкое основание статики, немного unit, **больше всего интеграционных**, немного e2e. Интеграционные тесты ближе к пользователю, чем unit, и гораздо дешевле и стабильнее e2e.

### Принципы Testing Library

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('показывает ошибку при пустом email', async () => {
  const user = userEvent.setup();
  render(<SignupForm />);

  await user.click(screen.getByRole('button', { name: /зарегистрироваться/i }));

  // Ищем так, как ищет пользователь и скринридер
  expect(await screen.findByRole('alert')).toHaveTextContent('Введите email');
  expect(screen.getByLabelText('Email')).toHaveAttribute('aria-invalid', 'true');
});
```

- Приоритет запросов: `getByRole` → `getByLabelText` → `getByText` → `getByTestId` (в крайнем случае).
- `userEvent` вместо `fireEvent`: настоящая последовательность событий (focus, keydown, input, click).
- `findBy*`/`waitFor` для асинхронного появления; `queryBy*` — чтобы проверить отсутствие.
- Не проверять внутреннее состояние, вызовы хуков, имена классов.

### Мок сети: MSW

Mock Service Worker перехватывает запросы на сетевом уровне (Service Worker в браузере, перехватчики в Node). Один набор обработчиков — для тестов, Storybook и локальной разработки без бэкенда.

```ts
import { http, HttpResponse, delay } from 'msw';
import { setupServer } from 'msw/node';

export const handlers = [
  http.get('/api/users/:id', ({ params }) => HttpResponse.json({ id: params.id, name: 'Аня' })),
];
export const server = setupServer(...handlers);

// В отдельном тесте — сценарий ошибки
server.use(http.get('/api/users/:id', () => new HttpResponse(null, { status: 500 })));
// Или медленный ответ для проверки состояния загрузки
server.use(http.get('/api/users/:id', async () => { await delay(200); return HttpResponse.json({}); }));
```

Почему не мокать `fetch`/axios модулем: тест привязывается к реализации клиента, а MSW проверяет реальную сериализацию, заголовки и обработку ответов.

### Асинхронность, таймеры и гонки

```ts
import { vi } from 'vitest';

test('поиск отправляет запрос через 300 мс после ввода', async () => {
  vi.useFakeTimers();
  const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime });
  render(<Search />);
  await user.type(screen.getByRole('searchbox'), 'react');
  await vi.advanceTimersByTimeAsync(300);
  expect(await screen.findByText('React — результат')).toBeInTheDocument();
  vi.useRealTimers();
});
```

Гонку запросов (ответ на старый запрос пришёл позже нового) воспроизводят в MSW разными задержками для разных параметров и проверяют, что на экране — результат последнего запроса.

🪤 **Ловушка:** предупреждение `act(...)` значит, что после теста ещё произошли обновления. Нужно дождаться результата (`findBy`), а не глушить предупреждение.

🪤 **Ловушка:** общее состояние между тестами (кэш TanStack Query, сторы-синглтоны, MSW-обработчики из `server.use`) → тесты зависят от порядка. Новый `QueryClient` на тест, `server.resetHandlers()` в `afterEach`.

### E2E на Playwright

- Только критичные пути: вход, оформление заказа, оплата, ключевые CRUD.
- Локаторы по ролям (`page.getByRole`), автоожидания, `expect(locator).toBeVisible()` вместо `waitForTimeout`.
- Данные готовятся через API или фикстуры, каждый тест независим; авторизация один раз через `storageState`.
- Параллелизм и шардинг в CI, ретраи с отчётом о нестабильных тестах, трассы (`trace: 'on-first-retry'`) для разбора.
- Сеть: реальный стенд для смоук-тестов или `page.route` для управляемых сценариев.

### Компонентные тесты в реальном браузере

jsdom не реализует раскладку, `IntersectionObserver`, canvas, реальные события фокуса. Vitest Browser Mode (с Playwright-провайдером) и Storybook interaction tests запускают компонентные тесты в настоящем браузере — ближе к реальности ценой скорости.

### Тестовая стратегия команды (лид)

Зафиксировать: какие уровни обязательны для какого кода (утилиты — unit, фичи — интеграционные, критичные сценарии — e2e), Definition of Done с тестами, работа с flaky (карантин + задача + владелец), время CI как метрика, тесты на баги (каждый баг → регрессионный тест), контрактные тесты API (сгенерированные типы из OpenAPI, Pact) при раздельных командах фронта и бэка.

## Вопросы с собеседований

<details><summary>Как распределить тесты между уровнями?</summary>

По риску и стоимости. Статика ловит целый класс ошибок бесплатно. Логику без UI — unit. Пользовательские сценарии внутри фичи — интеграционные тесты с Testing Library и MSW (основная масса). Несколько e2e на критичные пути через весь стек. Визуальная регрессия — для дизайн-системы. Распределение пересматривать по инцидентам: если баги уходят в прод — где их должен был поймать тест?
</details>

<details><summary>Почему нельзя тестировать детали реализации?</summary>

Такие тесты ломаются при рефакторинге без изменения поведения (ложные падения) и не ловят реальные баги (тест проверяет, что вызван `setState`, а пользователь видит не то). Тест должен падать, только если сломалось поведение, видимое пользователю или вызывающему коду.
</details>

<details><summary>Что такое flaky-тесты и как с ними бороться?</summary>

Нестабильные тесты, падающие без изменений кода. Причины: ожидание по таймауту вместо условия, общие данные и порядок тестов, анимации, время и случайность, гонки сети, нестабильное окружение. Лечение: автоожидания, изоляция данных, фиксированное время (`vi.setSystemTime`, `page.clock`), отключённые анимации, детерминированные моки; карантин с задачей на исправление и метрика доли flaky.
</details>

<details><summary>Как тестировать кастомный хук?</summary>

`renderHook` из Testing Library: проверить возвращаемые значения и их изменение после `act`/событий; провайдеры — через `wrapper`. Если хук — тонкая обёртка над запросом, лучше тестировать компонент, который его использует.
</details>

<details><summary>Snapshot-тесты: за и против?</summary>

Легко написать, но большие снимки разметки никто не читает при обновлении, и они ломаются от любой правки. Полезны маленькие inline-снимки для сериализуемых структур (результат трансформации, сообщение об ошибке). Для вёрстки лучше визуальная регрессия.
</details>

## Практика

1. Напишите интеграционный тест формы: валидация, отправка, ошибка сервера через MSW.
2. Напишите тест на гонку: два запроса поиска, ответ на первый приходит позже — на экране результат второго.
3. Напишите e2e-сценарий входа с `storageState` и переиспользуйте авторизацию в другом тесте.
