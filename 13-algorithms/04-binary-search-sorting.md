## Теория

### Бинарный поиск: один шаблон на всё

Работает на **монотонном** условии: есть граница, слева от которой `ok(x) === false`, справа — `true`. Ищем первую позицию, где условие истинно (lower bound).

```js
// Первый индекс i, для которого arr[i] >= target (или arr.length). O(log n)
function lowerBound(arr, target) {
  let lo = 0;
  let hi = arr.length; // полуинтервал [lo, hi)
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (arr[mid] < target) lo = mid + 1; // mid точно не ответ
    else hi = mid; // mid может быть ответом
  }
  return lo;
}
```

- Найти элемент: `i = lowerBound(arr, x)`, проверить `arr[i] === x`.
- Upper bound (первый `> target`): условие `arr[mid] <= target`.
- Количество вхождений: `upperBound - lowerBound`.

🪤 **Ловушка:** бесконечный цикл при `lo = mid` и `mid = (lo + hi) >> 1`. В шаблоне выше `lo` всегда сдвигается на `mid + 1`, а `hi = mid` уменьшает интервал — цикл конечен.

🪤 **Ловушка:** `(lo + hi) >> 1` работает только до 2³¹: битовые операции в JS приводят к int32. Для больших диапазонов (бинпоиск по ответу до 10¹²) используйте `Math.floor((lo + hi) / 2)`.

### Бинпоиск по ответу

Если вопрос «какое **минимальное** значение X, при котором что-то возможно», а проверка «возможно ли при X» монотонна и считается за O(n) — ищем X бинпоиском: O(n log(диапазон)).

Примеры: минимальная скорость поедания бананов за h часов, минимальная ёмкость для доставки за d дней, разбиение массива на k частей с минимальной максимальной суммой. Фронтенд-аналог: подобрать максимальный размер шрифта, при котором текст влезает в блок (проверка — измерение).

### Поиск в повёрнутом массиве

`[4,5,6,7,0,1,2]`: одна из половин всегда отсортирована. Определяем, какая, и проверяем, лежит ли target в её диапазоне.

### Сортировки

| Алгоритм | Время (среднее / худшее) | Память | Стабильна | Комментарий |
|---|---|---|---|---|
| Вставками | O(n²) / O(n²) | O(1) | да | O(n) на почти отсортированном, лучшая на маленьких массивах |
| Слиянием | O(n log n) / O(n log n) | O(n) | да | предсказуемая, подходит для связных списков и внешней сортировки |
| Быстрая | O(n log n) / O(n²) | O(log n) | нет | быстрая на практике; худший случай лечится случайным опорным |
| Кучей | O(n log n) / O(n log n) | O(1) | нет | гарантия без доп. памяти |
| Подсчётом / поразрядная | O(n + k) | O(k) | да | только для целых ключей из небольшого диапазона |
| TimSort (V8) | O(n log n) / O(n log n) | O(n) | да | слияние «серий» + вставки, O(n) на отсортированных данных |

Нижняя граница для сортировок **сравнением** — Ω(n log n). Подсчёт её обходит, потому что не сравнивает элементы.

```js
// Сортировка слиянием: O(n log n), стабильна
function mergeSort(arr) {
  if (arr.length <= 1) return arr;
  const mid = arr.length >> 1;
  const left = mergeSort(arr.slice(0, mid));
  const right = mergeSort(arr.slice(mid));
  const out = [];
  let i = 0;
  let j = 0;
  while (i < left.length && j < right.length) {
    // <= сохраняет стабильность: при равенстве берём левый
    out.push(left[i] <= right[j] ? left[i++] : right[j++]);
  }
  return out.concat(left.slice(i), right.slice(j));
}
```

### Компараторы в JS

```js
users.toSorted((a, b) => a.age - b.age); // числа по возрастанию
users.toSorted((a, b) => a.name.localeCompare(b.name, 'ru')); // строки с учётом локали
// По нескольким полям: первое ненулевое сравнение
users.toSorted((a, b) => a.role.localeCompare(b.role) || b.score - a.score);
// Для больших списков — один Intl.Collator вместо localeCompare на каждое сравнение
const collator = new Intl.Collator('ru', { numeric: true, sensitivity: 'base' });
files.toSorted((a, b) => collator.compare(a, b)); // 'file2' < 'file10'
```

🪤 **Ловушка:** компаратор `(a, b) => a > b` возвращает boolean — результат сортировки не гарантирован. Нужно отрицательное/ноль/положительное число.

## Вопросы с собеседований

<details><summary>Чем стабильная сортировка полезна во фронтенде?</summary>

Элементы с равными ключами сохраняют порядок. В таблице: отсортировали по дате, потом по статусу — внутри статуса порядок по дате сохранится. С ES2019 `Array.prototype.sort` обязана быть стабильной.
</details>

<details><summary>Почему quick sort на практике быстрее merge sort, хотя у него худший случай O(n²)?</summary>

Сортировка на месте (лучше для кэша процессора, меньше аллокаций), маленькая константа. Худший случай (уже отсортированный массив и плохой опорный) лечится случайным опорным или медианой трёх; introsort переключается на heap sort при глубокой рекурсии.
</details>

<details><summary>Что такое бинпоиск по ответу?</summary>

Бинпоиск не по массиву, а по диапазону возможных ответов, когда предикат «ответ X достижим» монотонен. Сложность — O(стоимость проверки × log диапазона).
</details>

<details><summary>Как отсортировать 10 млн целых чисел от 0 до 1000 быстрее, чем O(n log n)?</summary>

Сортировка подсчётом: массив счётчиков на 1001 элемент, один проход для подсчёта и один — для вывода. O(n + k).
</details>

<details><summary>Как найти первое вхождение элемента в отсортированном массиве с дубликатами?</summary>

Lower bound: не останавливаться при `arr[mid] === target`, а продолжать сужать влево (`hi = mid`).
</details>
