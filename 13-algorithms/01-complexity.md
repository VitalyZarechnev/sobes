## Теория

### Big O: что именно мы считаем

Big O описывает, **как растёт** время (или память) при росте входа `n`, отбрасывая константы и младшие члены: `3n² + 10n + 7` → `O(n²)`. Это верхняя граница роста, а не время в миллисекундах.

| Класс | Пример | n = 10⁶ — сколько операций |
|---|---|---|
| O(1) | доступ по индексу, `map.get` | 1 |
| O(log n) | бинарный поиск, операции кучи | ~20 |
| O(n) | один проход по массиву | 10⁶ |
| O(n log n) | сортировка | ~2·10⁷ |
| O(n²) | два вложенных цикла | 10¹² — не дождёмся |
| O(2ⁿ) | все подмножества | только для n ≤ ~25 |
| O(n!) | все перестановки | только для n ≤ ~10 |

💡 **На собеседовании:** по ограничениям можно угадать ожидаемую сложность. `n ≤ 20` — перебор/бэктрекинг; `n ≤ 10³` — O(n²) допустимо; `n ≤ 10⁵–10⁶` — нужно O(n) или O(n log n).

### Правила подсчёта

```js
// Последовательные блоки складываются: O(n) + O(m) = O(n + m)
for (const a of arrA) {}
for (const b of arrB) {}

// Вложенные — перемножаются: O(n · m)
for (const a of arrA) for (const b of arrB) {}

// Цикл, где шаг удваивается или делится пополам, — O(log n)
for (let i = 1; i < n; i *= 2) {}

// 🪤 Ловушка: скрытые циклы внутри методов
for (const x of arr) {
  if (result.includes(x)) continue; // includes — O(n) → итого O(n²)
  result.push(x);
}
```

### Стоимость операций в JavaScript

| Операция | Сложность | Комментарий |
|---|---|---|
| `arr[i]`, `arr.length`, `push`, `pop` | O(1) | `push` — амортизированно O(1) |
| `shift`, `unshift`, `splice(0, …)` | O(n) | сдвиг всех индексов; очередь на `shift` — O(n²) на n операций |
| `includes`, `indexOf`, `find`, `some` | O(n) | линейный поиск |
| `slice`, `concat`, `[...arr]`, `map`, `filter` | O(n) | создают новый массив — O(n) памяти |
| `sort`, `toSorted` | O(n log n) | TimSort, стабильная (с ES2019) |
| `map.get/set/has/delete`, `set.has/add` | O(1) в среднем | хэш-таблица |
| `obj[key]` | O(1) в среднем | но на «словарных» объектах медленнее Map при частом удалении |
| `Object.keys(obj)`, `JSON.stringify` | O(n) | n — число ключей/размер |
| `str[i]`, `str.length` | O(1) | |
| `str + str`, `slice`, `split`, `includes` | O(n) | строки неизменяемы; конкатенация в цикле — следите за суммарным размером |
| `structuredClone(obj)` | O(размер) | глубокое копирование |

### Амортизированная сложность

Массив в V8 хранится в буфере с запасом. Когда место кончается, буфер увеличивается примерно в 1,5 раза и элементы копируются — это O(n), но происходит всё реже. На n вставок суммарно O(n) работы → **амортизированно O(1)** на `push`.

### Сложность по памяти

Считаем **дополнительную** память: новые массивы, Map, стек рекурсии. Рекурсия глубины `d` — O(d) памяти; в JS стек ограничен (~10 000 вызовов, зависит от движка и размера фрейма), поэтому глубокую рекурсию (длинный список, вырожденное дерево) переписывают на явный стек.

### Сложность рекурсии

Дерево вызовов: время ≈ число узлов × работа в узле.

```js
// Наивный Фибоначчи: каждый вызов порождает 2 → O(2ⁿ) времени, O(n) памяти (глубина)
const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));

// С мемоизацией каждый n считается один раз → O(n) времени и памяти
const memo = new Map();
const fibMemo = (n) => {
  if (n < 2) return n;
  if (!memo.has(n)) memo.set(n, fibMemo(n - 1) + fibMemo(n - 2));
  return memo.get(n);
};
```

«Разделяй и властвуй» (сортировка слиянием): T(n) = 2T(n/2) + O(n) → O(n log n) — log n уровней, на каждом O(n) работы.

### Алгоритм решения задачи на интервью

1. **Уточнить** условие: типы и диапазоны входа, пустой вход, дубликаты, отрицательные числа, можно ли менять вход, что вернуть, если ответа нет.
2. **Примеры**: разобрать 1–2 своих, включая граничный.
3. **Брутфорс**: назвать простое решение и его сложность — это страховка и база для оптимизации.
4. **Оптимизация**: найти узкое место (повторные поиски → хэш; отсортированный вход → два указателя/бинпоиск; подотрезки → окно/префиксные суммы; «все варианты» → бэктрекинг; перекрывающиеся подзадачи → DP).
5. **Код**: понятные имена, маленькие функции, проговаривать вслух.
6. **Проверка**: прогнать пример руками, граничные случаи.
7. **Сложность** по времени и памяти + что можно улучшить.

💡 **На собеседовании:** молчание хуже ошибки. Если застряли — проговорите, что пробуете и почему не работает; интервьюер часто даёт подсказку.

## Вопросы с собеседований

<details><summary>Что такое Big O и почему константы отбрасывают?</summary>

Асимптотическая оценка роста затрат при росте входа. Константы зависят от железа и реализации, а интересует масштабирование: O(n) с константой 100 всё равно обгонит O(n²) при большом n. На практике константы важны при малых n — поэтому для 10 элементов линейный поиск может быть быстрее хэша.
</details>

<details><summary>Почему очередь на `Array.prototype.shift` — плохая идея?</summary>

`shift` сдвигает все элементы — O(n). Обработка n элементов в BFS даёт O(n²). Решения: хранить индекс головы (`head++`) и не удалять элементы, кольцевой буфер или очередь на двух стеках. Для небольших массивов V8 оптимизирует `shift`, но на больших это заметно.
</details>

<details><summary>Что такое амортизированная сложность? Пример.</summary>

Средняя стоимость операции на длинной последовательности, даже если отдельные операции дорогие. `push` в динамический массив: редкие перевыделения O(n), но суммарно O(n) на n операций → O(1) амортизированно. Аналогично — очередь на двух стеках.
</details>

<details><summary>Какая сложность у `arr.sort()` и какой алгоритм внутри?</summary>

O(n log n) по времени, V8 использует TimSort (гибрид сортировки слиянием и вставками, быстр на почти отсортированных данных), стабильная. Без компаратора сортирует как строки: `[10, 9, 1].sort()` → `[1, 10, 9]`.
</details>

<details><summary>Map или объект для хэш-таблицы?</summary>

Map: любые ключи (объекты, NaN), порядок вставки, `size`, быстрые частые добавления и удаления, нет конфликта с прототипом (`__proto__`, `constructor`). Объект: ключи — строки/символы, удобен для статических структур и JSON. Для алгоритмов — почти всегда Map/Set.
</details>

<details><summary>Как оценить сложность по памяти рекурсивной функции?</summary>

Глубина стека × память фрейма + дополнительные структуры. Обход сбалансированного дерева — O(log n), вырожденного — O(n). Мемоизация добавляет O(число состояний).
</details>

<details><summary>Какая сложность у этого кода?</summary>

```js
function f(arr) {
  const out = [];
  for (const x of arr) if (!out.includes(x)) out.push(x);
  return out.sort((a, b) => a - b);
}
```

O(n²) из-за `includes` в цикле (+ O(n log n) сортировки, поглощается). Оптимизация: `[...new Set(arr)].sort((a, b) => a - b)` — O(n log n).
</details>
