## Теория

### Проблемы CSS в больших проектах

Глобальное пространство имён, войны специфичности (`!important`, вложенные селекторы), мёртвые стили, которые страшно удалять, зависимость от порядка подключения файлов, переопределения стилей общих компонентов «снаружи».

### Подходы

| Подход | Плюсы | Минусы |
|---|---|---|
| БЭМ + Sass | понятная конвенция, нет зависимостей | изоляция только дисциплиной, длинные имена |
| CSS Modules | локальные имена при сборке, обычный CSS, ноль рантайма | динамика только через классы и переменные |
| Utility-first (Tailwind v4) | нет имён, нет мёртвого CSS, ограничения через тему, быстро | «шум» в разметке, нужен дизайн-конфиг; вариативность через `cva`/`tailwind-variants` |
| CSS-in-JS в рантайме (styled-components, Emotion) | стили рядом с логикой, динамические пропсы | стоимость в рантайме, проблемы с RSC и стримингом SSR, бандл |
| Zero-runtime CSS-in-JS (vanilla-extract, Panda CSS, StyleX, Linaria) | типобезопасность и колокация без рантайма | шаг сборки, ограничения динамики |
| Vue SFC `<style scoped>` | изоляция из коробки | глубокие переопределения через `:deep()` |

Тренд: отказ от runtime CSS-in-JS в пользу CSS-переменных + CSS Modules/Tailwind/zero-runtime. Styled-components в 2025 году перешёл в режим поддержки.

🪤 **Ловушка:** runtime CSS-in-JS вставляет стили во время рендера — в React Server Components нет контекста и рантайма для этого, а при стриминге SSR стили нужно собирать и отправлять вместе с чанками HTML.

### Cascade layers

```css
/* Порядок слоёв задаёт приоритет независимо от специфичности и порядка файлов */
@layer reset, tokens, ds, app, overrides;

@layer ds {
  .button { padding: var(--space-2) var(--space-4); }
}
@layer app {
  /* Простой селектор в более позднем слое побеждает сложный в раннем */
  .checkout .button { padding: 0; }
}
```

Стили без слоя имеют наивысший приоритет среди авторских. Библиотека дизайн-системы кладёт свои стили в слой `ds` — приложение переопределяет их без `!important` и гонки специфичности.

### Другие инструменты современного CSS

- `:where()` — нулевая специфичность: базовые стили библиотеки, которые легко переопределить.
- `@scope (.card) to (.card__content)` — стили применяются в границах компонента, «пончиковая» область.
- Container queries (`@container`) — компонент адаптируется к ширине своего контейнера, а не окна: правильная модель для переиспользуемых компонентов.
- CSS-переменные компонента как публичный API кастомизации: `--button-radius`, `--card-padding`.
- Нативный CSS nesting — меньше потребность в препроцессоре.
- Логические свойства (`margin-inline-start`) — поддержка RTL бесплатно.

### Как ограничить локальные переопределения

1. Дать официальные точки кастомизации: варианты, размеры, слоты, CSS-переменные компонента.
2. `className` — только на корневой элемент, внутренняя структура не контракт.
3. Слои: стили библиотеки в `@layer ds`.
4. Линтер: запрет селекторов по внутренним классам библиотеки (stylelint `selector-disallowed-list`), запрет `!important`.
5. Собирать запросы на кастомизацию: частые → новый вариант в библиотеке.
6. Сканировать использование и переопределения, чтобы видеть дрейф.

### Организация стилей приложения

Токены и глобальные стили (reset, типографика) → стили дизайн-системы → стили фич рядом с компонентами. Отступы между компонентами задаёт родитель (layout-примитивы `Stack`/`Grid` с `gap`), а не сам компонент внешним `margin` — иначе компонент нельзя переиспользовать в другом контексте.

## Вопросы с собеседований

<details><summary>Как структурировать CSS большого приложения, избегая конфликтов специфичности?</summary>

Изоляция имён (CSS Modules, scoped-стили, utility-классы), cascade layers для порядка приоритетов (reset → токены → ДС → приложение), низкая и плоская специфичность (`:where()`, один класс), токены через CSS-переменные, линтер против `!important` и глубоких селекторов, отступы через layout-примитивы.
</details>

<details><summary>Когда вы рекомендовали бы против CSS-in-JS?</summary>

Против runtime-решений: при SSR со стримингом и RSC, на слабых устройствах (стоимость вычисления стилей при рендере), в библиотеках компонентов (навязывает рантайм потребителям). Zero-runtime варианты дают типобезопасность без этих проблем.
</details>

<details><summary>Чем container queries лучше media queries для компонентов?</summary>

Компонент реагирует на доступное ему место: одна и та же карточка в узком сайдбаре и широкой колонке выглядит правильно без знания о странице. Media queries привязывают компонент к ширине окна.
</details>

<details><summary>Что дают cascade layers дизайн-системе?</summary>

Предсказуемый порядок: стили библиотеки в своём слое всегда проигрывают стилям приложения в более позднем слое, независимо от специфичности. Не нужен `!important` и раздувание селекторов.
</details>

## Практика

1. Разнесите стили проекта по слоям `reset, tokens, ds, app` и уберите все `!important`.
2. Переведите карточку с media queries на container queries.
3. Дайте компоненту `Button` публичные CSS-переменные для кастомизации и запретите линтером селекторы по его внутренним классам.
