## Как готовиться
1. Посмотрите на 2–3 открытые дизайн-системы: [Material 3](https://m3.material.io/), [Primer (GitHub)](https://primer.style/), [Gravity UI (Яндекс)](https://gravity-ui.com/), [Atlassian Design System](https://atlassian.design/) — как они устроены: токены, компоненты, документация, changelog.
2. Разберите headless-библиотеки: [React Aria](https://react-spectrum.adobe.com/react-aria/), [Radix Primitives](https://www.radix-ui.com/primitives), [Ark UI](https://ark-ui.com/) — какой API и как решена доступность.
3. Подготовьте историю из своего опыта: компонент или библиотека, которую вы спроектировали или поддерживали, и одна проблема (breaking change, расхождение с макетами, кастомизация командами).
4. Пройдите [банк вопросов](../quizzes/quiz.html?id=14-design-systems/interview-bank).

## Самопроверка раздела (топ-10 вопросов)
1. Чем примитивные токены отличаются от семантических и почему компоненты должны использовать только семантические?
2. Как сделать тёмную тему и брендинг нескольких продуктов без дублирования компонентов?
3. Как спроектировать API компонента, чтобы он не оброс десятком булевых пропсов?
4. Compound components, slots, `asChild`/polymorphic `as` — когда что?
5. Почему лучше брать headless-примитивы, чем писать доступный Combobox с нуля?
6. Как выпустить breaking change в библиотеке, которую используют 10 команд?
7. Как поддерживать Storybook и документацию в актуальном состоянии?
8. CSS Modules, Tailwind, CSS-in-JS в рантайме, zero-runtime — как выбрать?
9. Как не дать командам ломать стили общих компонентов локальными переопределениями?
10. Как организовать процесс между дизайном и разработкой, чтобы макеты и код не расходились?
