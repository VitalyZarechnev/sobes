## Теория

### Главная ось: автономия и единица работы

Удобнее всего классифицировать инструменты по тому, **какой кусок работы отдаётся модели** и **как часто человек вмешивается**:

```
строка/блок  →  правка в файлах  →  задача в репозитории  →  задача → PR без человека
(автодополнение)  (чат/inline edit)   (агент в IDE / CLI)       (облачный асинхронный агент)

      ← высокий контроль, низкий рычаг            низкий контроль, высокий рычаг →
```

Чем правее, тем больше выигрыш на единицу внимания и тем важнее **верификация** (тесты, CI, ревью), потому что человек видит не процесс, а результат.

### 1. Автодополнение (inline completion)

Модель дописывает код по месту курсора, часто многострочно, с учётом открытых файлов. Классический представитель — GitHub Copilot; аналогичные функции есть во всех AI-IDE (Cursor Tab и др.) и в JetBrains AI.

- Сильные стороны: нулевое трение, хорошо на бойлерплейте, тестах, повторяющихся паттернах.
- Слабые: видит локальный контекст, легко принимается «на автомате», незаметно вносит ошибки в мелочах (неверное имя поля, граничное условие).

### 2. Чат и AI-IDE

IDE со встроенным чатом, редактированием нескольких файлов и агентным режимом: Cursor, Windsurf, VS Code + Copilot (chat / agent mode), JetBrains IDE с AI-ассистентами. Ключевые возможности класса:
- индексация репозитория и поиск по нему;
- правки сразу в нескольких файлах с diff-просмотром;
- агентный режим — запуск команд, тестов, итерации до результата;
- файлы правил проекта (например, `.cursor/rules/`, `.github/copilot-instructions.md`; многие инструменты на момент написания понимают и `AGENTS.md`);
- подключение MCP-серверов.

### 3. Терминальные (CLI) агенты

Агент работает в терминале в вашем репозитории: читает файлы, ищет по коду, редактирует, запускает команды, коммитит. Примеры на момент написания: Claude Code, OpenAI Codex CLI, Gemini CLI, Aider (open source, исторически один из первых, с упором на git-коммиты по каждой правке).

Почему этот класс стал популярен у senior-разработчиков:
- **независимость от редактора** — работает рядом с любой IDE;
- **композиция с Unix-инструментами** — пайпы, скрипты, headless-режим для CI;
- **конфигурируемость** — файлы инструкций, команды, хуки, субагенты, MCP, права доступа;
- **параллелизм** — несколько сессий в разных git worktree.

### 4. Облачные / асинхронные агенты

Задача (issue, сообщение в чате, комментарий в PR) → агент в облачной песочнице клонирует репозиторий, работает, прогоняет проверки → открывает PR. Примеры на момент написания: GitHub Copilot coding agent (назначение issue на Copilot), облачный режим OpenAI Codex, Google Jules, облачные/фоновые агенты в AI-IDE, запуск Claude Code из GitHub Actions или в веб-интерфейсе.

- Сильные стороны: параллельно разгребать мелкие, хорошо описанные задачи (баги с репродукцией, обновление зависимостей, миграции по шаблону, тесты); не занимает локальную машину.
- Риски: ревью становится узким местом; песочнице нужны доступы (секреты, сеть) — вопрос безопасности; плохо описанная задача даёт PR «не о том».

### 5. Генераторы UI и приложений

Из текстового описания (или скриншота) — работающий интерфейс или целое приложение: v0 (Vercel), bolt.new (StackBlitz), Lovable и аналоги. Как правило, генерируют React + Tailwind + популярные UI-киты, умеют деплоить.

- Сильные стороны: прототип за минуты, проверка гипотез с продактом и дизайнером, стартовая разметка.
- Риски: код не следует вашей архитектуре (FSD, дизайн-система, стейт-менеджмент), доступность и обработка ошибок часто поверхностны, «работает в демо» ≠ готово к продакшену; данные/ключи в сторонних сервисах.

💡 На собеседовании: «Генераторы UI — инструмент discovery, а не delivery. Результат — референс или выброшенный прототип, в продакшен он попадает только через переписывание под наши стандарты».

### 6. Design-to-code

Связка дизайн-инструмента с агентом. На момент написания у Figma есть MCP-сервер (связан с Dev Mode), через который агент получает структуру макета, переменные (токены), компоненты, скриншоты фрейма; Code Connect позволяет сопоставить компоненты Figma с компонентами кодовой базы, чтобы агент использовал ваш `<Button>`, а не генерировал новый.

- Сильные стороны: агент видит реальные токены и структуру, а не «картинку»; меньше ручного переноса отступов и цветов.
- Риски: качество зависит от гигиены макетов (auto layout, именование, переменные); без маппинга компонентов агент плодит дубли.

### Критерии выбора инструмента для команды

1. **Безопасность и данные**: куда уходит код, обучается ли вендор на ваших данных, есть ли enterprise-план, zero data retention, on-prem/частное облако, SSO, аудит-лог. Для многих компаний это первый и решающий фильтр.
2. **Модели**: можно ли выбирать модель, есть ли доступ к сильным моделям для агентной работы.
3. **Конфигурируемость**: файлы инструкций в репозитории, хуки, MCP, права на команды.
4. **Интеграции**: Git-хостинг, трекер, CI.
5. **Стоимость**: подписка на место vs оплата по токенам; у агентов расход токенов на порядок выше, чем у автодополнения.
6. **Переносимость**: открытые стандарты (`AGENTS.md`, MCP) снижают lock-in — инструкции и MCP-серверы переживут смену инструмента.

🪤 Ловушка: выбирать «один инструмент на всех». Реалистичная картина — автодополнение у всех, агент (IDE или CLI) по выбору разработчика, общие стандарты (инструкции, MCP, правила ревью) — в репозитории, независимо от инструмента.

### Открытые стандарты, которые стоит знать

- **MCP (Model Context Protocol)** — открытый протокол подключения инструментов и данных к AI-приложениям. Один MCP-сервер (например, для вашего трекера) работает с разными клиентами. Подробнее — [03](03-working-with-agents.md#mcp-серверы).
- **AGENTS.md** — открытый формат файла инструкций для кодовых агентов: обычный Markdown в корне (и, при необходимости, во вложенных папках) репозитория. На момент написания поддерживается многими агентами; у отдельных инструментов есть собственные файлы (`CLAUDE.md`, `.cursor/rules/`, `.github/copilot-instructions.md`).

## Вопросы с собеседований

<details><summary>Какими AI-инструментами вы пользуетесь и почему именно ими?</summary>

Хороший ответ структурный, а не список брендов: «Автодополнение — постоянно, для рутины. Для фич и рефакторингов — агент (назвать), потому что работает с репозиторием и командами, настроен через инструкции и хуки. Облачные агенты — для изолированных задач с тестами. Генераторы UI — только для прототипов». Добавить, как вы проверяете результат, и одну конкретную историю, где агент сэкономил время, и одну, где ошибся и как это поймали.
</details>

<details><summary>Чем агент отличается от автодополнения с точки зрения процесса?</summary>

Автодополнение — подсказка в момент написания, человек контролирует каждую строку. Агент выполняет многошаговую задачу: ищет контекст, правит файлы, запускает команды, сам проверяет. Человек контролирует план и результат, а не каждый шаг. Следствие: смещение работы в постановку задачи и верификацию; обязательны тесты, линт, типы, ревью diff, ограничение прав.
</details>

<details><summary>Когда стоит использовать облачного агента, который сам делает PR?</summary>

Когда задача хорошо описана и проверяема автоматически: баг с шагами воспроизведения, обновление зависимостей, миграция API по шаблону, покрытие тестами, мелкие UI-правки по чётким критериям. Не стоит — для архитектурных изменений, задач с неясными требованиями, кода с доступом к чувствительным данным без настроенной песочницы. Главный риск — ревью становится бутылочным горлышком.
</details>

<details><summary>Продакт принёс прототип из генератора UI и просит «просто задеплоить». Ваши действия?</summary>

Похвалить скорость проверки гипотезы, но объяснить разницу прототипа и продукта: архитектура и дизайн-система, a11y, обработка ошибок и состояний загрузки, безопасность (ключи, авторизация), тесты, мониторинг. Предложить: прототип — это спецификация; оцениваем перенос в кодовую базу (часто агент делает его быстро, если есть хорошие инструкции проекта). Если нужно срочно — отдельный изолированный контур с явным статусом эксперимента.
</details>

<details><summary>Как вы оцениваете AI-инструмент для внедрения в компании?</summary>

По шагам: политика данных (обучение на коде, retention, хранение, регион, enterprise-соглашения), безопасность (SSO, аудит, права агента, песочница), качество на наших задачах (пилот на реальных тикетах с метриками, а не демо), конфигурируемость (инструкции в репозитории, MCP, хуки), стоимость (подписка vs токены), переносимость (открытые стандарты). Решение — после пилота с обратной связью от команды.
</details>

<details><summary>Что такое design-to-code через MCP и чем это лучше скриншота макета?</summary>

Агент получает не пиксели, а структуру: иерархию слоёв, auto layout, переменные (цвета, отступы, типографику), имена компонентов, а при настроенном маппинге — ссылки на компоненты кодовой базы. Это даёт точные токены и переиспользование существующих компонентов вместо генерации новых. Ограничение — качество зависит от гигиены макетов.
</details>

<details><summary>Почему важны открытые стандарты вроде MCP и AGENTS.md?</summary>

Снижают vendor lock-in: инструкции проекта и интеграции с внутренними системами делаются один раз и работают в разных агентах. Для лида это аргумент при выборе: инвестиции команды в настройку не обнуляются при смене инструмента.
</details>

<details><summary>Какие риски у автодополнения, которое «и так все используют»?</summary>

Незаметные ошибки в мелочах (поле, условие, off-by-one), копирование небезопасных паттернов, лицензионно сомнительные фрагменты (у ряда вендоров есть фильтры совпадений с публичным кодом), отправка содержимого открытых файлов вендору — включая `.env`, если он открыт. Меры: исключения файлов из контекста, корпоративный план, ревью как обычно.
</details>

## Практика

**1. Подберите инструменты.** Команда из 8 фронтендеров, банк, код нельзя отправлять во внешние сервисы без enterprise-соглашения. Задачи: поддержка большого монорепо, частые миграции между версиями библиотек, вёрстка по Figma. Предложите стек и процесс.

<details><summary>Решение</summary>

Сначала юридический фильтр: только инструменты с enterprise-соглашением (без обучения на данных, с ограниченным хранением) или с доступом к моделям через корпоративное облако. Стек: автодополнение для всех; агент (CLI или AI-IDE) с инструкциями проекта в репозитории (`AGENTS.md` + специфичные файлы), хуками на линт/тайпчек, запретом доступа к секретам; Figma MCP с Code Connect для дизайн-системы; миграции — агентом по чек-листу с прогоном тестов в CI, разбитые на небольшие PR. Облачные агенты — только после согласования песочницы с безопасностью. Пилот 4–6 недель на 2–3 разработчиках, метрики — lead time и качество, не строки кода (см. [05](05-ai-for-leads.md)).
</details>

**2. Классифицируйте задачи по классу инструмента:** а) написать 20 однотипных unit-тестов для утилит; б) разобраться, как устроена авторизация в незнакомом монорепо; в) показать заказчику три варианта лендинга завтра; г) обновить мажорную версию роутера в 40 файлах; д) поправить опечатку.

<details><summary>Решение</summary>

а) Агент (IDE/CLI) с образцом теста в контексте, либо автодополнение, если тестов немного. б) CLI-агент / агент IDE в режиме только чтения (исследование, без правок) — лучше субагентом, чтобы не засорять контекст. в) Генератор UI. г) Агент с планом и тестами, разбить на этапы; при хорошем покрытии — облачный агент. д) Руками — любой агент тут дороже.
</details>
