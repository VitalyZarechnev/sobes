## Теория

### Что такое LLM в одной фразе

Большая языковая модель (Large Language Model) — это функция, которая по последовательности токенов предсказывает распределение вероятностей следующего токена. Генерация текста — это цикл: выбрать токен из распределения → дописать в контекст → повторить. Отсюда все свойства, важные инженеру:

- модель **не «знает» факты**, а воспроизводит статистически правдоподобные продолжения;
- модель **не имеет памяти** между запросами — всё «знание о разговоре» передаётся в каждом запросе заново;
- генерация **последовательная** — время ответа растёт с длиной вывода;
- результат **недетерминирован** (в общем случае), даже при одинаковом входе.

### Токены

Токен (token) — единица, на которую токенизатор режет текст: часть слова, слово, пробел, знак. Для английского грубо ~4 символа на токен, для русского и для кода токенов на тот же объём обычно больше (конкретное соотношение зависит от токенизатора модели — не запоминайте цифры, считайте через API подсчёта токенов провайдера).

Почему это важно:
- **лимиты** (контекстное окно, максимальная длина ответа) — в токенах;
- **цена** — в токенах, причём входные и выходные токены тарифицируются по-разному (выходные обычно дороже);
- **латентность** — в первую очередь от числа выходных токенов.

🪤 Ловушка: модели плохо делают посимвольные операции (посчитать буквы, перевернуть строку) именно потому, что «видят» токены, а не символы. Для таких задач — код/инструмент, а не модель.

### Контекстное окно

Контекстное окно (context window) — максимум токенов, которые модель учитывает за один вызов: системный промпт + история + документы + описания инструментов + сам ответ.

Нюансы для senior:
- **Больше ≠ лучше.** Качество использования длинного контекста неравномерно: информация может «теряться», внимание размывается, нерелевантный шум ухудшает ответ. на практике качество падает по мере заполнения окна, поэтому контекст надо рассматривать как ограниченный ресурс, а не как бесплатное хранилище.
- **Стоимость и задержка** растут с каждым токеном входа на каждом шаге. У агента, который делает 30 итераций, весь контекст пересылается 30 раз.
- **Кэширование промпта** (prompt caching) — механизм ряда провайдеров: неизменный префикс (системный промпт, инструкции, документы) кэшируется, повторные запросы с тем же префиксом дешевле и быстрее. Вывод для архитектуры: стабильное — в начало, изменчивое — в конец.

### Температура и сэмплинг

Температура (temperature) масштабирует распределение перед выбором токена: низкая — выбирается наиболее вероятное, высокая — распределение «сплющивается». Есть также top-p / top-k.

| Задача | Настройка | Почему |
|---|---|---|
| Извлечение данных, классификация, код | низкая | нужна воспроизводимость |
| Генерация вариантов текста, брейншторм | выше | нужна вариативность |
| Агентная работа | по умолчанию провайдера | провайдеры тюнят дефолты под свои модели |

🪤 Ловушка: температура 0 **не гарантирует** детерминизм — на стороне инфраструктуры бывают недетерминированные вычисления. Тесты на точное совпадение строки ответа модели — хрупкие. Проверяйте свойства (схема, наличие фактов), а не текст.

Также у моделей с «режимом рассуждений» (extended thinking / reasoning) часть параметров сэмплинга может быть недоступна или ограничена — смотрите документацию конкретной модели.

### Галлюцинации

Галлюцинация (hallucination) — уверенно сформулированный, но неверный вывод: несуществующий метод API, выдуманный пакет, неверный факт. Причина структурная: модель оптимизирована на правдоподобие, а не на истинность, и не умеет надёжно говорить «не знаю».

Как снижать (по убыванию эффективности):
1. **Заземление (grounding)**: дать актуальные данные в контекст — документацию, код, результаты поиска (RAG, tools).
2. **Верификация**: проверять результат детерминированно — типы, тесты, линтер, сборка. Для кода это главный рычаг.
3. **Разрешить неуверенность**: явно в инструкциях «если не знаешь — скажи».
4. **Цитирование**: требовать ссылку на источник из переданного контекста.

🪤 Ловушка: «package hallucination» — модель предлагает установить несуществующий npm-пакет, а злоумышленник может заранее зарегистрировать такое имя. Любую новую зависимость из AI-ответа проверяйте вручную (OWASP LLM Top 10 относит это к рискам supply chain).

### Embeddings и векторный поиск

Эмбеддинг (embedding) — вектор чисел, представляющий смысл текста. Семантически близкие тексты дают близкие векторы (по косинусной близости). Используется для:
- семантического поиска («найди похожие тикеты»);
- RAG (поиск релевантных фрагментов);
- кластеризации, дедупликации, рекомендаций.

Эмбеддинги генерирует отдельная embedding-модель; хранятся в векторной БД или в обычной БД с векторным индексом.

### RAG

RAG (Retrieval-Augmented Generation) — перед генерацией найти релевантные данные и положить их в контекст.

```
Индексация (офлайн):  документы → чанкинг → эмбеддинги → векторный индекс
Запрос (онлайн):      вопрос → эмбеддинг → top-k чанков → (реранкинг) → промпт + чанки → LLM → ответ со ссылками
```

Точки отказа, которые стоит назвать на собеседовании:
- **чанкинг** — порезали таблицу или код посередине, потерялся смысл;
- **retrieval** — нашлось не то (семантический поиск плохо работает с точными идентификаторами — поэтому часто гибрид: векторный + полнотекстовый BM25);
- **устаревание индекса** — документы обновились, индекс нет;
- **права доступа** — пользователь получил в ответе фрагмент документа, к которому у него нет доступа (фильтрация должна быть на этапе retrieval, а не «попросим модель не показывать»);
- **отравление данных** — в индексируемом документе спрятан prompt injection.

💡 На собеседовании: «RAG — это не про модель, а про поиск. 80% качества — в чанкинге, retrieval и оценке; модель лишь формулирует ответ по найденному».

**Агентный поиск vs RAG.** Кодовые агенты (на момент написания — Claude Code и аналоги) часто не используют векторный индекс, а ищут по коду инструментами (`grep`, `glob`, чтение файлов) — модель сама решает, что искать. Плюсы: актуальность, точность по идентификаторам, нет инфраструктуры индекса. Минус: больше шагов и токенов.

### Tool calling / function calling

Модель **ничего не выполняет сама**. Протокол:

1. Вы передаёте модели описания инструментов: имя, описание, JSON Schema параметров.
2. Модель вместо текста возвращает «запрос на вызов»: имя инструмента + аргументы.
3. **Ваш код** выполняет инструмент и возвращает результат модели следующим сообщением.
4. Модель продолжает — либо вызывает следующий инструмент, либо отвечает.

```ts
// Псевдо-TS: суть цикла tool calling, без привязки к SDK конкретного провайдера
type ToolCall = { id: string; name: string; input: unknown };
type ModelTurn = { text?: string; toolCalls: ToolCall[] };

async function runAgent(
  messages: Message[],
  callModel: (m: Message[]) => Promise<ModelTurn>,
  tools: Record<string, (input: unknown) => Promise<string>>,
  maxSteps = 10, // всегда ограничивайте число шагов
): Promise<string> {
  let history = messages;
  for (let step = 0; step < maxSteps; step++) {
    const turn = await callModel(history);
    if (turn.toolCalls.length === 0) return turn.text ?? '';

    const results = await Promise.all(
      turn.toolCalls.map(async (call) => {
        const tool = tools[call.name];
        // Аргументы от модели — недоверенные данные: валидируйте схемой
        const output = tool ? await tool(call.input) : `Unknown tool: ${call.name}`;
        return { toolCallId: call.id, output };
      }),
    );
    history = [...history, assistantTurn(turn), toolResults(results)];
  }
  throw new Error('Agent exceeded max steps');
}
```

Что важно:
- **качество описаний инструментов** влияет на результат не меньше промпта (в «Building effective agents» это названо agent-computer interface, ACI — проектировать инструменты для модели так же тщательно, как UI для человека);
- **аргументы — недоверенный ввод**: модель могла быть «взломана» через контекст;
- **минимальные права**: инструмент «удалить запись» без подтверждения человека — это риск Excessive Agency из OWASP LLM Top 10.

### Structured output

Structured output — получение ответа в заданном формате (обычно JSON по схеме). Способы, от надёжного к слабому:
1. нативный режим провайдера «ответ строго по JSON Schema» (если поддерживается моделью);
2. tool calling с единственным инструментом, чьи параметры и есть нужная схема;
3. инструкция в промпте + парсинг + повтор при ошибке.

В любом случае **валидируйте на своей стороне** (zod / valibot) — схема на стороне провайдера гарантирует форму, но не смысл.

### Стоимость и латентность

Ключевые метрики UX: **TTFT** (time to first token) и **скорость генерации** (токенов/с). Полное время ≈ TTFT + выходные токены / скорость.

Рычаги:
- **стриминг** — не уменьшает общее время, но радикально улучшает воспринимаемую скорость;
- **модель по задаче** — маленькая быстрая модель для классификации/роутинга, большая — для сложных рассуждений;
- **короче вывод** — просите кратко, используйте structured output;
- **кэширование промпта**, кэширование ответов на идентичные запросы;
- **параллелизация** независимых вызовов;
- **batch API** (у ряда провайдеров) — дешевле, но асинхронно, для офлайн-задач.

### Prompt engineering vs context engineering

**Prompt engineering** — как сформулировать инструкцию: роль, задача, ограничения, формат вывода, примеры (few-shot), разметка разделов (например, XML-теги для отделения данных от инструкций), просьба рассуждать перед ответом.

**Context engineering** — более широкая дисциплина: **какие токены вообще попадают в контекст** на каждом шаге — системный промпт, инструкции проекта, история, результаты инструментов, найденные документы, память. Для агентов это главное: агент за десятки шагов набирает огромный контекст, и задача инженера — держать его компактным и релевантным (компактизация, субагенты с изолированным контекстом, загрузка по требованию, заметки вне контекста).

💡 На собеседовании: «Prompt engineering — про формулировку, context engineering — про отбор информации. Для одиночного запроса важнее первое, для агентов — второе».

### Ограничения, о которых нужно помнить

- **Knowledge cutoff** — модель не знает про релизы после даты среза обучения; для фронта это значит устаревшие API библиотек. Лечится документацией в контексте.
- **Недетерминизм** — нужны evals, а не единичные проверки.
- **Нет настоящей «памяти»** — память реализуется приложением (файлы, БД, суммаризация).
- **Sycophancy** — склонность соглашаться с пользователем; «ты уверен?» может заставить модель отказаться от верного ответа.
- **Безопасность** — модель не различает надёжно инструкции и данные; всё, что попало в контекст, может повлиять на поведение (prompt injection).

## Вопросы с собеседований

<details><summary>Почему LLM «галлюцинирует» и как с этим бороться в инженерной системе?</summary>

Модель оптимизирована предсказывать правдоподобное продолжение, а не истинное; у неё нет встроенного механизма «я не знаю». Бороться — не «лучшим промптом», а архитектурой: заземление (RAG, инструменты, документация в контексте), детерминированная верификация (типы, тесты, схемы), цитирование источников, разрешение отвечать «не знаю», human-in-the-loop для критичных действий. Для senior: упомянуть package hallucination как supply-chain риск.
</details>

<details><summary>Окно контекста у модели огромное. Почему бы не класть туда весь репозиторий?</summary>

Три причины: стоимость (каждый шаг агента пересылает весь контекст), латентность (TTFT растёт с длиной входа), качество (шум размывает внимание, релевантное «теряется»). Правильно — давать минимально достаточный контекст: агентный поиск по коду, загрузка файлов по требованию, изолированные субагенты для исследований. Плюс кэширование стабильного префикса.
</details>

<details><summary>Что такое RAG? Когда RAG, когда fine-tuning, когда просто длинный контекст?</summary>

RAG — поиск релевантных данных и подстановка в промпт. Подходит для знаний, которые часто меняются или требуют ссылок и разграничения доступа. Fine-tuning меняет поведение/стиль/формат модели, плохо подходит для «добавления фактов» и дорог в поддержке. Длинный контекст — когда данных немного и они нужны целиком (один документ, один модуль). В продуктовой разработке почти всегда начинают с промпта + RAG/tools, fine-tuning — последнее средство.
</details>

<details><summary>Как работает tool calling? Кто выполняет функцию?</summary>

Модель получает описания инструментов (имя, описание, JSON Schema), возвращает структурированный запрос вызова, а выполняет его **приложение**, затем возвращает результат модели. Цикл повторяется до финального ответа. Важно: ограничение числа шагов, валидация аргументов, минимальные права инструментов, подтверждение человеком для необратимых действий, качественные описания инструментов.
</details>

<details><summary>Как получить от модели гарантированно валидный JSON?</summary>

Использовать нативный structured output по JSON Schema, если провайдер и модель поддерживают, или tool calling с одной схемой. В любом случае валидировать на своей стороне (zod) и иметь стратегию на невалидный ответ: повтор с ошибкой валидации в контексте, фолбэк, понятная ошибка пользователю. Схема гарантирует форму, но не корректность значений.
</details>

<details><summary>Что такое температура? Какую ставить для генерации кода?</summary>

Масштабирование распределения вероятностей при выборе токена. Для кода, извлечения данных и классификации — низкая; для генерации вариантов — выше. Но 0 не даёт строгого детерминизма, а у reasoning-моделей параметры сэмплинга могут быть ограничены. Для агентов обычно оставляют дефолты провайдера.
</details>

<details><summary>Как снизить стоимость и латентность LLM-фичи?</summary>

Выбор модели по задаче (роутинг: маленькая модель для простого), стриминг для воспринимаемой скорости, короткий вывод, structured output, кэширование промпта (стабильный префикс в начало), кэш ответов, параллельные независимые вызовы, batch для офлайна, обрезка истории/суммаризация. Измерять TTFT, токены на запрос и стоимость на пользовательскую операцию.
</details>

<details><summary>Чем prompt engineering отличается от context engineering?</summary>

Prompt engineering — формулировка инструкции: роль, задача, формат, примеры. Context engineering — управление всем набором токенов, который видит модель на каждом шаге: инструкции проекта, история, результаты инструментов, документы, память. Для агентов context engineering критичнее: контекст растёт с каждым шагом и деградирует.
</details>

<details><summary>Что такое embeddings и где они пригодятся фронтенду?</summary>

Векторное представление смысла текста. Применения: семантический поиск по документации/товарам, «похожие» элементы, дедупликация обращений, RAG. Фронтенд обычно не считает эмбеддинги сам (хотя есть варианты in-browser моделей), но проектирует UX поиска: гибрид с полнотекстовым поиском, подсветка, объяснение, почему найдено.
</details>

<details><summary>Почему тесты вида «ответ модели равен строке X» — плохие?</summary>

Вывод недетерминирован и меняется при обновлении модели. Тестировать нужно свойства: соответствие схеме, наличие ключевых фактов, отсутствие запрещённого контента, оценку по рубрике (в том числе LLM-as-a-judge) на наборе примеров — то есть evals. Для unit-тестов UI модель мокается.
</details>

## Практика

**1. Оценка стоимости.** Чат-бот поддержки: системный промпт 2 000 токенов, в среднем 6 реплик, каждая реплика пользователя 100 токенов, ответ 300 токенов. История передаётся целиком. Сколько входных токенов уходит на шестой запрос? Что оптимизировать?

<details><summary>Решение</summary>

Шестой запрос: 2 000 (system) + 5 × (100 + 300) (история) + 100 (новый вопрос) = 4 100 входных токенов. За диалог суммарно вход растёт квадратично по числу реплик. Оптимизации: кэширование системного промпта (стабильный префикс), суммаризация старой истории, ограничение длины ответа, маленькая модель для простых интентов (роутинг).
</details>

**2. Спроектируйте RAG для поиска по внутренней документации дизайн-системы.** Назовите 4 риска и как их закрыть.

<details><summary>Решение</summary>

Чанкинг по структуре (заголовки, отдельные блоки кода с примерами компонентов), гибридный поиск (векторный + полнотекстовый — имена компонентов и пропсов — точные идентификаторы), реранкинг, ответ со ссылками на страницы. Риски: устаревший индекс → переиндексация по событию деплоя документации; поиск по точным именам → BM25; галлюцинация пропсов → в ответе только то, что есть в чанках, + ссылка; injection через документ → документы только из доверенного источника, вывод модели не исполняется как HTML.

**3. Вы получили от модели JSON.** Напишите функцию, которая валидирует его zod-схемой и делает один повтор с текстом ошибки.

<details><summary>Решение</summary>

```ts
import { z } from 'zod';

const Product = z.object({
  title: z.string().min(1),
  price: z.number().nonnegative(),
  tags: z.array(z.string()).max(10),
});
type Product = z.infer<typeof Product>;

async function extractProduct(
  ask: (prompt: string) => Promise<string>,
  text: string,
): Promise<Product> {
  const base = `Extract product as JSON {title, price, tags} from:\n<text>${text}</text>`;
  let prompt = base;
  for (let attempt = 0; attempt < 2; attempt++) {
    const raw = await ask(prompt);
    let candidate: unknown;
    try {
      candidate = JSON.parse(raw);
    } catch {
      prompt = `${base}\nPrevious answer was not valid JSON. Return JSON only.`;
      continue;
    }
    const parsed = Product.safeParse(candidate);
    if (parsed.success) return parsed.data;
    prompt = `${base}\nPrevious answer failed validation: ${parsed.error.message}`;
  }
  throw new Error('Model did not return valid product after retry');
}
```
