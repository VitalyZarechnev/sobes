## Теория

### Термины: render ≠ обновление DOM

В React «рендер» (render) — это **вызов функции компонента** для вычисления нового описания UI. Изменение DOM — отдельная фаза, **commit**. Поэтому «компонент перерендерился» не значит «DOM поменялся».

Цикл обновления:
1. **Trigger** — первичный `root.render()` или `setState` / dispatch / изменение контекста / внешнего стора.
2. **Render phase** — React вызывает компоненты, строит новое дерево Fiber (work-in-progress), вычисляет разницу. Фаза **чистая и прерываемая** (в concurrent-режиме) — может быть выброшена и повторена.
3. **Commit phase** — синхронно применяет мутации DOM, обновляет `ref`, вызывает `useLayoutEffect`, затем браузер рисует, затем (обычно) `useEffect`.

```tsx
function Counter() {
  const [n, setN] = useState(0);
  console.log('render', n);          // render phase — может вызываться несколько раз
  useLayoutEffect(() => console.log('layout', n)); // commit, до отрисовки
  useEffect(() => console.log('effect', n));       // после отрисовки
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
```

🪤 Ловушка: побочные эффекты в теле компонента (запросы, мутация внешних объектов, `Math.random` для id) ломаются при повторном/прерванном рендере. Именно поэтому StrictMode в dev **дважды вызывает** функции компонентов, инициализаторы `useState`, редьюсеры и дважды монтирует эффекты (mount → unmount → mount).

### Virtual DOM — что это на самом деле

JSX компилируется в вызовы `jsx(type, props, key)` и возвращает **React-элементы** — лёгкие иммутабельные объекты `{ $$typeof, type, key, props, ref }`. Это и есть «виртуальный DOM» — описание желаемого UI. Важно для senior:

- VDOM — **не про скорость** «быстрее DOM». Прямые точечные мутации всегда быстрее. VDOM — про **декларативную модель**: вы описываете состояние → UI, а библиотека вычисляет минимальные мутации. Плюс VDOM абстрагирует рендер-таргет (React DOM, React Native, ink, three-fiber).
- Цена — работа на каждом рендере: вызов компонентов + сравнение. Отсюда мемоизация, а у Vue/Solid/Svelte — компиляторные оптимизации и fine-grained реактивность.

### Fiber

**Fiber** — внутренняя структура данных (и одновременно «единица работы»), введённая в React 16 вместо рекурсивного stack reconciler. Каждый компонент/host-элемент — узел Fiber:

```ts
// Упрощённо
interface Fiber {
  tag: WorkTag;              // FunctionComponent, HostComponent ('div'), Suspense, ...
  type: any;                 // функция компонента или 'div'
  key: string | null;
  stateNode: any;            // DOM-узел для host-компонентов
  child: Fiber | null;       // первый ребёнок
  sibling: Fiber | null;     // следующий брат
  return: Fiber | null;      // родитель
  pendingProps: any;
  memoizedProps: any;
  memoizedState: any;        // для функциональных — связный список хуков
  updateQueue: any;          // эффекты, обновления
  flags: Flags;              // Placement, Update, Deletion, Passive...
  lanes: Lanes;              // приоритет ожидающей работы
  alternate: Fiber | null;   // пара current <-> workInProgress
}
```

Ключевые идеи:
- **Связный список вместо рекурсии.** Обход `child → sibling → return` можно остановить в любой точке и продолжить позже. Рекурсию JS-стека прервать нельзя.
- **Double buffering.** Есть дерево `current` (то, что на экране) и `workInProgress`. Рендер строит WIP; в commit указатель корня переключается — WIP становится current. Пары связаны через `alternate`, узлы переиспользуются.
- **Lanes** — битовые маски приоритетов (SyncLane для дискретных событий вроде click, InputContinuous, Default, Transition lanes, Idle). Позволяют прервать низкоприоритетный рендер ради срочного и затем возобновить/перезапустить.
- **Work loop** в concurrent-режиме: `while (wip && !shouldYield()) performUnitOfWork(wip)`. Планировщик (`scheduler`) отдаёт управление браузеру примерно каждые 5 мс через `MessageChannel`.

💡 На собеседовании: «Fiber — это переписанный реконсилер, где дерево представлено связным списком узлов-единиц работы. Это дало возможность делить рендер на кусочки, приоритизировать обновления (lanes), прерывать и переиспользовать работу. Commit при этом остаётся синхронным — DOM никогда не бывает в полуобновлённом состоянии».

### Reconciliation: эвристики O(n)

Точный diff двух деревьев — O(n³). React использует две эвристики и получает O(n):

1. **Разный `type` → поддерево пересоздаётся.** `<div>` → `<section>` или `<A/>` → `<B/>` — старое поддерево размонтируется вместе со всем состоянием.
2. **`key` идентифицирует детей в списке.** Без ключей сравнение идёт по индексу.

Позиция в дереве + тип + key = **идентичность** компонента. Состояние привязано к позиции в дереве, а не к JSX-переменной.

```tsx
// 🪤 Ловушка: компонент, объявленный внутри другого компонента
function Parent() {
  // Каждый рендер — НОВАЯ функция => новый type => размонтирование, потеря state и фокуса
  const Input = () => <input />;
  return <Input />;
}

// Один и тот же тип в одной позиции — состояние СОХРАНЯЕТСЯ
function Profile({ isAdmin }: { isAdmin: boolean }) {
  return isAdmin ? <Form role="admin" /> : <Form role="user" />;
}

// Сброс состояния ключом — штатный приём
<ChatRoom key={roomId} roomId={roomId} />
```

### Keys в списках

```tsx
// Плохо: key=index при вставке в начало / сортировке / удалении
{items.map((item, i) => <Row key={i} item={item} />)}
```

Если вставить элемент в начало, у всех элементов сместятся индексы. React решит, что `key=0` — тот же компонент, и **переиспользует его состояние** (введённый текст в `<input>`, раскрытость, фокус) для другого элемента. Плюс лишние обновления всех строк.

Правила:
- Ключ стабилен, уникален среди братьев, приходит из данных (`id`).
- Не генерировать `key={Math.random()}` / `crypto.randomUUID()` в рендере — каждое обновление ремоунтит всё.
- Index допустим только для статичных, неизменяемых списков без состояния.

Алгоритм для детей-массива: проход слева направо, пока ключи совпадают; затем строится `Map` оставшихся старых по ключу, новые ищутся в ней; узлы, которые «уехали» левее последней позиции, помечаются `Placement` (перемещение). Поэтому перенос последнего элемента в начало дороже, чем первого в конец.

### Batching

С React 18 действует **automatic batching**: несколько `setState` в одном синхронном тике объединяются в один рендер — независимо от того, где они вызваны (обработчик, `setTimeout`, промис, нативный listener). До 18 батчинг был только в обработчиках React.

```tsx
async function onSave() {
  setLoading(true);
  const data = await api.save();
  setData(data);      // ┐ один рендер
  setLoading(false);  // ┘
}
```

`flushSync` из `react-dom` принудительно синхронно применяет обновление — нужно, например, чтобы прокрутить к только что добавленному элементу:

```tsx
import { flushSync } from 'react-dom';
flushSync(() => setItems(prev => [...prev, newItem]));
listRef.current?.lastElementChild?.scrollIntoView();
```

🪤 Ловушка: `setState` не меняет значение в текущем замыкании. `setN(n + 1); setN(n + 1);` даст +1. Используйте функциональную форму `setN(p => p + 1)` — обновления ставятся в очередь и применяются последовательно.

### Concurrent rendering и transitions

Concurrent rendering — не «многопоточность», а **прерываемый рендер с приоритетами**. Включается автоматически при использовании concurrent-фич (`createRoot` + transitions/Suspense/`useDeferredValue`).

```tsx
const [query, setQuery] = useState('');
const [results, setResults] = useState<Item[]>([]);
const [isPending, startTransition] = useTransition();

function onChange(e: React.ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value);                 // срочно: инпут отзывчивый
  startTransition(() => {
    setResults(filterHeavy(e.target.value)); // не срочно: можно прервать
  });
}
```

- Обновления внутри `startTransition` получают transition lane. Если пришло срочное обновление — React бросит незаконченный WIP и начнёт заново.
- Transition **не показывает fallback** Suspense для уже показанного контента — оставляет старый UI (с `isPending`), вместо того чтобы «мигать» спиннером.
- В React 19 `startTransition` принимает **async-функцию** (Actions): `isPending` держится до завершения промиса.
- 🪤 Ловушка: transition не ускоряет тяжёлый синхронный код вне рендера. Если `filterHeavy` выполняется в обработчике, он заблокирует поток. Прерывается только **рендер компонентов**, поэтому тяжёлое вычисление должно жить в рендере (через `useMemo` от отложенного значения).
- Контролируемые инпуты нельзя обновлять в transition — ввод начнёт «залипать».

`useDeferredValue` — то же, но со стороны потребителя: получаем «отстающую» копию значения.

```tsx
const deferredQuery = useDeferredValue(query);
const isStale = query !== deferredQuery;
const list = useMemo(() => <HeavyList query={deferredQuery} />, [deferredQuery]);
return <div style={{ opacity: isStale ? 0.6 : 1 }}>{list}</div>;
```

React 19: `useDeferredValue(value, initialValue)` — начальное значение для первого рендера (полезно при SSR).

### Suspense

`<Suspense fallback>` — граница, которая показывает fallback, пока какой-то ребёнок «приостановлен». Механика: компонент во время рендера **бросает промис** (или вызывает `use(promise)` с незавершённым промисом); React ловит его на ближайшей границе Suspense, показывает fallback и повторяет рендер, когда промис разрешится.

Что поддерживает Suspense:
- `React.lazy` (code splitting);
- `use(promise)` в React 19 и data-фреймворки (Next.js, Relay, TanStack Query `useSuspenseQuery`);
- Server Components и стриминг SSR.

Не поддерживает: данные, загружаемые в `useEffect`, — эффект выполняется после commit, Suspense о нём не знает.

Нюансы:
- **Вложенные границы** задают последовательность раскрытия: снаружи общий скелетон, внутри — детальные.
- Состояние приостановленного поддерева при первом монтировании **не сохраняется** — компонент не смонтирован. Уже показанный контент при повторной приостановке скрывается (`display: none`), но не размонтируется, а эффекты layout вызывают cleanup.
- React 19 изменил поведение: при приостановке ребёнка React **сразу показывает fallback**, не дорендеривая соседей («pre-warming» соседей происходит после). Это ускоряет показ fallback, но обнажает водопады, если каждый ребёнок сам начинает загрузку — данные надо запрашивать выше (в роутере/лоадере/RSC).
- Промис для `use` должен быть **стабильным** (создан вне рендера или закэширован), иначе бесконечный цикл приостановок.

### Как React решает, какие компоненты рендерить

- Обновление состояния помечает Fiber и путь к корню (`lanes` / `childLanes`).
- При рендере React начинает с корня, но **пропускает (bailout)** поддеревья без работы.
- Компонент, у которого изменилось состояние, рендерится; **все его дети рендерятся по умолчанию**, даже если пропсы не изменились (сравнение только по ссылке JSX-объекта: новые элементы создаются каждый рендер).
- Bailout для ребёнка: `React.memo` (shallow compare пропсов), либо тот же объект-элемент (`children`, переданный сверху, — паттерн «поднятие контента вверх»), либо `Object.is` равенство нового state старому.

```tsx
// children созданы в App — при изменении state в Layout не перерендериваются
function Layout({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false);
  return <div>{/* ... */}{children}</div>;
}
```

## Вопросы с собеседований

<details><summary>Что происходит после вызова setState?</summary>

Обновление ставится в очередь хука с lane по контексту (дискретное событие — SyncLane, внутри transition — TransitionLane). Fiber и его предки помечаются. Планировщик назначает задачу; синхронные обновления батчатся и обрабатываются в микрозадаче в конце события. Render phase: React идёт от корня, пропускает поддеревья без работы, вызывает компонент, применяет очередь апдейтов, сравнивает детей. Commit: мутации DOM, `ref`, layout-эффекты, затем пассивные эффекты. Для senior: упомянуть eager state (если очередь пуста и новый state `Object.is` равен старому, рендер может не планироваться), прерываемость в transitions и то, что commit атомарен.
</details>

<details><summary>Почему не стоит использовать индекс как key?</summary>

Key — идентичность элемента между рендерами. При вставке/удалении/сортировке индексы смещаются, React сопоставит состояние не тем элементам: значения неконтролируемых инпутов, фокус, локальный state «переедут». Плюс лишние обновления. Индекс допустим для статических списков. Генерация случайного ключа в рендере — ещё хуже: полный ремоунт каждый раз.
</details>

<details><summary>Что такое Fiber и что он дал?</summary>

Структура-узел и единица работы. Дерево как связный список (`child/sibling/return`), что позволяет прерывать и возобновлять обход; double buffering через `alternate`; приоритеты через lanes. Это основа concurrent-фич: transitions, Suspense, selective hydration, `useDeferredValue`. Commit остаётся синхронным.
</details>

<details><summary>Чем отличаются фазы render и commit? Какие требования к коду в каждой?</summary>

Render — чистое вычисление, может вызываться многократно, прерываться, отбрасываться. Никаких сайд-эффектов, мутаций, подписок. Commit — синхронное применение изменений к DOM, вызов ref-коллбеков, `useLayoutEffect` (блокирует отрисовку), после отрисовки — `useEffect`. Побочные эффекты — в обработчиках событий или эффектах.
</details>

<details><summary>Что такое automatic batching и когда он мешает?</summary>

С React 18 все `setState` в одном тике объединяются в один рендер в любом контексте. Мешает, когда нужно синхронно прочитать DOM после обновления (скролл, измерение) — тогда `flushSync`. Классовый `setState` с колбэком и `useLayoutEffect` — альтернативы.
</details>

<details><summary>Объясните useTransition vs useDeferredValue vs debounce.</summary>

`useTransition` — помечает **обновление** как несрочное в месте вызова setState; даёт `isPending`. `useDeferredValue` — помечает **значение** как отстающее в месте потребления, полезно, когда нет доступа к setState (значение из пропсов). Оба прерываемы и не имеют фиксированной задержки: на быстром устройстве отстают минимально. Debounce/throttle — фиксированная задержка, уменьшает **число** операций (например, сетевых запросов), а не делает рендер прерываемым. Для запросов в сеть обычно нужен debounce, для тяжёлого рендера — deferred value.
</details>

<details><summary>Как работает Suspense под капотом?</summary>

Компонент во время рендера бросает thenable (или `use()` получает незавершённый промис). React раскручивает стек Fiber до ближайшей `Suspense`, помечает её как приостановленную, рендерит fallback, подписывается на промис и при резолве ретраит рендер. Внутри transition уже показанный контент не заменяется fallback'ом. Данные из `useEffect` Suspense не поддерживает.
</details>

<details><summary>Почему компонент, объявленный внутри другого компонента, теряет состояние?</summary>

При каждом рендере родителя создаётся новая функция → новый `type`. Эвристика reconciliation: разный тип — пересоздать поддерево. Итог: размонтирование, потеря state и фокуса, лишние эффекты. Выносить на модульный уровень.
</details>

<details><summary>Как сбросить состояние компонента при смене сущности?</summary>

Передать `key={entity.id}`: новый ключ — новая идентичность — компонент монтируется заново. Это предпочтительнее, чем эффект, сбрасывающий state при изменении пропа (лишний рендер с неконсистентными данными).
</details>

<details><summary>Почему в dev-режиме эффекты срабатывают дважды?</summary>

StrictMode монтирует, размонтирует и снова монтирует компонент, чтобы выявить эффекты без корректного cleanup. Это подготовка к фичам вроде Activity (бывший Offscreen), где компонент может скрываться и показываться с сохранением состояния. В проде этого нет. Решение — не отключать StrictMode, а писать идемпотентный cleanup (abort запроса, отписка).
</details>

<details><summary>Что такое bailout и почему дочерние компоненты рендерятся без изменения пропсов?</summary>

JSX создаёт новые объекты пропсов на каждый рендер, React по умолчанию не делает глубоких сравнений — рендер дешевле сравнения в большинстве случаев. Bailout происходит, если элемент тот же по ссылке (паттерн `children`), если компонент обёрнут в `memo` и пропсы shallow-равны, или если в нём нет работы по lanes и контекст не менялся.
</details>

## Практика

**1. Предскажи вывод.**

```tsx
function App() {
  const [n, setN] = useState(0);
  console.log('render', n);
  return (
    <button onClick={() => {
      setN(n + 1);
      setN(n + 1);
      setN(p => p + 1);
      console.log('click', n);
    }}>{n}</button>
  );
}
```

<details><summary>Решение</summary>

После клика: `click 0`, затем `render 2`. Очередь: `0+1 → 1`, `0+1 → 1`, `p => p+1 → 2`. Один рендер благодаря батчингу; `n` в замыкании равен 0.
</details>

**2. Найди баг.** Список задач с `key={index}` и неконтролируемым `<input defaultValue>`; после удаления первой задачи в инпутах «съезжают» тексты. Объясни и исправь.

<details><summary>Решение</summary>

Fiber с `key=0` переиспользуется для бывшего второго элемента, DOM-инпут сохраняет набранное значение, а `defaultValue` применяется только при монтировании. Фикс: `key={todo.id}`.
</details>

**3. Спроектируй.** Поиск по 10 000 элементам, ввод лагает. Предложи решение без сторонних библиотек.

<details><summary>Решение</summary>

`useDeferredValue(query)` + `memo`-компонент списка, принимающий отложенное значение, + индикатор устаревания. Если и так тормозит — виртуализация списка; фильтрацию можно вынести в Web Worker. Для запросов в сеть — debounce + `AbortController`.
</details>
