## Теория

### Модель

Коммит — снимок дерева файлов + метаданные + ссылки на родителей; хэш вычисляется из содержимого. Ветка — просто подвижный указатель на коммит. `HEAD` — указатель на текущую ветку (или коммит в detached-состоянии). Три области: рабочая директория → индекс (staging) → репозиторий.

### merge, rebase, squash

| | Что делает | Плюсы | Минусы |
|---|---|---|---|
| merge | merge-коммит с двумя родителями | история как была, не переписывает | «косички» в истории |
| rebase | переносит коммиты поверх другой базы с новыми хэшами | линейная история | переписывает историю — не для общих веток |
| squash merge | все коммиты PR в один в main | чистый main, один коммит = одна фича | теряется детальная история PR |

Правило: **не переписывать историю, на которую опираются другие** (опубликованные общие ветки). Свою фича-ветку — можно, с `push --force-with-lease` (не перетрёт чужие изменения, которых вы не видели).

### Конфликты

Возникают, когда обе стороны изменили одни и те же строки (или одна удалила файл, а другая изменила).

```text
<<<<<<< HEAD (ваша сторона)
const limit = 20;
=======
const limit = config.pageSize;
>>>>>>> main
```

Порядок: понять **намерение** обеих сторон (посмотреть коммиты: `git log -p --merge`), собрать правильный результат (иногда — третий вариант), запустить тесты, `git add`, продолжить (`git rebase --continue` / `git commit`). Lock-файлы — не править руками, а перегенерировать установкой. `git rerere` запоминает решения повторяющихся конфликтов. Настройка `merge.conflictStyle = zdiff3` показывает ещё и общего предка — сильно упрощает понимание.

🪤 **Ловушка:** при rebase «ours» и «theirs» меняются местами: «ours» — ветка, на которую переносите (main), «theirs» — ваши коммиты.

Профилактика: маленькие PR, частое обновление от main, форматтер (меньше шумовых изменений), договорённость о владении файлами, не переформатировать чужой код в фича-PR.

### Полезные команды

```bash
git rebase -i main             # переупорядочить, склеить (fixup/squash), переименовать коммиты перед PR
git commit --fixup=<hash>      # исправление к конкретному коммиту; затем git rebase -i --autosquash
git bisect start; git bisect bad; git bisect good v2.3.0
git bisect run pnpm vitest run search.test.ts   # автоматический поиск регрессии
git reflog                     # история перемещений HEAD: найти «потерянный» коммит после reset/rebase
git cherry-pick <hash>         # перенести коммит (hotfix в релизную ветку)
git revert <hash>              # отменить опубликованный коммит новым коммитом
git restore --staged file      # убрать из индекса
git stash push -m "wip"        # отложить изменения
git switch -c fix/login        # новая ветка
git log --oneline --graph --all
git blame -w -C file           # кто менял строку, игнорируя пробелы и перемещения
```

`.git-blame-ignore-revs` — исключить из `blame` массовые коммиты форматирования.

### Восстановление

- Удалил ветку / сделал `reset --hard` / испортил rebase → `git reflog`, найти хэш, `git branch restore <hash>` или `git reset --hard <hash>`.
- Закоммитил секрет → удаление из истории (`git filter-repo`) **и обязательно ротация секрета**: он уже мог утечь.
- Закоммитил в main вместо ветки → `git branch feature` (сохранить), `git reset --hard origin/main` на main.

### Стратегии ветвления

- **Trunk-based** — короткие ветки (часы–дни), частые слияния в main, незавершённое — за feature flags. Стандарт для CI/CD.
- **GitHub Flow** — ветка на фичу → PR → main → деплой.
- **GitFlow** — develop, release, hotfix ветки; для продуктов с версиями и редкими релизами; для веб-приложений обычно избыточен.

Сообщения коммитов: Conventional Commits (`feat:`, `fix:`, `refactor:`) — читаемая история и автоматический changelog.

## Вопросы с собеседований

<details><summary>Как вы работаете с git: ветки, merge, rebase?</summary>

Короткие фича-ветки от main, атомарные коммиты с понятными сообщениями, регулярный rebase на main, перед PR — `rebase -i` для чистой истории, слияние — squash или merge по договорённости команды, защищённый main с обязательным CI и ревью. Общие ветки не переписываю, свою — с `--force-with-lease`.
</details>

<details><summary>Почему возникают конфликты и как их исправить?</summary>

Обе ветки изменили одни строки. Разобраться в намерении сторон (`log --merge`, zdiff3), собрать корректный результат, прогнать тесты, продолжить merge/rebase. Уменьшать конфликты маленькими PR и частым обновлением.
</details>

<details><summary>Как восстановить коммит после `git reset --hard`?</summary>

`git reflog` хранит историю перемещений HEAD (по умолчанию ~90 дней): найти хэш и создать ветку или сбросить на него.
</details>

<details><summary>Чем `revert` отличается от `reset`?</summary>

`reset` перемещает указатель ветки (переписывает историю, для локальных изменений). `revert` создаёт новый коммит с обратными изменениями — безопасно для опубликованной истории.
</details>

## Практика

1. В учебном репозитории сделайте 5 коммитов и с помощью `rebase -i` склейте их в 2 с понятными сообщениями.
2. Сымитируйте конфликт при rebase и разрешите его с `zdiff3`.
3. «Потеряйте» коммит через `reset --hard` и восстановите через `reflog`.
4. Решите задачу из теста темы: имитация `git bisect`.
