## Теория

### Путь запроса

```
Браузер → DNS → CDN (кэш статики и HTML) → балансировщик / Ingress → nginx (опционально)
       → Pod с Node.js (Next.js server) → API / БД / кэш (Redis)
```

На собеседовании про «технологическую грамотность» обычно спрашивают именно это: где запрос может закэшироваться, где упасть по таймауту, где теряется заголовок, сколько процессов обслуживают пользователя и что будет, если один из них перезапустится.

### Три способа запустить Next.js

| Способ | Что получается | Когда |
|---|---|---|
| `next build && next start` | Node-сервер, нужен весь `node_modules` | просто, но образ тяжёлый |
| `output: 'standalone'` | `.next/standalone/server.js` + только нужные зависимости (их находит трассировка импортов) | контейнеры, свой сервер |
| `output: 'export'` | статический HTML/JS в `out/`, сервера нет | нет SSR, Server Actions, ISR, middleware/proxy, оптимизации картинок «на лету» |

🪤 **Ловушка standalone:** в `.next/standalone` не попадают `public/` и `.next/static/`. Их нужно скопировать рядом с `server.js` или отдать с CDN — иначе стили и чанки вернут 404.

Платформы вроде Vercel скрывают всё, что ниже. На собеседовании полезно сказать, что вы понимаете, *что именно* они скрывают: CDN, кэш между инстансами, раскатку и защиту от рассинхрона версий.

### Dockerfile

```dockerfile
# 1. Зависимости — отдельный слой: кэшируется, пока не изменился lock-файл
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# 2. Сборка
FROM node:22-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED=1
# NEXT_PUBLIC_* нужно передать ЗДЕСЬ — они вшиваются в бандл
ARG NEXT_PUBLIC_SENTRY_DSN
RUN npm run build

# 3. Рантайм — только то, что нужно для запуска
FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production NEXT_TELEMETRY_DISABLED=1 PORT=3000 HOSTNAME=0.0.0.0
RUN addgroup -S app && adduser -S app -G app
COPY --from=builder --chown=app:app /app/.next/standalone ./
COPY --from=builder --chown=app:app /app/.next/static ./.next/static
COPY --from=builder --chown=app:app /app/public ./public
USER app
EXPOSE 3000
CMD ["node", "server.js"]
```

Что спросят про этот файл:
- **Зачем три стадии?** В итоговом образе нет исходников, devDependencies и кэша сборки. Образ меньше, быстрее скачивается при масштабировании, меньше поверхность атаки.
- **Почему сначала `package*.json`, а потом весь код?** Слой с `npm ci` пересобирается только при изменении зависимостей.
- **Почему не root?** Если в приложении найдут уязвимость, у процесса будет меньше прав.
- **Почему `CMD ["node", "server.js"]`, а не `npm start`?** npm — лишняя прослойка: сигналы `SIGTERM` до приложения могут не дойти, контейнер будет убит по таймауту через `SIGKILL`. Форма exec (массив) запускает процесс без shell.
- **`HOSTNAME=0.0.0.0`** — иначе сервер слушает только localhost внутри контейнера и снаружи недоступен.
- **`.dockerignore`**: `node_modules`, `.next`, `.git`, `.env*` — чтобы не тащить мусор и секреты в контекст сборки.

### Переменные окружения: сборка или рантайм

| Где используется | Когда подставляется |
|---|---|
| `NEXT_PUBLIC_*` в клиентском коде | **при сборке**, значение вшивается строкой в JS-бандл |
| `process.env.X` в серверном коде динамической страницы | в рантайме, при каждом запросе |
| `process.env.X` в серверном коде **статической** страницы | при сборке — страница отрендерена заранее |

Последствия:
- Один образ нельзя «перенастроить» на другое окружение через `NEXT_PUBLIC_*` — нужна пересборка. Это ломает принцип «собрать один раз», см. [CI/CD](../10-tooling-testing/05-ci-cd-devops.md).
- Решение: публичную конфигурацию отдавать с сервера в рантайме — серверный компонент читает `process.env` и передаёт значения клиенту через props/контекст. Страница при этом должна быть динамической (например, `await connection()`).
- `NEXT_PUBLIC_` — это публичные данные. Ключ API с этим префиксом виден любому в DevTools.

### Когда реплик больше одной

Kubernetes обычно держит 2+ пода, и вот что начинает расходиться:

1. **Кэш данных и ISR.** По умолчанию Next.js хранит кэш в памяти и на диске *каждого* инстанса. `revalidateTag` или `revalidatePath` попадёт в один под — остальные отдают старые данные. Решение — общий кэш через `cacheHandler` (например, Redis) и отключение кэша в памяти (`cacheMaxMemorySize: 0`). Для `'use cache'` в новых версиях — отдельные `cacheHandlers`.
2. **Ключ шифрования Server Actions.** Next.js шифрует замыкания Server Actions. Если у реплик или у старой и новой сборок разные ключи, вызов падает. Решение — общий `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` во всех инстансах.
3. **Build ID.** Должен совпадать у всех реплик одной версии — собирайте образ один раз, а не на каждом сервере.
4. **Рассинхрон версий при раскатке.** Пользователь получил HTML от новой версии, а за чанком пришёл к старому поду — 404. Или наоборот: старая вкладка вызывает Server Action, которого в новой сборке уже нет («Failed to find Server Action»). Что помогает:
   - статику отдавать с CDN или объектного хранилища и хранить несколько версий (`assetPrefix`);
   - опция `deploymentId`: Next.js помечает ассеты и запросы версией и при расхождении делает полную перезагрузку страницы;
   - ловить ошибку загрузки чанка и один раз перезагружать страницу.

### nginx, CDN и заголовки

Зачем прокси перед Node: TLS, сжатие, раздача статики, ограничение частоты запросов, буферизация медленных клиентов, единая точка для нескольких сервисов.

```nginx
location /_next/static/ {
  alias /app/.next/static/;
  add_header Cache-Control "public, max-age=31536000, immutable";
}

location / {
  proxy_pass http://next_upstream;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_buffering off;          # иначе nginx копит ответ целиком и ломает стриминг
}
```

🪤 **Ловушка стриминга:** nginx по умолчанию буферизует ответ. Suspense-стриминг и `loading.tsx` перестают работать: пользователь видит страницу целиком только когда всё догрузилось. Лечится `proxy_buffering off` или заголовком `X-Accel-Buffering: no` в ответе.

Кэширование на CDN:
- `/_next/static/*` — имена с хэшем, кэш на год, `immutable`.
- Динамический HTML — `private, no-store` (персональные данные не должны попасть в общий кэш).
- ISR и статические страницы — `s-maxage` + `stale-while-revalidate`: CDN отдаёт старую версию и обновляет её в фоне.
- `Vary` и cookies: если ответ зависит от cookie, а CDN это не учитывает, один пользователь увидит страницу другого. Это реальный инцидент, а не теория.

Оптимизация картинок (`next/image`) нагружает CPU сервера. При большом трафике её выносят на CDN с ресайзом через собственный `loader`.

### Остановка и проверки здоровья

Что происходит при раскатке в Kubernetes:
1. Под получает `SIGTERM`. Одновременно его убирают из балансировки, но не мгновенно.
2. Приложение перестаёт принимать новые запросы, дожидается текущих и закрывает соединения с БД и Redis.
3. Через `terminationGracePeriodSeconds` (по умолчанию 30 с) приходит `SIGKILL`.

```js
let shuttingDown = false;
process.on('SIGTERM', async () => {
  shuttingDown = true;                 // readiness начинает отвечать 503
  await sleep(5_000);                  // даём балансировщику убрать под
  server.close(() => process.exit(0)); // дожидаемся текущих запросов
  setTimeout(() => process.exit(1), 20_000).unref();
});
```

Для standalone-сервера Next.js собственные обработчики сигналов включаются переменной `NEXT_MANUAL_SIG_HANDLE=true`.

| Проба | Вопрос | Что проверять |
|---|---|---|
| **startup** | процесс запустился? | дать время на холодный старт |
| **readiness** | можно слать трафик? | приложение готово; при остановке → 503 |
| **liveness** | процесс жив или завис? | **только сам процесс**, без БД и внешних API |

🪤 **Ловушка:** если liveness проверяет базу данных, то при падении базы Kubernetes начнёт перезапускать *все* поды фронтенда. Получится каскадный отказ вместо частичной деградации.

### Память, CPU и масштабирование

- Node.js однопоточный для JS: один процесс использует одно ядро. Масштабируются числом подов, а не потоков. CPU-тяжёлый SSR блокирует event loop для всех запросов этого пода.
- Лимит памяти контейнера и куча V8 — разные вещи. При превышении лимита контейнера процесс молча убивает OOM killer (`OOMKilled` в `kubectl describe pod`). Явно задайте `--max-old-space-size` примерно 75% от лимита, чтобы GC начал работать раньше.
- Автомасштабирование (HPA) обычно по CPU. Для SSR полезны метрики задержки: p95 TTFB, задержка event loop.

### Профилирование и утечки в SSR

Типичные причины утечек на сервере:
- модульная переменная-кэш (`const cache = new Map()`), которая растёт с каждым запросом;
- подписки и `setInterval`, созданные во время рендера и не очищенные;
- данные пользователя, сохранённые в модульной области, — это ещё и утечка *данных между пользователями*.

Инструменты:
- `node --inspect` + Chrome DevTools (`chrome://inspect`): CPU-профиль, снимки кучи. Сравнение двух снимков под нагрузкой показывает растущие объекты.
- `node --heapsnapshot-signal=SIGUSR2` — снять снимок кучи у работающего процесса командой `kill -USR2 <pid>`.
- `node --cpu-prof` — профиль CPU в файл.
- `perf_hooks.monitorEventLoopDelay()` — задержка event loop как метрика.
- `instrumentation.ts` в Next.js: подключение OpenTelemetry и хук `onRequestError` для отправки серверных ошибок в мониторинг.

Логи — в stdout в формате JSON, с request-id. Собирает их инфраструктура (Loki, ELK, Datadog), а не приложение.

## Вопросы с собеседований

<details><summary>Как вы задеплоите Next.js-приложение без Vercel?</summary>

`output: 'standalone'`, многоэтапный Docker-образ без root, запуск `node server.js`. Статика `/_next/static` — на CDN с долгим кэшем. Перед сервером — Ingress или nginx с TLS и без буферизации ответов. Минимум две реплики, общий кэш для ISR и `revalidateTag` через `cacheHandler` и Redis, единый ключ Server Actions. Проверки здоровья, корректная остановка по `SIGTERM`, логи в stdout, мониторинг ошибок и метрик.
</details>

<details><summary>Почему после смены переменной окружения в Kubernetes значение на клиенте не поменялось?</summary>

Переменная с префиксом `NEXT_PUBLIC_` вшивается в бандл при сборке. Перезапуск пода её не меняет — нужна пересборка. Если конфигурация должна меняться без сборки, её отдают с сервера в рантайме. Аналогично для статических страниц: серверный `process.env` прочитан при сборке.
</details>

<details><summary>Что ломается, когда у Next.js-приложения появляется вторая реплика?</summary>

Кэш данных и ISR у каждой реплики свой — нужен общий `cacheHandler`. Ключ шифрования Server Actions должен совпадать. Сборка должна быть одна (одинаковый build ID). При раскатке появляется рассинхрон версий: старые вкладки запрашивают несуществующие чанки или Server Actions — нужна стратегия для ассетов и `deploymentId`.
</details>

<details><summary>Чем liveness отличается от readiness и что в них проверять?</summary>

Readiness — «можно ли слать трафик»: при старте и при остановке под должен отвечать «не готов». Liveness — «жив ли процесс»: при провале Kubernetes перезапускает контейнер. В liveness нельзя проверять внешние зависимости, иначе сбой базы приведёт к перезапуску всех подов.
</details>

<details><summary>Пользователи жалуются, что страница «долго белая», хотя в dev стриминг работает. Почему?</summary>

Скорее всего, прокси (nginx, иногда CDN или балансировщик) буферизует ответ и отдаёт его целиком. Проверить: `curl -N` напрямую к поду и через прокси, сравнить время прихода первых байт. Лечится `proxy_buffering off` или заголовком `X-Accel-Buffering: no`.
</details>

<details><summary>Под периодически перезапускается с OOMKilled. Как разбираться?</summary>

Посмотреть графики памяти: растёт ли память постоянно (утечка) или скачками под нагрузкой (недостаточный лимит). Для утечки — снимки кучи под нагрузкой с интервалом и их сравнение; искать модульные кэши, подписки, данные запросов в глобальной области. Задать `--max-old-space-size` ниже лимита контейнера. Временная мера — поднять лимит, но не вместо поиска причины.
</details>

<details><summary>Где в цепочке «браузер → CDN → nginx → Node» может закэшироваться ответ и чем это опасно?</summary>

В браузере (`Cache-Control`), на CDN (`s-maxage`), в nginx (`proxy_cache`), в кэше данных Next.js. Опасно кэшировать персональный ответ в общем кэше: если CDN не учитывает cookie или `Authorization`, один пользователь увидит данные другого. Для персональных страниц — `private, no-store`, для общих — явные `s-maxage` и корректный `Vary`.
</details>

<details><summary>Как SSR может блокировать других пользователей?</summary>

JS в Node выполняется в одном потоке. Тяжёлый синхронный рендер или вычисление (огромный JSON, сортировка, разбор markdown) блокирует event loop, и все остальные запросы этого пода ждут. Помогают: вынести тяжёлое в воркеры или отдельный сервис, кэшировать результат, стримить, следить за задержкой event loop.
</details>

## Практика

1. Соберите standalone-образ своего Next.js-проекта и сравните его размер с образом на `next start`.
2. Поставьте перед ним nginx в `docker compose` и убедитесь через `curl -N`, что стриминг работает только с `proxy_buffering off`.
3. Запустите две реплики и проверьте, что `revalidateTag` на одной не обновляет данные на другой. Затем подключите общий `cacheHandler`.
4. Снимите два снимка кучи под нагрузкой (`autocannon`) и найдите растущий объект в намеренно «протекающем» модуле.
