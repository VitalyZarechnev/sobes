## Теория

### Типы флагов

| Тип | Пример | Срок жизни |
|---|---|---|
| Релизный | новая страница корзины за флагом | дни–недели, удалить после 100% |
| Экспериментальный | вариант A/B кнопки | до конца эксперимента |
| Операционный (kill switch) | отключить тяжёлую рекомендательную ленту при нагрузке | долго |
| Разрешения/тарифы | фича для тарифа Pro | постоянно (это уже конфигурация продукта) |

### Где вычислять

- **Сервер / edge** — флаги известны до рендера: нет мигания, SSR сразу правильный, назначение варианта стабильно (cookie). Предпочтительно.
- **Клиент** — SDK загружает флаги; до загрузки нужен дефолт. Опасность — мигание и сдвиги макета.
- Значения по умолчанию в коде на случай недоступности сервиса флагов. Таймаут загрузки флагов — короткий.

```ts
// Типизированный доступ: опечатка в имени флага — ошибка компиляции
const FLAGS = {
  newCheckout: false,
  searchV2: false,
} as const satisfies Record<string, boolean>;
type FlagName = keyof typeof FLAGS;

export function isEnabled(name: FlagName, provider: FlagProvider): boolean {
  return provider.getBoolean(name, FLAGS[name]); // дефолт из кода
}
```

OpenFeature — вендор-нейтральный стандарт API флагов (провайдеры LaunchDarkly, Unleash, GrowthBook, Flagsmith, свой).

### Гигиена

- У каждого флага — владелец, тип, дата удаления.
- Отчёт о «протухших» флагах (100% включены > 30 дней) и задача на удаление кода.
- Не вкладывать флаги друг в друга; ветка кода за флагом — минимальная (на уровне маршрута или компонента).
- Тестировать оба состояния критичных флагов.
- Флаги — не замена авторизации: скрытая кнопка не защищает API.

### A/B-эксперименты без вреда производительности

🪤 **Ловушка anti-flicker:** клиентские инструменты экспериментов прячут страницу (`opacity: 0`), пока не применят вариант — LCP ухудшается на сотни миллисекунд у всех пользователей.

Правильно:
1. Назначение варианта на сервере или edge (middleware), хранение в cookie.
2. Оба варианта — код в приложении; тяжёлая ветка — ленивый чанк.
3. Событие показа (exposure) отправляется в момент реального отображения варианта, а не при назначении.
4. Guardrail-метрики в каждом эксперименте: CWV, ошибки, ключевые бизнес-метрики.
5. Чистка кода после эксперимента.

### Статистика (минимум для лида)

- Размер выборки и длительность — **заранее** (минимально детектируемый эффект, мощность); минимум полный недельный цикл.
- «Подглядывание» и остановка при первой значимости даёт ложные победы — фиксированный горизонт или последовательные методы.
- Множественные метрики/варианты увеличивают вероятность ложноположительного результата.
- Sample ratio mismatch (например, 50/50 превратилось в 48/52) — признак бага в назначении или трекинге.

## Вопросы с собеседований

<details><summary>Как управлять feature flags в масштабе?</summary>

Сервис флагов со стандартным API (OpenFeature), вычисление на сервере/edge, типизированный список флагов с дефолтами в коде, типы флагов и жизненный цикл, владелец и срок, отчёты о протухших флагах, удаление кода после раскатки, тестирование обоих состояний.
</details>

<details><summary>Как сделать A/B-тест без проблем с производительностью?</summary>

Назначать вариант на сервере/edge, не прятать страницу anti-flicker-скриптом, держать варианты в коде (тяжёлые — лениво), отправлять exposure в момент показа, отслеживать CWV и ошибки как guardrails, удалять код после завершения.
</details>

<details><summary>Чем feature flag отличается от ветки в git?</summary>

Ветка — изоляция кода до слияния (долгие ветки — конфликты и интеграционный ад). Флаг — изоляция **поведения** в уже слитом коде: trunk-based development, деплой отделён от релиза, можно включать постепенно и выключать мгновенно.
</details>

## Практика

1. Сделайте типизированный слой флагов с дефолтами и провайдером из JSON (задача в тесте темы — детерминированное распределение по процентам).
2. Найдите в своём проекте флаги, включённые на 100% больше месяца.
